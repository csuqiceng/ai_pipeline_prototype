日期: 2026-05-14

范围: 重构前原始目录 `新方案_Qt项目副本` 内的源码、运行配置、mock、工具脚本、打包脚本和主要运行数据。`build/`、`dist/`、`打包输出/`、`build_output/` 中的二进制和 PyInstaller 产物只作为发布产物记录，不作为业务源码重复盘点。重构后当前目录的保留/裁剪情况见本文第二十三章。

## 一、项目定位

本项目是“双车床机械手自然语言编程控制系统”的 Qt 桌面应用副本。当前实现不是单纯的 Modbus 通讯 demo，而是一个完整的上位机应用，包含：

- PySide6 桌面 GUI。
- 六轴机械手 V4.3 Modbus TCP 协议发送链路。
- 历史 VR/标准协议兼容模型与 mock 行为。
- 指令模板管理、流程编排、并行流程执行。
- 自然语言文本解析、DeepSeek 在线解析、讯飞语音识别。
- 授权/订阅、代理模式 API 访问、配额展示。
- 本地 mock 控制器、真机 ZMotion SDK 客户端。
- 系统配置、安全限位、安全中间点、日志、导入导出、打包。

## 四、当前支持的机器人函数

当前项目的 V4.3 主路径支持以下函数：

| 函数 | 名称 | slot | 当前状态 |
|---|---|---|---|
| Func104 | 系统控制/急停/暂停/结束/复位 | system | 已实现。跳过普通前置检查，可在任意状态触发。 |
| Func106 | 关节点动 | motion | 已实现。支持轴号 0~5、目标值、速度/加减速百分比、模糊选项、停止指令。 |
| Func107 | 虚拟轴点动 | motion | 已实现。支持轴号 6~11、目标值、速度/加减速百分比、模糊选项、停止指令。 |
| Func108 | 直线插补/PTP | motion | 已实现。支持位姿目标、速度/加减速百分比、模糊选项、停止指令、move_type。 |
| Func11 | 多点插补 | motion | 已实现模型、模板、mock 和发送参数。 |
| Func109 | T0 定时检测 | motion | 已实现。 |
| Func110 | T1 延时 | program | 已实现。支持执行中再次 Func110 覆盖更新时间。 |
| Func120 | IO 控制/夹爪输出 | program | 已实现。 |
| Func111 | 预留 | 未定 | 当前不实现，文档已标注预留。 |

slot 规则：

- `motion`: Func11/106/107/108/109 同槽互斥。
- `program`: Func110/120 同槽互斥，但 Func110 执行中再次 Func110 是覆盖更新特例。
- `system`: Func104 不受 motion/program slot 限制。

### 5.1 命令构建

`RobotModbusService.build_six_command_from_record()` 将模板 `QueryRecord` 转成 `SixAxisCommand`。

`SixAxisCommand.to_func_writes()` 决定 IEEE 参数写入：

| 函数 | 写入概要 |
|---|---|
| Func104 | IEEE(0)=104，IEEE(2/4/6/8)=estop/pause/cancel/reset。 |
| Func106/107 | IEEE(0)=函数号，IEEE(2~20)=轴号、位置、速度、加减速、模糊、停止。 |
| Func108 | IEEE(0)=108，IEEE(2~30)=目标位姿、速度、加减速、停止、模糊、运动模式。 |
| Func11 | IEEE(0)=11，IEEE(2)=点数，IEEE(14/16/18)=速度/加减速，IEEE(400+) 写插补点。 |
| Func109 | IEEE(0)=109，IEEE(2)=check_value，IEEE(4)=delay_sec。 |
| Func110 | IEEE(0)=110，IEEE(6)=delay_sec。 |
| Func120 | IEEE(0)=120，IEEE(2)=io_no，IEEE(4)=io_action。 |

触发写入：

```text
IEEE(32) = 1
```

回显地址：

```text
IEEE(280 + src_addr) = IEEE(src_addr)
```

### 5.2 发送顺序

当前 Qt 发送顺序：

1. 非 Func104 先读 LONG(34) 做前置检查。
2. 写 IEEE(0~30) 参数。
3. 读 IEEE(280~312) 回显。
4. 回显匹配后写 IEEE(32)=1 触发。
5. 等待 LONG(34) 对应函数位进入 DONE 或 ERR。
6. 读取反馈区和实时位姿。

Func104 特例：

- 不做普通前置检查。
- 仍写参数、校验回显、触发。
- 等待 Func104 DONE。
- 校验急停、暂停、结束、复位后的 LONG(34)/LONG(36) 状态。

### 5.3 回显容错

当前默认配置来自 `data/system_config.json` 和 fallback 常量：

| 参数 | 默认值 |
|---|---:|
| `echo_retry_interval_sec` | 0.005 |
| `echo_retry_count` | 3 |
| `echo_write_rounds` | 2 |
| `echo_compare_epsilon` | 0.001 |

流程：

1. 每轮写参数。
2. 按 5ms 间隔读回显，最多 3 次。
3. 任一轮回显匹配即继续触发。
4. 当前轮失败且还有写入轮次，则重写参数。
5. 2 轮都失败则抛出“六轴回显通讯失败”。

### 5.4 LONG(34) 状态解析

`SixAxisStatus` 解析函数状态和全局状态：

- 函数状态：每个函数 2bit，`IDLE/EXEC/DONE/ERR`。
- 全局报警：34.24。
- 急停：34.25。
- 暂停：34.26。
- 结束/取消：34.27。
- 就绪：34.28。

当前实现状态位：

- 104: 34.00/01
- 106: 34.02/03
- 107: 34.04/05
- 108: 34.06/07
- 109: 34.08/09
- 110: 34.10/11
- 11: 34.14/15
- 120: 34.18/19

Func111 为预留，不解析为可执行函数。

### 5.5 LONG(38) 报警解析

`SixAxisAlarmDetail` 支持：

- bit0 半径超限。
- bit1 高度超限。
- bit2 指令忙。
- bit3 速度超限。
- bit4 加速度超限。
- bit5 减速度超限。
- bit6 ECAT 异常。
- bit7 驱动器报警。
- bit8 函数号非法。
- bit9 参数非法。

### 5.6 指令忙自动恢复

当前只对 LONG(38).02 指令忙做有限自动恢复：

1. `_wait_six_command_done()` 发现 ERR 后抛 `SixAxisCommandRuntimeError`。
2. `_execute_send_six()` 检查 `exc.is_cmd_busy`。
3. 最多自动恢复 2 次。
4. 等待目标 slot 空闲，默认最多 5s。
5. 发送 Func104 `reset_ctrl=1`。
6. 等待 Func104 DONE。
7. 等待 34.28 就绪且 34.24 无报警，默认最多 5s。
8. 重发原命令。

其他 ERR 不自动循环复位，直接向上层报错。

### 5.7 反馈读取

当前读取：

- Func11：IEEE(640) 当前点，IEEE(642) 总点。
- Func109：IEEE(326) 检测结果，IEEE(330) 延时。
- Func110：IEEE(328) 状态，IEEE(332) 延时，LONG(40) 计时 ms。
- Func120：LONG(44) Y 输出状态，LONG(46) X/反馈状态。
- 通用位姿：IEEE(1612~1622)。
- 通用关节：IEEE(1600~1610)。
- 运动状态：IEEE(56)。
- 可选兼容反馈：IEEE(52)、IEEE(54)、IEEE(70)、IEEE(72)。

## 七、流程执行功能

流程执行位于 `qt_gui.py`。

支持：

- 启动流程。
- 单步执行。
- 停止流程。
- 重置流程。
- 步间延时。
- 流程启动前检查模板是否存在。
- 流程启动前等待控制器就绪。
- 流程执行失败后停止。
- 与自然语言动作序列联动。

并行流程组规则：

- 当前步骤是 motion 函数。
- 下一步是 Func110。
- 可选第三步是 Func120。
- 执行顺序：
  - motion 先触发不等待。
  - Func110 触发并等待完成。
  - Func120 如存在，触发并等待完成。
  - 最后等待 motion 完成。

当前并行能力是特定模式，不是任意 DAG/任意并发调度器。

### 12.1 配置默认值来源说明

重构时要区分两类默认值来源：

| 来源 | 位置 | 作用 |

| G16 | 根目录 `license.db` 与当前 GUI 授权缓存路径不一致 | 当前 GUI 使用 `LicenseManager(self.runtime_root / "data")` 和 `data/license_cache.enc`；根目录存在 `license.db` | 可能是历史授权数据或废弃产物，重构时不应盲目迁移 | 先确认来源；若不用则移入归档或加入清理清单 |

| G18 | Python 依赖没有独立锁定文件 | 根目录未见 `requirements.txt`/`pyproject.toml`/锁文件；打包脚本默认本机环境已装 PySide6、PyInstaller、requests、cryptography、sounddevice 等 | 换机器重构、CI、打包复现成本高 | 重构前补依赖清单，并区分运行依赖、打包依赖、语音可选依赖 |

### 22.3 二次复核结论

当前功能盘点没有发现大块业务域遗漏：GUI、协议、mock、自然语言、语音、授权、流程、安全、日志、工具脚本均已覆盖。

真正需要在重构前额外注意的是：

1. 用户可见但语义不完整的功能：`启动/停机/上电` 系统按钮、协议下拉显示。
2. 历史入口和历史协议兼容代码：`cli.py`、旧 VR/标准协议模型。
3. 配置可达性问题：回显参数只在 JSON 中，GUI 未暴露。
4. 发布工程问题：打包脚本硬编码路径、真实 `.env` 打包、构建产物和运行日志污染工作区。
5. 工程复现问题：README 表述过时、依赖未锁定、旧 demo/旧授权数据需要归档或明确保留。

建议在正式重构方案里先做一次“保留/废弃/改名”裁决，尤其是 G1/G2/G3/G4/G12/G13/G18/G19。否则重构后容易把历史行为继续带入新架构，或者继续依赖当前机器环境才能运行和打包。

### 22.4 隐蔽运行模式与拆分风险

本节记录源码中不容易从功能入口直接看出的运行模式。它们不一定是当前 bug，但会直接影响 `qt_gui.py`、协议层、语音层和授权层的重构边界。

| 编号 | 隐蔽模式 | 源码位置 | 重构影响 | 建议 |
|---|---|---|---|---|
| H1 | 线程模型分散，未形成统一抽象 | `qt_gui.py` 使用 `threading.Lock`、`threading.local`、裸 `threading.Thread`、局部 `QThread`；`mock_controller/controller.py` 使用 `RLock` 和执行线程；`zmotion_client.py` 使用 `Lock`；`license_dialog.py` 使用 2 个 `QThread`；`license_manager.py` 使用心跳线程 | 拆分 GUI 后如果线程归属不清，容易出现 UI 跨线程更新、锁粒度混乱和关闭时资源泄露 | 重构时先定线程策略：UI 只收信号/队列，IO/协议/语音/授权后台任务统一封装；不要继续在业务方法里随手开裸线程 |
| H2 | `MicStreamThread` 是 `qt_gui.py` 内部类 | `qt_gui.py::_ensure_mic_stream()` 内部定义 `MicStreamThread(QThread)`，带 `audio_captured = Signal(bytes)` | 方法索引不容易看到这个类，迁移语音模块时可能遗漏 | 抽出到独立语音 worker 模块，并明确音频帧缓冲和停止语义 |
| H3 | 麦克风 worker 使用文件 IPC 停止信号 | `qt_gui.py` 创建 `data/exported_logs/voice_stop_<timestamp>.flag`；`iflytek_worker.py` 传入 `--stop-flag-path`；`iflytek_iat.py::_should_stop()` 轮询文件是否存在 | 这是 GUI 与 worker 子进程之间的隐式协议，误删会导致录音子进程无法停止或超时退出 | 保留时写成显式 `VoiceWorkerStopSignal` 抽象；替换时改为管道/队列/进程事件，并保留打包场景可用性 |
| H4 | 授权机器码依赖平台命令和注册表 | `license_manager.py` 调用 `subprocess.run()` 执行 `wmic`、`powershell`，Linux 下读 `/proc/cpuinfo`，Windows 下读 `winreg` | 跨平台重构、打包权限和无控制台环境下可能失败 | 将硬件指纹采集隔离为平台适配器，失败时有降级路径和可诊断日志 |
| H5 | 动态导入和延迟导入较多 | `zmotion_client.py` 通过 `importlib.util.spec_from_file_location()` 加载 ZMotion SDK；`qt_gui.py` 延迟检测/导入 `xfyunsdkspeech`、`sounddevice`、`numpy`、`requests`；`iflytek_iat.py` 动态选择 `sounddevice`/`pyaudio` | 打包、依赖清单、模块拆分时容易漏 hidden import 或可选依赖 | 在依赖清单中区分必需/可选/打包 hidden imports，并把 SDK 加载逻辑封装到单一适配器 |
| H6 | Qt Signal/Slot 连接关系密集 | `qt_gui.py` 约 72 处 `.connect()`；整个 `robot_modbus_lite` 约 80 处 `.connect()`；自定义信号包括 `_main_thread_call` 和 `audio_captured` 等 | UI 拆文件时最容易漏连接或产生重复连接 | 拆分 UI 前先按页面/组件生成连接清单；每个组件负责自己的信号绑定，主窗口只做编排 |
| H7 | `RobotQtWindow` 持有大量无结构实例状态 | `RobotQtWindow.__init__` 中 `self.` 赋值约 74 个，包括连接缓存、日志、流程、机器人实时态、NLP、语音、授权、配置等 | 这是 `qt_gui.py` 最难拆的部分；状态读写跨轮询线程、后台线程和 UI 刷新，容易在拆分后丢失同步关系 | 先建立状态模型：`ConnectionState`、`RobotRealtimeState`、`FlowExecutionState`、`VoiceState`、`LogSessionState`、`LicenseUiState`；再拆 UI |
| H8 | 自定义异常未集中管理，领域异常混在 GUI 层 | 自定义异常包括 `CommandParseError`、`FlowStoreError`、`QueryTableError`、`IFlytekRTASRError`、`ZMotionClientError`、`ValidationError`、`SixAxisCommandRuntimeError`、`BackgroundTaskError` | `SixAxisCommandRuntimeError` 携带 V4.3 诊断字段但定义在 `qt_gui.py`，协议层重构时容易继续依赖 GUI 模块 | 新增协议/应用异常模块，把六轴发送异常移出 GUI；GUI 只负责展示错误 |
| H9 | PyInstaller 冻结路径和 worker 启动路径是运行兼容点 | `qt_gui.py::_runtime_dir()` 检查 `sys.frozen`；`_resource_dir()` 使用 `_MEIPASS`；`gui_main.py --iflytek-worker` 作为打包后 worker 入口 | 打包后路径、资源目录、子进程命令和源码运行路径不同，拆分入口时容易破坏 | 重构入口前保留源码模式/冻结模式两套路径测试；worker 命令构建集中到一个函数 |
| H10 | 依赖图总体可按层拆分，这是正面约束 | `models.py` 基本无包内依赖；`service.py` 不依赖 Qt；`qt_gui.py` 是上层编排节点；mock 和 tools 相对独立 | 可以降低重构风险，但 `cli.py` 已坏、`qt_gui.py` 对 mock 有 fallback import，不能当成完全无问题的 DAG | 推荐拆分顺序：先冻结 `models.py` 数据契约，再拆 `service.py` 协议/流程服务，再拆 `qt_gui.py` 页面和后台任务 |

优先级建议：

1. 先处理 H7/H3/H8：它们决定 GUI 状态模型、语音模块边界和协议异常归属。
2. 再处理 H1/H5/H6：它们决定后台任务框架、依赖清单和 UI 拆分方法。
3. 最后处理 H4/H9/H2：它们影响跨平台、打包和语音实现细节。
