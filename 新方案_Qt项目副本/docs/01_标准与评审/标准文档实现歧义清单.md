本文档不修改标准正文，只整理当前标准在工程实现时存在的歧义点，供后续评审确认。

## 1. `DEV_ID` 与 `posId` 的关系不清

标准中同时存在：
- `VR[10] DEV_ID = 设备/工位ID`
- JSON 中 `params.posId = 工位ID`

当前歧义：
- `posId` 是否最终直接写入 `VR[10]`
- `VR[10]` 是否只用于设备ID，`posId` 仅在上位机内部使用
- 如果两者都存在，控制器实际应读取哪一个字段

这会直接影响：
- 上位机 JSON 到 VR 的映射方式
- 后台模板设计
- 控制器内部查表方式

## 2. `TASK_ID` 说用于请求/响应匹配，但反馈区没有任务号

标准中定义：
- `VR[1] TASK_ID`
- 说明：用于匹配请求与响应

但反馈区只定义了：
- `VR[16] RESULT`
- `VR[17] STATUS`
- `VR[18]~VR[23] CUR_*`
- `VR[24] ALM_CODE`
- `VR[25] IO_STAT`

当前歧义：
- 响应中没有回传任务号字段
- 上位机如何确认当前响应对应哪个请求

这会直接影响：
- 指令队列实现
- 异步响应匹配
- 日志关联

## 3. `EMG_RESET` 需要 `alm_code`，但输入区没有对应寄存器

标准命令表中定义：
- `1008 EMG_RESET`
- JSON关键字段：`alm_code:0`

但指令区 `VR[0]~VR[15]` 中没有专门的报警清除码输入字段。

当前歧义：
- `alm_code` 应写入哪个 VR
- 是否复用 `EXT_P1`
- 还是 `EMG_RESET` 实际无需携带报警码

这会影响：
- 上位机 JSON 组包
- 下位机复位逻辑

## 4. “无参数指令一律禁止” 与固定函数/回零命令存在冲突

标准 8.1 写明：
- `无参数指令一律禁止`

但当前命令体系和业务需求中又存在明显接近无参数或固定语义的命令：
- `HOME`
- `EMG_RESET`
- 业务上明确提到的 `5001 固定函数`

当前歧义：
- 是真的完全禁止无参数指令
- 还是允许“固定函数型无参数指令”

这会影响：
- 后台模板字段设计
- 运行页按钮逻辑
- 控制器固定函数调用方式

## 5. `MOVE_REL` 的参数定义不完整

标准中定义：
- `1002 MOVE_REL`
- 示例：`Z轴向上抬升50mm`
- JSON关键字段：`z,speed(相对增量)`

但寄存器区仍固定有：
- `POS_X`
- `POS_Y`
- `POS_Z`
- `ROT_RX`
- `ROT_RY`
- `ROT_RZ`

当前歧义：
- `MOVE_REL` 是否只填写变化轴，未填写轴默认 `0`
- 是否支持 `RX/RY/RZ` 相对增量
- 是否必须全轴都写

这会影响：
- 自然语言解析
- JSON 构造
- 控制器解释方式

## 6. 通用 JSON 示例容易被误解为“所有命令都必须带完整位置参数”

标准中的通用 JSON 示例是 `MOVE_ABS`：

```json
{
  "taskId": 1001,
  "cmd": "MOVE_ABS",
  "code": 1001,
  "params": {
    "x": 120.5,
    "y": 80.0,
    "z": 45.0,
    "rx": 0.0,
    "ry": 0.0,
    "rz": 0.0,
    "speedPercent": 30,
    "accPercent": 40,
    "posId": 2
  },
  "safetyLevel": 5,
  "desc": "绝对移动到原料1号取料位"
}
```

但以下命令并不适合要求完整位置字段：
- `GRIP_SET`
- `DOOR_CTRL`
- `WAIT_MS`
- `CHECK_IN`
- `EMG_RESET`

当前歧义：
- 该 JSON 是否只是“移动类示例”
- 还是所有命令统一用这套必填结构

## 7. `IO_STAT` 位定义不完整

标准当前只写：
- `位0:门1, 位1:门2, 位2:夹爪...`

当前歧义：
- bit2 具体代表什么
- 是否还有急停位、限位位、夹爪有料位、卡盘位
- 状态页应如何逐位解释

这会影响：
- Qt 界面状态显示
- 报警联动
- 调试判断

## 8. `R/W` 容易引起误解

标准表中很多寄存器权限写为 `R/W`。

当前歧义：
- 是否允许 PC 和控制器都修改同一寄存器
- 还是仅表示“从系统角度可读写”，但实际分工不同

这会影响：
- 上下位机职责边界
- 通信实现方式

## 9. 数据类型定义和实际传输方式之间存在歧义

标准中同时使用了：
- `UINT16`
- `INT16`
- `FLOAT`

但当前项目实际通信链路和 SDK 调用多处按浮点处理。

当前歧义：
- 这些类型是“物理传输类型”
- 还是“业务解释类型”

这会影响：
- 上位机编码方式
- 下位机解析方式
- 日志展示方式

## 10. 设备ID与工位定义之间缺少明确映射规则

标准中有：
- `5.1 设备ID映射`
- `5.2 工位坐标定义`

但未明确：
- `posId = 2` 时，`DEV_ID` 应是什么
- 上位机是否应先把 `posId` 展开成坐标
- 控制器是否需要内部维护工位表

这会影响：
- 后台页面设计
- JSON 与 VR 的关系
- 控制器内部逻辑复杂度

## 当前最优先需要确认的 4 个点

1. `DEV_ID` 与 `posId` 的关系
2. `TASK_ID` 是否需要在反馈区回传
3. `EMG_RESET` 的 `alm_code` 应写入哪个字段
4. 是否允许固定函数型无参数指令，例如 `5001`
