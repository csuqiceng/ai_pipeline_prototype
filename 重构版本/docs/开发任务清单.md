## P0：安全和交互底线

### T001 修改应急语义：单独"急停"不直接执行

- **现状**：`_handle_operator_ui_command()` 中 `"急停"` / `"紧急停止"` 直接触发 `sys_estop`
- **目标**：单独提及"急停"关键词 → 提示"未识别有效授权应急指令，请使用标准格式 `急停 XXX 急停`"
- **代码位置**：`robot_modbus_lite/operator_ui_mixin.py` 中 `_handle_operator_ui_command()` 方法
- **验收**：输入"急停"不触发动作，对话区显示提示信息

---

### T002 新增三段式应急编码模块和白名单

- **目标**：新建 `robot_modbus_lite/emergency_channel.py`
- **内容**：
  - 正则匹配 `急停\s+\w{3,16}\s+急停` 三段式编码格式
  - 授权编码白名单管理（可配置的编码列表）
  - 编码命中 ≤30ms 直接触发 Func104 急停（独立通道，绕过 NLP 和预检队列）
  - 无效编码 ≤200ms 明确回应"编码无效，未执行"
  - 日常提及"急停"（不匹配三段式）只提示不执行
- **需明确的设计决策**：界面按钮急停是否也走本条通路，还是保留直接执行
- **验收**：`急停 ABC123 急停` → 触发急停；`急停` 或 `紧急停止了` → 仅提示

---

### T003 建立统一回应框架

- **目标**：新建 `robot_modbus_lite/response_builder.py`
- **定义四个回应层级**：

  | 层级 | 触发时机 | 时限 | 示例 |
  |------|---------|------|------|
  | `receipt` 回执 | 输入到达时 | ≤50ms(文字) / ≤200ms(语音) | "收到，正在处理" |
  | `progress` 进度 | 后台处理期间 | 每 2s 一次 | "安全预检进度60%，已完成限位检查和速度检查" |
  | `result` 结果 | 处理完成时 | ≤500ms(简单) / ≤5s(预演) | "J1运动完成，当前位置30.02°" |
  | `alert` 告警 | 状态异常变化 | 立即 | "注意：J2轴速度超限报警" |

- **安抚性回应模板**：后台等待期间自动填充当前设备状态
  > "收到查询，正在同步轴位数据。当前设备处于运行状态，无报警，通讯正常。"
- **验收**：每个层级都有独立的调用接口和时限日志

### T004 给用户页所有输入加即时回执

- **目标**：在 `operator_ui_mixin.py` 中接入 T003 的 `receipt` 层
- **文字输入回执**：
  - 用户按下"解析"或"执行"后 ≤50ms 显示"收到，正在处理"（`QTimer.singleShot(0, ...)` 在主线程）
  - 在 `_operator_push_text_to_nlp()` 或 `_operator_parse_text()` / `_operator_execute_text()` 入口处调用
- **语音输入回执**：
  - VAD 触发后 ≤200ms 显示"系统在线，正在识别"
  - 当前录音链路：start → stop → wait result，需改为在 start 成功时即给出回执
- **应急编码回执**：
  - T002 的编码命中路径自带 ≤30ms 回执
- **验收**：每条输入都有应答耗时日志，文字回执 < 50ms，语音回执 < 200ms

### T005 增加状态变化主动播报事件队列

- **目标**：新建 `robot_modbus_lite/broadcast_queue.py`
- **内容**：
  - 事件队列模型：`(priority, event_type, message, timestamp)`
  - 优先级：`estop(0) > alarm(1) > motion_done(2) > precheck_fail(3) > comm_error(4)`
  - 去重策略：同一 event_type 连续触发时合并/限频
  - 播报通道：当前先接入对话区 `_operator_add_chat_message("assistant", message)`，后续可扩展语音 TTS
- **触发点**（需在各种状态变化处注册）：
  - 报警发生/清除
  - 急停按下/释放
  - 暂停/继续
  - 运动完成
  - 通讯异常/恢复
  - 预检不通过
- **同时修复 `_operator_add_chat_from_log()` 阻断点**：
  - 当前只处理 `category == "自然语言"` 的日志
  - 扩展为：至少处理 `category in {"系统", "六轴", "自然语言"}` 的日志
- **验收**：报警发生时对话区自动出现报警描述，运动完成时自动出现"J1运动完成，当前xx°"

## P1：看板和预检

### T006 抽独立看板缓存层

- **目标**：新建 `robot_modbus_lite/dashboard.py`
- **内容**：
  - 7 个看板 dataclass：
    - `Dashboard1_DeviceStatus`（急停/暂停/报警/伺服/夹爪/通讯/ECAT）
    - `Dashboard2_ActionFeasibility`（四条件、通道空闲、回显一致、预检通过）
    - `Dashboard3_SafetyBoundary`（R/Z安全范围、当前R/Z、软限位）
    - `Dashboard4_MotionLimits`（速度/加减速上限、当前速度、超限报警）
    - `Dashboard5_FlowPrecheck`（预演活跃、总步数/当前步、进度%、风险汇总）
    - `Dashboard6_ProcessAdaptation`（FSTATUS最优、奇异点风险、中点需求）— P2 阶段填充
    - `Dashboard7_CommFault`（ECAT、驱动器故障、报警码、T0/T1通道状态）
  - `DashboardSnapshot` 聚合容器，提供 `to_json()` 导出类型 C 快照
  - 线程安全读写锁，Qt 和 Web 共用同一实例
- **依赖**：需控制器轮询数据（来自 `controller_runtime_mixin._poll_feedback_silent()` 或新的分组轮询）
- **验收**：7 个看板对象可独立访问，每次轮询后更新，有 stale 时间戳

---

### T007 实现 50ms 核心分组轮询

- **目标**：在看板缓存层基础上，建立分组轮询策略
- **轮询分组**（按 V2.1 6.3.1 节）：

  | 组 | 地址范围 | 周期 | 说明 |
  |----|---------|------|------|
  | A-核心 | LONG(34/36/38) + IEEE(324) | 50ms | 状态字 |
  | B-核心 | IEEE(1500~1522) DPOS 12轴 | 50ms | 指令位置 |
  | C-核心 | IEEE(1600~1622) MPOS 12轴 | 50ms | 编码器位置 |
  | D-次要 | IEEE(1700~1742) 安全+速度+R/Z | 100ms | 安全参数 |
  | E-次要 | IEEE(200~262) AXISSTATUS+MTYPE | 100ms | 轴状态 |
  | F-低频 | IEEE(50~126) 软限位 | 启动1次 | 限位参数 |
  | G-低频 | IEEE(340~560) 标定数据 | 500ms | 按需 |

- **实现**：在 `controller_runtime_mixin.py` 中新增轮询逻辑，或在 `dashboard.py` 中独立启动后台线程
- **验收**：A+B+C 三组请求在 50ms 周期内完成（3次 × ~10ms ≈ 30ms）

### T009 抽独立 L1 安全预检模块

- **目标**：新建 `robot_modbus_lite/safety_precheck.py`
- **内容**：从 `WebPrecheckService.run_l1()` 中提取通用逻辑，重构为 Qt 和 Web 共用

  | 检查项 | 计算方式 | 数据源 |
  |--------|---------|--------|
  | 系统状态 | estop/alarm/pause/ready | 看板1 |
  | 控制器在线 | 连接状态 | 看板7 |
  | 通道可用 | 目标槽位空闲 | 看板2 |
  | 球面半径 | `r_min < sqrt(x²+y²+z²) < r_max` | 看板3 |
  | Z 高度 | `z_min < z < z_max` | 看板3 |
  | 速度百分比 | `0 < spd_pct ≤ safe_speed_max` | 看板4 |
  | 软限位 | `rs_limit[i] ≤ target[i] ≤ fs_limit[i]` | 看板3 |

- **接口**：`l1_check(target_params: dict, dashboard: DashboardSnapshot) -> PrecheckResult`
- **`PrecheckResult`** 包含：每项 pass/fail、风险描述、建议参数
- **验收**：7 项检查全覆盖，失败项有中文描述

### T010 将预检场景从 UI 文案改为真实检查驱动

- **目标**：预检场景不再固定显示"等待/进行中/等待/等待"，而是由 T009 的 L1 检查逐项驱动
- **修改**：

  - 每个 checklist label 显示对应检查项的实时结果（✅ 通过 / ❌ 失败 / ⏳ 检查中）
  - 进度条绑定 L1 检查的完成数量
- **验收**："J1转到30度" → 预检场景逐项显示软限位 ✅、速度 ✅、R/Z ⏳ 等

---

### T011 安全确认页接入风险项和建议参数

- **目标**：`_operator_accept_suggestion()` 不再是空壳
- **内容**：
  - T009 的 `PrecheckResult` 中失败项 → 确认页 `_operator_confirm_detail_text()` 展示风险项表格
  - 每个风险项附带建议（如 "R 超限 20mm，建议将 X 从 350 调整为 330"）
  - 采纳建议 → 改写 NLP 计划中的目标参数 → 重新触发 L1 检查 → 更新确认页
  - 确认执行 → 锁定计划 → 下发给 `_execute_nlp_plan()`
  - 取消 → 清理待确认计划
- **验收**：预检不通过时确认页显示风险 + 建议，采纳后参数更新并重新显示通过

## P2：运动预演和流程预演

### T012 实现运动学引擎

- **目标**：新建 `robot_modbus_lite/kinematics_engine.py`
- **内容**：
  - 封装 ZMotion PC 函数库 `FRAME_TRANS2` 调用
  - 正解接口：`forward_kinematics(joint_angles: list[float], fstatus: int) → cart_pose`
  - 逆解接口：`inverse_kinematics(cart_pose: list[float], fstatus: int) → joint_angles`
  - 错误处理：控制器不可达时返回 None 而非抛异常
- **复用**：参照 V2.1 文档 3.2 节的 Python 伪代码
- **依赖**：需 ZMotion SDK（已在 `Windows Python（64位）/dll库文件/` 中）
- **验收**：逆解结果与控制器内置 `FRAME_TRANS2` 结果一致

---

### T013 实现运动规划预演模块

- **目标**：新建 `robot_modbus_lite/motion_plan.py`
- **内容**（按 V2.1 文档 6.4.2 节）：
  - `find_best_fstatus()` — 遍历 8 个 FSTATUS，评分（运动代价+奇异惩罚+缠绕惩罚），返回最优
  - `path_check_singularity()` — 起点→目标插值 5 点，每点逆解后检查 J4 是否接近 0
  - 中点绕行策略 — 检测到姿态大变或低位大范围移动时，生成 RY 偏移 5° 的中间点
  - `motion_plan()` 主决策函数 — 组合上述三步，返回规划结果 + 进度播报回调
- **看板填充**：结果写入 T006 的看板6
- **验收**：对典型位姿指令可输出最优 FSTATUS 和奇异点风险等级

---

### T014 实现流程级 L3 预演

- **目标**：新建 `robot_modbus_lite/process_precheck.py`
- **内容**：
  - 对流程每个动作循环调用 T009 L1 + T013 L2
  - 时序适配性检查（状态机模拟：急停后未复位→禁止后续运动）
  - 累积误差评估（每步误差传播叠加）
  - 简化包围盒干涉检查（可选，后期迭代）
  - 进度回调：每步完成后报告"步骤 3/8 预检通过"
- **看板填充**：结果写入 T006 的看板5
- **验收**：8 步流程预检完成，输出每步结果和风险汇总

### T016 定义类型 A/B/C JSON schema

- **目标**：新建 `robot_modbus_lite/json_schema.py`
- **内容**：
