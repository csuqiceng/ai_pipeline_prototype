## 三、状态位模型 — 根本性架构差异 (P0)

### V4.3 模型: LONG(34) 按函数分组

V4.3 使用 LONG(34)（32位长整数），每个函数占 2 位，支持多函数并行状态跟踪：

```
函数执行状态 (每函数 2-bit):
  00 = 空闲 (IDLE)
  01 = 执行中 (EXEC)
  10 = 完成 (DONE)
  11 = 错误 (ERR)

BIT0-1:   Func104   掩码 $00000003
BIT2-3:   Func106   掩码 $0000000C
BIT4-5:   Func107   掩码 $00000030
BIT6-7:   Func108   掩码 $000000C0
BIT8-9:   Func109   掩码 $00000300
BIT10-11: Func110   掩码 $00000C00
BIT12-13: Func111   掩码 $00003000 (预留)
BIT14-15: Func11    掩码 $0000C000
BIT16-17: 预留      掩码 $00030000
BIT18-19: Func120   掩码 $000C0000

全局状态位:
BIT24: M_ALARM  掩码 $01000000  报警标志
BIT25: M_ESTOP  掩码 $02000000  急停标志
BIT26: M_PAUSE  掩码 $04000000  暂停标志
BIT27: M_CANCEL 掩码 $08000000  取消标志
BIT28: M_READY  掩码 $10000000  系统就绪
```

V4.3 明确声明：**LONG(34) 和 IEEE(34) 是不同的存储区，不能混用！**

> V4.3 第六章 6.2/6.3/6.5 进一步从 Modbus 寄存器物理空间层面解释了原因：REG/LONG/IEEE 共用同一 4X 空间但地址映射不同，读取 LONG(34) 必须使用 `ZAux_Modbus_Get4x_Long` 而非 `ZAux_Modbus_Get4x_Float`。

### 当前代码模型: IEEE(34) 单一组状态位

文件: `mock_controller/protocol.py:161-169`

```python
SIX_STATUS_RECEIVED = 1    # Bit0 = 下位机收到
SIX_STATUS_EXECUTING = 2   # Bit1 = 执行中
SIX_STATUS_COMPLETE = 4    # Bit2 = 完成
SIX_STATUS_ERROR = 8       # Bit3 = 错误
SIX_STATUS_ALARM = 64      # Bit6 = 报警
```

文件: `robot_modbus_lite/models.py:392-427` (SixAxisStatus)

```python
is_received = (raw & 1) != 0    # Bit0
is_executing = (raw & 2) != 0   # Bit1
is_complete = (raw & 4) != 0    # Bit2
has_error = (raw & 8) != 0      # Bit3
has_alarm = (raw & 64) != 0     # Bit6
can_send = raw in (0, 4)        # 全局判断
```

### 逐项对比

| 维度 | V4.3 | 代码 | 匹配 |
|------|------|------|------|
| **存储区类型** | LONG(34) 长整数 | IEEE(34) 浮点数 | **不匹配** |
| **Modbus地址映射** | LONG(n) → 400001+n | IEEE(n) → 400001+n×2 | **地址计算不同** |
| **状态粒度** | 每函数独立 2-bit (8组) | 全局单组 bit (1组) | **不匹配** |
| **并发支持** | 多函数可同时有不同状态 | 不支持并行状态 | **不匹配** |
| **空闲判定** | 目标函数掩码 AND = 00 | raw == 0 或 raw == 4 | **逻辑不同** |
| **完成判定** | 目标函数掩码 AND = 10 (DONE) | (raw & 4) != 0 | **逻辑不同** |
| **错误判定** | 目标函数掩码 AND = 11 (ERR) | (raw & 8) != 0 | **逻辑不同** |
| **报警标志** | BIT24 (全局) | Bit6 | **位置不同** |
| **急停标志** | BIT25 | 无独立判断 | **缺失** |
| **暂停标志** | BIT26 | 无 | **缺失** |
| **取消标志** | BIT27 | 无 | **缺失** |
| **就绪标志** | BIT28 | 无 | **缺失** |
| **可发送判定** | 函数位=00 且 BIT24=0 且 BIT25=0 且 BIT28=1 | raw in (0,4) | **条件不完整** |

### 判断示例对比

**检查 Func108 是否完成：**
- V4.3: `(LONG(34) & $C0) == $80`
- 代码: `(raw & 4) != 0` (读 IEEE(34))

**检查是否可发送 Func108：**
- V4.3: `(LONG(34) & $C0) == 0` 且 `(LONG(34) & $01000000) == 0` 且 `(LONG(34) & $02000000) == 0` 且 `(LONG(34) & $10000000) != 0`
- 代码: `raw in (0, 4)`

## 五、Func104 特殊执行逻辑 (P1)

### V4.3 规定

> 急停函数与标准函数的关键区别:
> - 不检查状态标志位 (不管当前是空闲/执行/完成/错误/报警)
> - 不需要等待空闲状态
> - 任何情况下都可以立即执行

### 代码实现

代码在 qt_gui.py:3233-3237 已实现了跳过前置检查逻辑:
```python
skip_precheck = (
    six_cmd.func_num == 104          # Func104急停/慢停: 不需要前置检查
    or six_cmd.func_num == -10       # ALARM_RESET: 报警时can_send为false，必须跳过
    or six_cmd.func_num < 0          # 其他本地命令
)
if not skip_precheck:
    # ... 前置检查 ...
```

**Func104 已正确跳过前置检查。** ✅

但存在以下残余差异:
- Func104 的参数模型不完整 (见第二节)，只写了 IEEE(2)=stop_mode，未实现 IEEE(4)暂停控制、IEEE(6)结束控制、IEEE(8)报警复位
- 系统命令（上电/启动/停机/暂停/继续）走的是 `_handle_system_action_six` 方法，将 code 映射为 `SixAxisCommand` 后发送 Func104，也不做前置检查
- ⚠️ 差异：V4.3 要求 Func104 一次可同时操作多个控制字（如同时急停+报警复位），但代码的 `SixAxisCommand` 只支持单个 `stop_mode` 字段，每次只能做一种操作

## 七、LONG(38) 报警码 — API 类型错误 + 缺少 4 个报警位 (P1)

> 当前代码用 `read_modbus_float(38)` 读 IEEE(38) 获取报警详情，V4.3 要求用 `read_modbus_long(38)` 读 LONG(38)。不仅是字段缺失，更是 SDK API 调用层面的类型错误。详见第十九节冲突 2。

### V4.3 定义 (10 位)

| BIT | 掩码 | 含义 | 代码 SixAxisAlarmDetail |
|-----|------|------|----------------------|
| BIT0 | $1 | 半径超限 | radius ✅ |
| BIT1 | $2 | 高度超限 | height ✅ |
| BIT2 | $4 | 指令忙(重复触发) | **缺失** |
| BIT3 | $8 | 速度超限 | speed ✅ |
| BIT4 | $10 | 加速度超限 | accel ✅ |
| BIT5 | $20 | 减速度超限 | decel ✅ |
| BIT6 | $40 | ECAT通讯故障 | ecat_exceeded ✅ |
| BIT7 | $80 | 驱动器报警 | **缺失** |
| BIT8 | $100 | 函数号非法 | **缺失** |
| BIT9 | $200 | 参数非法 | **缺失** |

缺失的 4 个报警位:
- **BIT2 指令忙**: 重复触发时的常见错误
- **BIT7 驱动器报警**: 伺服驱动器故障，实际运行中重要
- **BIT8 函数号非法**: 发送了未定义的函数号
- **BIT9 参数非法**: 参数超范围，调试阶段高频出现

## 八、MODBUS_BIT 汇总状态 — **V4.3 已移除此特性** ✅

> V4.3 协议删除了整个 3.5 节 MODBUS_BIT 独立状态位（原 BIT 220~290 共 18 个位），以及 4.3 节 BIT 位操作说明。

| 222 | 有函数错误 | 3.5 节 | **已移除** |
| 223 | 急停激活 | 3.5 节 | **已移除** |
| 224 | 暂停激活 | 3.5 节 | **已移除** |
| 225 | 取消激活 | 3.5 节 | **已移除** |
| 226 | 系统就绪 | 3.5 节 | **已移除** |

## 十、并行执行 — 未实现 (P2)

### V4.3 并行规则

```
110(T1延时) 和 120(IO输出) 可与运动函数 (106/107/108) 同时执行
但 110 和 120 之间串行执行 (同一任务)，不能同时运行
```

典型并行场景 (V4.3 原文):
1. 触发 108 运动到目标位置
2. 同时触发 110 延时 0.5 秒
3. 等 110 完成 (DONE)
4. 触发 120 闭合夹爪
5. 等 120 完成 (DONE)
6. 触发下一个运动指令

### 代码现状

- 所有命令串行发送和等待
- GUI 轮询逻辑 (qt_gui.py 200ms 定时器) 仅轮询一个全局状态
- 无并行命令管理器
- V4.3 的 2-bit-per-function 状态模型天然支持并行，但代码的单组状态位模型不支持

> ⚠️ **实现注意**: Func110/Func120 是并行函数（1.3 节），不应套用标准函数的等待完成流程。它们应进入 **program slot**（LONG(34) BIT10-11 / BIT18-19），不占用 motion slot（BIT2-7 / BIT14-15）。实现时需要并行状态机，不能简单串行化。

## 十一、Mock Controller 差异

`mock_controller/controller.py` 的模拟逻辑与 V4.3 存在对应差异:

| 维度 | V4.3 | Mock Controller | 匹配 |
|------|------|----------------|------|
| 状态存储 | LONG(34) 独立长整数区 | IEEE(34) 浮点区 | **不匹配** |
| 状态模型 | 按函数分组 2-bit | 全局单组 bit | **不匹配** |
| Func104 分发 | 无前置状态检查 | **已跳过忙状态检查** (`func_num != FuncSixAxis.STOP`)，但旧线程 `join(timeout=5.0)` 仍有阻塞，非真正即时抢占 | **半匹配** |
| 回显区 | IEEE(280~312) | 未实现回显区 | **缺失** |
| LONG(36) | 系统状态 | 未模拟 | **缺失** |
| Func109/110/120/11 | 有定义 | 未分发 | **缺失** |
| 并行执行 | 支持 | 单线程执行 | **不匹配** |

**Func104 分发细节说明**（controller.py:491-494）:
```python
if func_num != FuncSixAxis.STOP and raw_status in (SIX_STATUS_EXECUTING, SIX_STATUS_RECEIVED):
    return
```
Func104 已正确跳过忙状态检查（`func_num != FuncSixAxis.STOP` 条件为 False 时不触发 return）。但随后的 `_exec_thread_six.join(timeout=5.0)` 会在旧线程存续时阻塞最多 5 秒，这意味 Func104 在下发时仍可能被等待旧线程结束而延迟，做不到协议要求的"1ms 内响应"。

## 十二、IEEE(40~72) 实时回传区 — 存在 V4.3 LONG(40~46) 物理地址冲突 (P0/P1)

### 现状

代码在执行完成后读取了协议 V4.3 中**分层状态不同**的地址段来获取实时回传数据:

| IEEE地址 | 代码读取的参数 | V4.3 第六章分区 | 状态 |
|----------|-------------|----------------|------|
| **IEEE(40~46)** | X/Y/Z/Rx/Ry/Rz 运行时位姿 | **LONG(34~46) 状态反馈区** | 与 LONG(40~46) 物理冲突，必须迁移 |
| IEEE(50~72) | 速度/距离/关节/ECAT/FRAME | IEEE(50~312) 回显与反馈区 | 位于回显区内，但 1~5 章未定义具体语义，需固件确认 |

V4.3 第六章 6.3 明确：
```
LONG(34~46)  → 控制器状态反馈区
IEEE(50~312) → 回显与反馈区
```

**关键区分**：IEEE(40~46) 完全处于 LONG 状态反馈区，与 LONG(40)（Func110 剩余毫秒）、LONG(44)（Y输出状态）、LONG(46)（X输入状态）物理重叠，必须迁移。IEEE(50~72) 处于 IEEE(50~312) 回显与反馈区范围内，地址规划不冲突，但 1~5 章未定义具体语义，需固件确认后补充到协议。

代码位置: `qt_gui.py:3378-3384`, `models.py:SixAxisRealtimeData`

### 对比 V4.3 定义的数据源

V4.3 定义的关节/位姿数据源:
- IEEE(1500~1522) = DPOS(0~11) — 需求位置
- IEEE(1600~1622) = MPOS(0~11) — 实际位置
- IEEE(200~222) = AXISSTATUS(0~11) — 轴状态
- IEEE(240~262) = MTYPE(0~11) — 运动类型

代码同时也在 `service.py:build_six_joint_feedback_read()` 和 `build_six_pose_feedback_read()` 中使用了 IEEE(1500) 和 IEEE(1512) 作为独立的反馈查询通道。

### 影响（按分层分析）

- **IEEE(40~46)**：与 LONG(40~46) 物理地址重叠，属于 P0 冲突，必须迁移至 IEEE(1500+) 或 IEEE(50+)
- **IEEE(50~72)**：地址不冲突，但在协议中语义未定义，需固件确认后补充。目前属于"未确认的自定义回传区"
- 代码中存在两套数据读取通道（IEEE(40~72) 和 IEEE(1500~1522)），统一后可删除 IEEE(40~72) 通道

### ⚠️ 已存在的代码级错位: IEEE(1500/1512) 读取与 mock 写入步进不一致 (P1)

**问题根因**: Mock Controller 的 `read_modbus_float()` 按连续地址读取（`start+i`），但 ZMotion SDK 的 `ZAux_Modbus_Get4x_Float(start, count)` 在 count>1 时按间隔 2 读取（`start + i*2`），因为每个 IEEE float 占 2 个 Modbus 寄存器。mock 未模拟此行为。

**service 读取调用**（实机正确，mock 下错误）:
```python

```

**mock `_sync_six_realtime_locked` 写入**（步进 *2，正确模拟了实机行为）:
```python

for i in range(6):
    self._modbus_ieee[1500 + i * 2] = ...  # 写 IEEE(1500,1502,1504,1506,1508,1510)

```

**mock `read_modbus_float` 实现**（步进 *1，错误）:
```python

return list(self._modbus_ieee[start : start + count])
```

**错位后果**（仅影响 mock 模式）:
- mock 读取 `start=1500, count=6` 得到 `[IEEE(1500), IEEE(1501), IEEE(1502), IEEE(1503), IEEE(1504), IEEE(1505)]`
- 但 mock 写入的是 `[IEEE(1500), IEEE(1502), IEEE(1504), IEEE(1506), IEEE(1508), IEEE(1510)]`

- 同样的错位也发生在 IEEE(1512~1522) 的笛卡尔位姿反馈

**修复方向**: Mock 的 `read_modbus_float()` 在 count>1 时应使用 `start + i*2` 步进而非 `start + i`，与 ZMotion SDK 的寄存器映射行为一致。注意 `write_modbus_float()` 也需要同样修正（当前写单个值不存在此问题，但未来批量写入会遇到）。

## 十三、BIT(151) 报警复位 vs Func104 IEEE(8) 报警复位 — 违反 V4.3 通讯边界 (P1)

> V4.3 6.5 明确声明：**"本项目上位机通讯只使用 IEEE(浮点) 和 LONG(整数) 两种格式，不使用 BIT 和 REG"**。因此 BIT(151) 不仅是协议外自定义地址，而是对 V4.3 通讯边界的直接违反，必须移除。

### V4.3 规定的报警复位方式

通过 Func104 的 IEEE(8)=1 触发:
```
IEEE(0) = 104
IEEE(8) = 1   (报警复位)
IEEE(32) = 1  (触发)
```
复位效果: 清除 BIT24(报警标志) + 所有函数状态位 + 驱动复位

### 代码实现方式

代码使用独立的 **BIT(151)** 进行报警复位:

```python
# qt_gui.py:3249
client.write_modbus_bit(151, [1])   # 置1触发复位
# ... 轮询确认 ...
client.write_modbus_bit(151, [0])   # 清0还原
```

代码位置: `qt_gui.py:3249-3258`, `qt_gui.py:3449-3458`, `mock_controller/controller.py:194-196`

### 差异

| 维度 | V4.3 | 代码 |
|------|------|------|
| 复位方式 | Func104 IEEE(8)=1 + IEEE(32)=1 | BIT(151)=1 |
| 协议一致性 | V4.3 6.5 明确不使用 BIT | **违反通讯边界** |
| 复位范围 | 清除 34.24+所有函数状态位+驱动复位 | 仅清除 IEEE(34) 和 IEEE(38) (mock) |
| V4.3 中的定义 | 明确指定 Func104 IEEE(8)=1 | BIT(151) **不在** V4.3 协议中 |

### 关联: BIT(20000)/BIT(20001) — 残留不可达的协议外 IO 控制代码

代码中**存在**对两个 V4.3 协议中完全不存在的 BIT 地址的直接写入逻辑:

| BIT地址 | 代码用途 | V4.3 定义 |
|---------|---------|----------|
| BIT(20000) | 夹爪控制 (1=闭合) | **不存在** (协议用 Func120，且 V4.3 6.5 不使用 BIT) |
| BIT(20001) | 门控制 (1=开门) | **不存在** (同上) |

代码位置: `qt_gui.py:3264` (`func_num == -1` 分支), `qt_gui.py:3278` (`func_num == -3` 分支)

**⚠️ 重要：此代码在当前主流程中不可达**。`service.py` 的 `build_six_command_from_record()` 只构造 `func_num=104/106/107/108`，`build_six_system_command()` 只构造 `func_num=104/-10/-5`。没有任何路径会构造 `SixAxisCommand(func_num=-1)` 或 `func_num=-2` 或 `func_num=-3`。这是历史残留代码或预留扩展点，**不是当前实际功能路径**。

V4.3 通过 Func120 (`IEEE(2)=io_no, IEEE(4)=action`) 以标准函数方式控制 IO 输出，支持完整的校验和状态反馈机制 (LONG(34)-(34.18,34.19) 状态跟踪, LONG(44)=Y输出状态, LONG(46)=X输入状态)。当下实现 Func120 后应移除此残留代码。

## 十五、query_table 查询表映射机制 (P2)

### 现状

代码使用查询表 (`query_table.json` / `机械臂AI地址表.csv`) 将中文自然语言命令映射为具体的函数号和参数:

```
用户文本 → command_parser → query_key → QueryRecord → SixAxisCommand
```

文件: `service.py:build_six_command_from_record()`

QueryRecord 的 `params` 字段是一个自由 `dict[str, float | int]`，key 名称需要与协议参数名对应:

```python
# service.py:173-226
if func_num == 108:
    return SixAxisCommand(
        target_x=float(params.get("target_x", 0.0)),
        target_y=float(params.get("target_y", 0.0)),
        ...
    )
```

### 潜在问题

- JSON 加载时有参数 key 白名单校验（`query_table.py:108`：只接受 `_default_params_for_func(func_num)` 预定义的 key），不在白名单中的 key 会被**静默丢弃**，不会报错
- 在白名单内但 JSON 中未提供的 key 会落入 `_default_params_for_func()` 的默认值（如 `spd: 300.0`），不会报错
- 拼写错误的 key 会被静默忽略并落回默认值——错误不会被发现，但也不会造成任意参数透传
- 风险本质是**静默默认值**：例如 `spd` 拼成 `sped` → 实际速度变成默认值 300.0，而用户期望的是 JSON 中定义的值，这个差异不会被任何日志或校验捕获

## 十九、V4.3 第六章暴露的物理地址冲突风险 (P0)

V4.3 第六章 6.2/6.3 明确了项目的 IEEE/LONG 地址分区规划，暴露了当前代码中存在多处 IEEE/LONG 地址编号重叠的问题。

### 6.3 规定的分区（本项目仅使用 IEEE 和 LONG）

| 地址范围 | 类型 | 用途 |
|---------|------|------|
| IEEE(0~32) | FLOAT | 上位机参数传入区 |
| LONG(34~46) | LONG | 控制器状态反馈区 |
| IEEE(50~312) | FLOAT | 回显与反馈区 |
| IEEE(400~) | FLOAT | 插补点数据区 |

### 冲突 1: IEEE(36) vs LONG(36) — 物理地址重叠

**代码当前** (`service.py:251`):


**V4.3 定义**:
```text
LONG(36) = 系统状态 (50ms刷新)
```

IEEE(36) 和 LONG(36) 在 ZMotion Modbus 架构中共用同一 4X 物理空间（见 6.2 节），地址编号相同意味着物理冲突。修复方向：
- 系统状态 → 读 LONG(36)，使用 `ZAux_Modbus_Get4x_Long`
- 当前函数号 → 改读 IEEE(322)（V4.3 已在 5.1 节分配：IEEE(322)=当前执行的 func_id）

### 冲突 2: IEEE(38) vs LONG(38) — 物理地址重叠 + API 类型错误

**代码当前** (`service.py:245`):
```python
def build_six_alarm_detail_read(self) -> VrReadRequest:
    return VrReadRequest(start_vr=38, count=1)  # 读 IEEE(38)
```

**V4.3 定义**:
```text
LONG(38) = 报警码 (10个位定义)
```

代码不仅地址编号冲突，更存在 **SDK API 调用层面的类型错误**：V4.3 6.5 明确 LONG 必须用 `ZAux_Modbus_Get4x_Long`，而代码用 `Get4x_Float` 读。修复方向：
- 报警详情 → 读 LONG(38)，使用 `ZAux_Modbus_Get4x_Long`
- 当前 `SixAxisAlarmDetail.from_value()` 接收 float，需改为 int

### 冲突 3: IEEE(40~46) vs LONG(40~46) — 最危险的区域重叠

**代码当前** (`qt_gui.py:3378-3384`): 读取 IEEE(40~50)、IEEE(52)、IEEE(54)、IEEE(56)、IEEE(58~68)、IEEE(70)、IEEE(72) 获取实时位姿/速度/关节角度。

**V4.3 定义**:
```text
LONG(40) = Func110 剩余毫秒
LONG(44) = Y输出状态 (Func120 反馈)
LONG(46) = X输入状态 (Func120 反馈)
```

IEEE(40~46) 与 LONG(40~46) 的物理地址完全重叠。这不是简单的"协议未定义"，而是与 V4.3 已分配的状态反馈区直接冲突。

**分层分析**:

| 地址范围 | 代码用途 | V4.3 状态 | 严重性 | 建议 |
|---------|---------|----------|--------|------|
| **IEEE(40~46)** | 位姿回传 | 与 LONG(40~46) 物理冲突 | **P0** | 删除/迁移至 IEEE(1500+) 或 IEEE(50+) |
| IEEE(50~72) | 速度/距离/关节/ECAT | 在 IEEE(50~312) 回显区内，协议未定义具体语义 | P1 | 需确认固件是否提供，如提供则补充到协议 |
| IEEE(56) | 运动状态 | 同上 | P1 | 同上 |

**修复方向**:
- IEEE(40~46) 必须迁移：位姿数据应从 IEEE(1500~1522) DPOS/MPOS 或 IEEE(50+) 读取
- IEEE(50~72) 需固件确认后补充协议定义
- `SixAxisRealtimeData` 数据源切换到协议定义的地址
