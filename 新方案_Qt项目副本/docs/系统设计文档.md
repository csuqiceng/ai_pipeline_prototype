# 双车床机械手自然语言编程控制系统设计文档

版本：V1.0  
日期：2026-05-08  
项目目录：`新方案_Qt项目副本`

## 1. 项目概述

本项目是一套面向双车床上下料场景的机械手上位机控制系统。系统以 Qt 桌面端作为操作入口，支持模板指令、流程指令、自然语言文本、讯飞语音识别和 DeepSeek 语义解析，并通过 ZMotion 控制器接口向真实控制器或本地模拟控制器发送运动命令。

当前项目的工程形态是“可演示、可联调、可逐步产品化”的 Qt 样机版。代码中同时保留了早期 VR 寄存器协议、标准 VR 命令模型，以及当前重点落地的六轴机械手 Modbus TCP 协议。后续工程应以 Func104/106/107/108 六轴协议为主线，旧 VR 协议作为兼容链路和调试参考保留。

### 1.1 建设目标

- 提供可视化 Qt 控制台，支持连接控制器、执行模板、查看状态、管理模板和流程。
- 将自然语言输入稳定映射到“模板、流程、系统动作”三类受控动作。
- 通过统一服务层将查询表记录转换为控制器可执行的寄存器写入。
- 支持真实 ZMotion 控制器和本地 Mock 控制器的同接口切换。
- 提供运行日志、导出日志、语音识别记录和调试反馈能力。
- 通过 JSON 数据文件维护模板、流程、安全参数和规避点，减少硬编码。

### 1.2 当前边界

当前系统不直接让大模型生成任意寄存器写入，也不做多轮开放式机器人调度。自然语言和语音只负责归类到已有模板、已有流程或系统动作，真正执行仍走 Qt 主链路。

## 3. 总体架构

系统按“界面层、应用服务层、数据模型层、通信适配层、控制器执行层”分层。

```text
用户 / 操作员
    │
    ▼
PySide6 Qt GUI
    │
    ├─ 模板执行
    ├─ 流程执行
    ├─ 自然语言 / 语音输入
    ├─ 模板与流程管理
    └─ 日志与状态显示
    │
    ▼
RobotModbusService
    │
    ├─ 查询表解析
    ├─ 标准命令构建
    ├─ 六轴命令构建
    ├─ 状态解析
    └─ 流程存储
    │
    ▼
ControllerClient 协议接口
    │
    ├─ ZMotionVrClient       真实控制器
    └─ MockZMotionVrClient   本地模拟控制器
    │
    ▼
ZMotion 控制器 / MockController
```

### 3.1 关键设计原则

- GUI 不直接拼接底层协议，命令构建集中在 `RobotModbusService`。
- 真实控制器和模拟控制器实现同一组读写方法，便于联调和回归。
- 模板、流程、安全配置以 JSON 存储，便于现场调整和打包分发。
- 自然语言只输出受控动作，不绕开模板和系统按钮。
- 六轴协议以函数号和参数区为核心，不依赖早期命令字体系。

## 5. 核心数据模型

### 5.1 QueryRecord

`QueryRecord` 是模板表中的基本执行单元，字段包括：

- `query_key`：模板名称，例如 `位置A`、`home`、`慢停`。
- `func_num`：六轴函数号，当前支持 `104/106/107/108`。
- `params`：函数参数字典。
- `keywords`：自然语言匹配关键词。
- `description`：界面说明和日志描述。
- `safety_level`：安全等级，默认 5。

不同函数号的参数含义：

| 函数号 | 类型 | 关键参数 |
| --- | --- | --- |
| 104 | 停止 | `stop_mode` |
| 106 | 关节点动 | `axis_no`、`pos_val`、`spd`、`acc_v`、`dec_v`、模糊参数、`stop_cmd` |
| 107 | 虚拟轴点动 | 同 106，轴号映射到 X/Y/Z/Rx/Ry/Rz |
| 108 | 直线插补/PTP | `target_x/y/z/rx/ry/rz`、`spd`、`acc_v`、`dec_v`、模糊参数、`move_type` |

### 5.2 SixAxisCommand

`SixAxisCommand` 是当前六轴协议的执行模型。它将模板参数转换为一组 Modbus Float 写入：

- `IEEE(0)`：函数号。
- `IEEE(2~30)`：参数区。
- `IEEE(32)`：执行触发。

它通过 `to_func_writes()` 生成参数写入列表，通过 `to_trigger_write()` 生成触发写入。

### 5.3 状态模型

| 模型 | 来源 | 用途 |
| --- | --- | --- |
| `SixAxisStatus` | `IEEE(34)` | 解析收到、执行中、完成、错误、报警 |
| `SixAxisAlarmDetail` | `IEEE(38)` | 解析半径、高度、速度、加减速、ECAT 报警 |
| `SixAxisRealtimeData` | 关节和位姿反馈 | 展示 J1-J6 与 X/Y/Z/Rx/Ry/Rz |
| `StandardProtocolStatus` | 旧 VR 状态区 | 标准 VR 协议兼容 |
| `StandardRealtimeStatus` | 旧 VR 监控区 | 标准 VR 协议兼容 |

### 5.4 ControllerClient

`ControllerClient` 是通信适配接口，真实控制器和 Mock 控制器都需要实现：

- `connect()` / `disconnect()`
- `write_vr()` / `read_vr()`
- `write_modbus_float()` / `read_modbus_float()`
- `write_modbus_bit()` / `read_modbus_bit()`

GUI 只依赖该接口，不关心后端是真机还是模拟器。

## 6. 主要业务流程

### 6.1 模板单次执行

```text
用户点击模板卡片 / 输入模板文本
    │
    ▼
RobotQtWindow._execute_query_key
    │
    ▼
RobotModbusService.resolve
    │
    ▼
QueryRecord
    │
    ▼
安全中间点规划
    │
    ▼
_execute_send_by_protocol
    │
    ├─ 六轴最终协议：_execute_send_six
    └─ 旧 VR/标准协议：兼容路径
    │
    ▼
ControllerClient 写入寄存器
    │
    ▼
读取状态和反馈
    │
    ▼
刷新 UI、写入日志、更新历史
```

### 6.2 六轴协议发送时序

```text
1. 检查控制器连接
2. 读取 IEEE(34) 状态，确认可发送
3. 将 QueryRecord 转为 SixAxisCommand
4. 写 IEEE(0) 函数号
5. 写 IEEE(2~30) 参数
6. 写 IEEE(32)=1 触发执行
7. 轮询 IEEE(34)
8. 若完成，读取实时反馈
9. 若错误或报警，读取 IEEE(38) 报警详情
10. 写日志并更新界面
```

### 6.3 流程执行

流程由 `FlowDefinition` 表示：

- `name`：流程名。
- `steps`：模板 `query_key` 顺序列表。
- `step_delay_ms`：步骤间延时。

执行流程时，GUI 按顺序调用模板执行入口。每一步完成后评估反馈结果，成功则延时后进入下一步；失败则停止流程并记录日志。

### 6.4 自然语言/语音执行

```text
文本输入 / 讯飞语音识别文本
    │
    ▼
VoiceNlpAdapter.parse
    │
    ├─ 本地规则解析
    └─ DeepSeek 可选解析，失败自动回退
    │
    ▼
VoiceNlpPlan
    │
    ├─ template：调用模板执行入口
    ├─ flow：调用流程执行入口
    ├─ system：调用系统动作入口
    └─ unknown：只提示，不执行
```

多动作自然语言通过“然后、接着、再、之后、并且”等分隔词拆成有序动作列表，逐项执行。

## 7. 通信协议设计

### 7.1 当前主协议：六轴 Modbus TCP

当前主链路使用 ZMotion Modbus API：

- Float 寄存器：`ZAux_Modbus_Set4x_Float` / `ZAux_Modbus_Get4x_Float`
- Bit 寄存器：`ZAux_Modbus_Set0x` / `ZAux_Modbus_Get0x`

#### 7.1.1 基础地址

| 地址 | 含义 |
| --- | --- |
| `IEEE(0)` | 函数号 |
| `IEEE(2)` | 参数区起始 |
| `IEEE(30)` | 参数区结束 |
| `IEEE(32)` | 执行触发，写 1 触发 |
| `IEEE(34)` | 函数状态 |
| `IEEE(36)` | 当前函数号 |
| `IEEE(38)` | 报警详情 |
| `IEEE(40~50)` | X/Y/Z/Rx/Ry/Rz 实时位姿 |
| `IEEE(52)` | 当前速度 |
| `IEEE(54)` | 剩余距离 |
| `IEEE(56)` | 运动状态 |
| `IEEE(58~68)` | J1~J6 关节角 |
| `IEEE(1500~1510)` | 实际关节角度反馈 |
| `IEEE(1512~1522)` | 实际笛卡尔位姿反馈 |
| `IEEE(1700~1712)` | 安全限位参数 |

#### 7.1.2 Bit 地址

| 地址 | 含义 |
| --- | --- |
| `BIT(150)` | 急停触发 |
| `BIT(151)` | 报警复位 |
| `BIT(243)` | 总报警 |
| `BIT(253)` | 启动就绪 |

#### 7.1.3 状态位

`IEEE(34)` 使用位组合：

| 值 | 含义 |
| --- | --- |
| `0` | 空闲或可发送 |
| `1` | 已收到 |
| `2` | 执行中 |
| `4` | 完成 |
| `8` | 错误 |
| `64` | 报警 |
| `68` | 完成 + 报警，运动结束但有警告 |
| `72` | 错误 + 报警，严重异常 |

发送前通常只允许 `0` 或 `4` 状态继续发送。`104` 停止命令允许在执行中介入。

#### 7.1.4 函数号

| 函数号 | 名称 | 用途 |
| --- | --- | --- |
| `104` | STOP | 急停/慢停 |
| `106` | JOINT_JOG | 关节点动，J1-J6 |
| `107` | VIRTUAL_JOG | 虚拟轴点动，X/Y/Z/Rx/Ry/Rz |
| `108` | LINE_MOVE | 六维目标位姿直线插补或 PTP |

#### 7.1.5 Func104 参数

| 地址 | 参数 | 说明 |
| --- | --- | --- |
| `IEEE(2)` | `stop_mode` | `0` 急停，`1` 慢停 |

#### 7.1.6 Func106/107 参数

| 地址 | 参数 |
| --- | --- |
| `IEEE(2)` | `axis_no` |
| `IEEE(4)` | `pos_val` |
| `IEEE(6)` | `spd` |
| `IEEE(8)` | `acc_v` |
| `IEEE(10)` | `dec_v` |
| `IEEE(12)` | `fuzzy_pos` |
| `IEEE(14)` | `fuzzy_spd` |
| `IEEE(16)` | `fuzzy_acc` |
| `IEEE(18)` | `fuzzy_dec` |
| `IEEE(20)` | `stop_cmd` |

`Func106` 轴号表示关节轴，`Func107` 轴号表示虚拟轴。Mock 中虚拟轴 `6~11` 映射到 `X/Y/Z/Rx/Ry/Rz`。

#### 7.1.7 Func108 参数

| 地址 | 参数 |
| --- | --- |
| `IEEE(2)` | `target_x` |
| `IEEE(4)` | `target_y` |
| `IEEE(6)` | `target_z` |
| `IEEE(8)` | `target_rx` |
| `IEEE(10)` | `target_ry` |
| `IEEE(12)` | `target_rz` |
| `IEEE(14)` | `spd` |
| `IEEE(16)` | `acc_v` |
| `IEEE(18)` | `dec_v` |
| `IEEE(20)` | `stop_cmd` |
| `IEEE(22)` | `fuzzy_pos` |
| `IEEE(24)` | `fuzzy_spd` |
| `IEEE(26)` | `fuzzy_acc` |
| `IEEE(28)` | `fuzzy_dec` |
| `IEEE(30)` | `move_type`，`0` 直线插补，`1` PTP |

### 7.2 兼容协议：标准 VR 命令模型

项目内仍保留标准 VR 命令模型，主要用于历史兼容、Mock 演示和协议过渡。

| 区间 | 用途 |
| --- | --- |
| `VR[0~15]` | 命令区 |
| `VR[16~25]` | 结果状态区 |
| `VR[500~515]` | 镜像区 |
| `VR[516]` | ACK |
| `VR[517]` | 执行触发 |
| `VR[700~719]` | 实时监控区 |

标准 VR 命令区字段：

| VR | 字段 |
| --- | --- |
| `0` | `CMD_CODE` |
| `1` | `TASK_ID` |
| `2~7` | X/Y/Z/Rx/Ry/Rz |
| `8` | 速度百分比 |
| `9` | 加速度百分比 |
| `10` | 设备/工位 ID |
| `11` | 夹爪 IO |
| `12` | 门 IO |
| `13~14` | 扩展参数 |
| `15` | 安全等级 |

该协议体现“命令字 + 数据区 + 状态区”的产品化方向，但当前真实控制器主联调应以六轴 Modbus 协议为准。

## 9. 安全设计

### 9.1 上位机侧安全

上位机侧当前包含以下安全机制：

- 模板参数校验，只允许 Func104/106/107/108。
- 系统配置中的 X/Y/Z 范围约束。
- 安全中间点策略，必要时在目标动作前插入安全过渡点。
- 执行前读取控制器状态，避免执行中重复下发非停止命令。
- 六轴报警状态解析，错误或报警时记录并提示。
- 自然语言不直接生成寄存器写入。

### 9.2 Mock 侧安全模拟

Mock 控制器支持：

- 运行中拒绝重复命令。
- X/Y/Z 范围校验。
- 速度、加速度、减速度限位。
- 安全半径、高度、速度、加减速报警位组合。
- 急停、暂停、报警复位模拟。

### 9.3 真实现场注意事项

真实控制器联调时，应由下位机最终负责硬限位、伺服状态、急停、门禁、夹爪互锁等强安全逻辑。上位机校验只能作为辅助保护，不应替代控制器和现场电气安全回路。

## 10. 自然语言与语音设计

### 10.1 本地规则解析

本地规则支持：

- 系统动作：上电、启动、停止、暂停、继续、急停。
- 流程动作：执行流程、开始流程、运行流程。
- 模板动作：通过 `query_key`、关键词、别名匹配。
- 多动作拆分：然后、接着、再、之后、并且。

### 10.2 DeepSeek 解析

DeepSeek 只负责分类，不负责生成底层控制参数。允许输出：

- `template`
- `flow`
- `system`
- `unknown`

DeepSeek 调用失败时自动回退到本地规则解析。

### 10.3 讯飞语音

讯飞 IAT 支持：

- 本地麦克风采集。
- 子进程 worker 识别。
- 调试 PCM 保存。
- 识别结果 JSON 落盘。
- 授权代理或本地 Key 模式。

语音识别结果最终作为文本进入 `VoiceNlpAdapter`，不直接执行底层协议。

## 11. 授权与外部服务

授权模块用于支持商业化订阅能力，主要职责：

- 激活和停用授权。
- 本地加密缓存授权状态。
- 获取后端访问 Token。
- 判断 DeepSeek 和讯飞代理功能是否可用。
- 在 UI 中展示授权状态。

外部服务调用模式：

| 服务 | 直接 Key 模式 | 授权代理模式 |
| --- | --- | --- |
| DeepSeek | 读取 `DEEPSEEK_API_KEY` | 通过 LicenseManager 获取 Token 后访问后端代理 |
| 讯飞 IAT | 读取 `IFLYTEK_APP_ID/API_KEY/API_SECRET` | 通过订阅代理识别 |

`.env` 可位于项目根目录或包目录，打包时会被包含到发布目录。

## 13. 真实控制器适配

`ZMotionVrClient` 通过动态加载 SDK 包装文件连接真实控制器：

```text
Windows Python（64位）/
  Windows Python（64位）/
    zmcdll/zauxdllPython.py
    dll库文件/zauxdll.dll
```

连接流程：

```text
1. 动态加载 zauxdllPython.py
2. 临时切换 PATH 和 cwd 到 DLL 目录
3. 创建 ZAUXDLL 设备对象
4. 调用 ZAux_OpenEth(host)
5. 后续通过 SDK 方法读写 VR 或 Modbus
```

所有 SDK 调用由线程锁保护，避免 GUI 定时轮询和发送命令并发访问同一设备句柄。

## 14. Mock 控制器设计

Mock 控制器用于无硬件开发和回归测试。其核心能力：

- 使用 list 模拟 VR、IEEE Float、BIT 寄存器。
- 写入触发地址后启动后台线程模拟执行。
- 根据函数号分发到停止、关节点动、虚拟轴点动、直线插补。
- 更新状态位、当前函数号、实时位姿和报警详情。
- 与真实客户端暴露同样的 `ControllerClient` 方法。

Mock 的价值在于：

- 开发 UI 和服务层时不依赖真实机械手。
- 能复现基本的状态轮询和报警路径。
- 支持流程执行和自然语言执行的闭环验证。

## 15. 日志与可观测性

当前日志主要由 GUI 维护，记录内容包括：

- 连接检测。

## 17. 已知风险与改进建议

### 17.1 当前风险

- `qt_gui.py` 体量过大，界面、业务编排、后台线程、协议调用混在一个类中，后续维护成本高。
- 旧 VR 协议、标准 VR 协议和六轴 Modbus 协议并存，若界面文案不清晰，现场容易选错协议。
- `.env` 被打包存在泄露风险，正式发布应区分开发 Key 和生产授权代理。
- Mock 控制器只能模拟基础行为，不能替代真实控制器的安全回路和运动学约束。
- 查询表参数缺少 schema 版本字段，后续协议升级时迁移不够明确。

### 17.2 建议演进

- 将 `qt_gui.py` 拆分为运行页、管理页、日志页、语音页和执行编排服务。
- 为 `query_table.json`、`flows.json`、`system_config.json` 增加 `version` 字段。
- 将协议选择收敛为“六轴最终协议”默认主路径，旧协议放入高级调试。
- 增加单元测试：查询表加载、命令构建、状态解析、VoiceNlpAdapter、多步骤流程。
- 增加集成测试：Mock 控制器下执行 Func104/106/107/108 并验证状态。
- 将真实控制器联调 checklist 固化到文档和 UI 提示中。
- 将授权代理、DeepSeek、讯飞调用失败的错误码统一成可读诊断信息。

## 18. 结论

当前项目已经具备完整的上位机样机骨架：Qt 操作界面、模板管理、流程执行、自然语言入口、语音识别入口、真实/模拟控制器适配、六轴 Modbus 协议和打包发布链路。

后续开发的主线应是：保留 Mock 闭环用于稳定迭代，以 Func104/106/107/108 六轴 Modbus 协议作为真实现场主协议，逐步弱化旧 VR 协议入口，并把过大的 GUI 类拆分成更清晰的页面和服务模块。
