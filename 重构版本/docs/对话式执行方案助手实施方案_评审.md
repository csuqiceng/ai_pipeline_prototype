# 方案评审：对话式执行方案助手实施方案（代码级对齐）

评审时间：2026-05-26

---

## 一、"当前实现对照"有 3 处不精确，直接影响实施判断

**1. "修改确认循环：已支持整体速度/步长修改"——只对了一半**

实际只有 `operator_ui_mixin.py:1986` 的 `_operator_handle_pending_confirm_modify` 能改速度和步长，且**只对 `_operator_pending_confirm_plan`（原子动作路径）生效，对 `_operator_pending_flow_draft`（流程草案路径）完全无效**。方案没区分这两条路径，实施时会漏覆盖流程草案的编辑。

**2. "反提问：已支持未知 gesture 映射澄清"——机制是脆弱的**

澄清逻辑在 `voice_nlp_adapter.py:613-647`，用两个实例变量 (`_pending_flow_draft_payload` / `_pending_flow_missing_gesture`) 维护状态。但 `VoiceNlpAdapter` 是无状态设计的——每次 `parse()` 调用后如果用户说了无关内容，pending 状态不会被清理也不会超时，可能卡死。方案应补充澄清会话的**超时/失效机制**。

**3. "安全预检：已实现"——但没有短路机制**

`operator_ui_mixin.py:2576-2586` 的 `_operator_prepare_plan_prechecks` **L1 失败后仍继续跑 L2/L3**，三阶段全部同步串行执行。对单步操作这意味着即使 L1 就 fail 了，用户还要等 L2/L3 跑完。阶段 3 的"修改后重新预检"如果不加短路，频繁修改场景下体验会很差。

---

## 二、方案遗漏的架构级问题

**问题 1：两条并行的草案路径没有统一抽象**

代码里存在两条完全独立的状态链路：

| | 原子动作路径 | 流程草案路径 |
|---|---|---|
| 存储位置 | `_operator_pending_confirm_plan` (VoiceNlpPlan) | `_operator_pending_flow_draft` (dict) |
| 数据类型 | dataclass，有 schema | 自由 dict，无 schema |
| 编辑能力 | 可改速度/步长 | 无 |
| 预检支持 | L1/L2/L3 全覆盖 | 不清楚是否覆盖 |
| 确认路径 | `_operator_confirm_execute` | 走 flow save 流程 |

方案四个阶段都在讲统一的"步骤级编辑"，但代码里是**两条分裂的路径**。不先做统一抽象，四个阶段都会变成两套实现。

**建议：** 在阶段 1 前增加"统一草案模型"步骤——定义 `ExecutionPlan` dataclass，让原子动作和流程草案共用同一个编辑/预检/确认管线。

**问题 2：方案没有状态机，但代码里 scene state 管理已经很复杂**

`operator_ui_mixin.py:61` 有 `OperatorSceneState`，加上 `_operator_pending_confirm_plan` / `_operator_pending_flow_draft` / `VoiceNlpAdapter` 内部的 pending 状态，至少有 **3 层状态在 2 个对象上**。方案新增的编辑/追问能力会引入更多中间状态（编辑中、追问中、预检中），但没有定义状态转换规则和互斥条件。

**建议：** 补充草案状态机，至少覆盖：`drafting → clarifying → editing → prechecking → confirmed → executing`，明确哪些状态允许哪些操作。

## 三、四个阶段的实施风险

### 阶段 1：草案步骤级编辑

- `voice_nlp_adapter.py` **完全没有"修改第N步"的解析能力**——grep `修改|modify|edit|第.*步` 零命中。edit 指令的解析是全新功能，不是增量修改。方案应明确这一点。
- `operator_ui_mixin.py` 已有 4673 行 + 150 方法，是目前系统最重的单文件。步骤级编辑的 UI 交互 + NLP 解析 + 状态管理全加进去，维护成本会失控。建议拆出 `draft_editor.py`，和上面说的统一草案模型一起做。

### 阶段 2：通用参数追问

- 方案列了追问场景，但没给**决策矩阵**：哪些参数缺失必须追问阻塞？哪些可以默认+告知？这是追问逻辑的核心设计，不能留到编码时决定。
- `voice_nlp_adapter.py:704-720` 的 DeepSeek prompt 完全没有提到追问能力——只说"未知动作保留 gesture 文本"。要让 DeepSeek 支持追问，需要改 prompt schema 和返回结构，方案应明确是走 DeepSeek 追问还是走本地参数校验追问（建议后者，更可控）。

### 阶段 3：修改后重新预检

- 当前预检是同步串行的（L1→L2→L3 无短路），全量跑完的耗时方案没有评估。
- `_operator_prepare_plan_prechecks` 每次修改都全量重跑，用户快速连续修改时会串行堆积。需要 debounce 或增量预检策略。

### 阶段 4：结构化方案展示

- 方案没说用什么 UI 技术。当前是纯 Qt Widget（`operator_ui_mixin.py:396-424`），步骤卡片在 Qt Widget 里做比 HTML 复杂很多。如果要做可交互的步骤卡片（点击编辑、拖拽排序），Qt Widget 的实现成本远高于 QML/Web 嵌入。这个技术选型需要提前决定。

---

## 四、方案完全缺失的内容

1. **错误路径：** DeepSeek 超时/失败降级、预检不可恢复错误的方案处置、编辑中机器人状态变化（突然报警）的处置——全部未提及。
2. **测试策略：** 零测试规划。新功能（步骤编辑、参数追问、重预检）的测试怎么覆盖？
3. **接口变更：** `VoiceNlpAdapter.parse()` 的返回类型需要扩展吗？新增什么 action type？方案没说。
4. **上下文引用（"把上次那个流程再做一遍"）：** 列为目标能力但无实施阶段对应，属于范围蔓延风险。

---

## 五、结论

| 维度 | 评价 |
|---|---|
| 目标流程设计 | 清晰完整 |
| 现状分析 | 有 3 处不精确，最关键的是没有区分原子动作/流程草案两条并行路径 |
| 优先级排序 | 合理 |
| 实施可操作性 | **不够**——缺少统一草案模型、状态机、参数决策矩阵、接口定义 |
| 最大风险 | 在两条分裂路径上做两套编辑/预检/确认，代码膨胀且维护困难 |

**核心建议（优先级从高到低）：**

1. **先做统一草案模型**（`ExecutionPlan` dataclass），合并原子动作和流程草案两条路径
2. **补充草案状态机**，明确 editing/clarifying/prechecking 状态转换
3. **补充参数缺失决策矩阵**，哪些必问、哪些可默认
4. **评估预检性能**，确定是否需要短路或 debounce
5. **确定步骤卡片的 UI 技术选型**
