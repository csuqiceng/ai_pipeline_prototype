# 智能协同机械手操作方案

本文记录“机械手状态感知 + 多轮人机对话 + 计划草案 + 人工确认 + 执行闭环”的方案。目标是在不破坏现有 V5.0 六轴执行链路的前提下，增加一个可审计、可迭代的智能协同层。

## 1. 目标

当前系统已经支持语音/文本输入、自然语言解析、流程执行、V5.0 三道门发送、状态轮询和日志记录。下一步不是让用户一句话直接驱动机械手，而是建立一个安全的人机协同流程：

```text
用户输入
  -> 智能体读取机械手当前状态
  -> 智能体理解目标并生成计划草案
  -> 智能体向操作人解释当前状态和建议动作
  -> 操作人多轮修改或确认
  -> 执行前重新读取状态并复核安全条件
  -> 操作人最终许可
  -> 系统执行
  -> 全过程结构化记录，用于后续迭代
```

早期阶段必须保留人工确认，运动、IO 输出、报警复位等会改变设备状态的动作不得自动执行。

## 2. 核心原则

1. 查询状态可以直接回答。
2. 生成计划可以自动完成。
3. 运动动作、IO 输出、复位、流程启动必须人工确认。
4. 执行前必须重新读取机械手状态，避免对话期间状态变化导致误执行。
5. 急停、报警、暂停等安全状态下，智能体只能说明状态和建议处理，不能绕过安全链路。
6. 所有用户输入、状态快照、计划版本、人工确认、执行结果都要写入结构化日志。
7. 现有 V5.0 三道门、回显比对、IEEE(312) 接受确认、第三道门复查仍是最终下发的硬安全边界。

## 3. 多轮对话形态

示例：

```text
用户：把机械手移动到位置A，再去位置B。

智能体：
当前状态：无报警，无急停，T0/T1 空闲，当前位置为 ...
我理解你的目标是：先到位置A，再到位置B。
建议计划：
1. 移动到位置A
2. 等待动作完成
3. 移动到位置B
是否确认执行，或需要修改速度/中间点/等待时间？

用户：速度慢一点。

智能体：
已把两步速度调整为 40%。
更新后计划：
1. 以 40% 速度移动到位置A
2. 等待动作完成
3. 以 40% 速度移动到位置B
是否确认执行？

用户：中间等2秒。

智能体：
已加入延时步骤。
最终计划草案：
1. 以 40% 速度移动到位置A
2. 等待 2 秒
3. 以 40% 速度移动到位置B
请确认是否执行。

用户：确认执行。

智能体：
执行前重新读取状态：无报警，无急停，通道空闲。
开始执行第 1 步：移动到位置A。
```

## 4. 会话状态

每次智能体协同操作应维护一个会话对象：

```text
agent_session_id
created_at
updated_at
state
user_goal_original
conversation_turns
latest_robot_state_snapshot
plan_draft
plan_version
pending_confirmation
confirmed_by_operator
confirmation_text
execution_started_at
execution_finished_at
execution_result
failure_reason
operator_feedback
safety_checks_passed
safety_check_result
robot_state_at_plan
robot_state_at_confirm
robot_state_diff
```

说明：

1. `state` 是会话状态机当前状态，例如 `IDLE`、`WAITING_CONFIRM`、`EXECUTING`。
2. 多轮修改计划时不原地修改旧计划，而是创建新的计划对象并递增 `plan_version`。
3. `robot_state_at_plan` 和 `robot_state_at_confirm` 必须分开保存，用于判断确认时状态是否已经变化。
4. `safety_checks_passed` 和 `safety_check_result` 记录执行前复核结果，便于审计。

## 5. 状态机

建议状态机：

```text
IDLE
  空闲，等待新目标或状态查询。

COLLECTING_CONTEXT
  正在读取机械手状态和上下文。

DRAFT_READY
  已生成计划草案，可继续修改。

WAITING_CONFIRM
  等待操作人确认、取消或继续修改。

EXECUTING
  正在执行已确认计划，只允许查询状态、停止、暂停等安全动作。

COMPLETED
  执行完成。

FAILED
  执行失败，可生成恢复建议。

CANCELLED
  操作人取消。
```

用户每一轮输入都根据当前状态处理：

| 当前状态 | 用户输入 | 处理 |
|---|---|---|
| `IDLE` | 新操作目标 | 采集状态并生成计划草案 |
| `IDLE` | 查询状态 | 读取状态并直接回答 |
| `WAITING_CONFIRM` | 确认执行 | 执行前复核状态，安全则执行 |
| `WAITING_CONFIRM` | 修改计划 | 更新计划版本并重新展示摘要 |
| `WAITING_CONFIRM` | 取消 | 会话转为 `CANCELLED` |
| `WAITING_CONFIRM` | 超时无操作 | 会话自动转为 `CANCELLED`，建议默认 5 分钟 |
| `EXECUTING` | 查询状态 | 返回当前执行进度和机械手状态 |
| `EXECUTING` | 停止/暂停 | 走现有安全停止/暂停动作 |
| `EXECUTING` | 执行完成 | 会话转为 `COMPLETED` |
| `EXECUTING` | 执行失败 | 会话转为 `FAILED` |
| `FAILED` | 询问原因 | 汇总错误日志和最终状态快照 |

与现有状态的关系：

1. `AgentSession.state` 应作为上层协同状态机。
2. 现有 `nlp_parse_running`、`nlp_sequence_running` 和 `flow_running` 继续作为底层运行状态，不再另起一套并行执行逻辑。
3. 阶段一建议让智能体确认层包裹现有 `_parse_nlp_text()`、`_execute_nlp_plan()`、`_execute_query_key()` 和 `_start_flow()`，不要重写执行链路。

建议新增 `RobotStateSnapshot`，包含：


这些字段来自现有轮询、V5.0 反馈读取和日志上下文。状态快照要同时用于智能体解释、执行前安全检查和审计日志。

采集时机：

1. 生成计划时实时读取一次状态，作为 `robot_state_at_plan`。
2. 多轮对话期间可以复用最近一次轮询缓存，用于展示状态变化提示。
3. 操作人确认执行后，必须再实时读取一次状态，作为 `robot_state_at_confirm`。
4. 如果确认时状态与生成计划时存在安全相关差异，必须重新展示摘要并要求再次确认。
5. 低风险数值漂移可以配置容忍度，例如坐标差异小于 1mm 且无报警、无急停、无暂停、通道状态不变时可仅写警告；否则重新确认或拒绝执行。

## 7. 计划草案

建议定义 `AgentPlanDraft`：

```text
plan_id
version
summary
risk_level
requires_confirmation
steps
created_from_user_input
state_snapshot_id
warnings
blocked_reason
```

每个 step：

```text
step_id
type
query_key
func_num
display_name
params
estimated_effect
requires_confirmation
safety_notes
parse_confidence
source
```

早期可只支持现有模板和流程：

1. 执行某个已有模板。
2. 执行某个已有流程。
3. 根据用户修改速度、延时、中间点后创建临时流程草案。
4. 查询状态。
5. 停止、暂停、取消、报警复位等系统动作，但必须人工确认。

### 与现有模型的关系

阶段一建议把 `AgentPlanDraft` 作为 `VoiceNlpPlan` 的包装层，而不是立即替代现有模型：

```text
AgentPlanDraft
  -> source_plan: VoiceNlpPlan
  -> steps: AgentPlanStep[]
  -> safety metadata
  -> confirmation metadata
```

原因：

1. 当前 `VoiceNlpAdapter.parse()` 已经能复用本地规则和 DeepSeek 白名单校验。
2. 当前 `_execute_nlp_plan()`、`_execute_query_key()`、`_start_flow()` 已经能执行 `VoiceNlpAction`。
3. 包装层可以先增加版本号、风险等级、确认状态和安全说明，降低改造风险。

阶段二如需支持“速度慢一点”“加等待2秒”“删除第二步”等修改，应新增 `PlanModification`，每次修改生成新的 `AgentPlanDraft`：

```text
PlanModification
  type: set_speed | insert_delay | delete_step | replace_target | add_safe_point
  target_step_id
  params
  reason
```

参数修改不得直接改原始模板文件，优先生成内存中的临时计划步骤；只有操作人明确保存时，才写入模板或流程配置。

## 8. 解析置信度与模型回退策略

本地规则解析很快、可控，但不能保证覆盖所有自然语言。DeepSeek 理解能力更强，但存在网络延迟、额度不可用和模型误判。智能协同层必须同时使用置信度、白名单和人工确认。

### 8.1 解析顺序

推荐顺序：

```text
本地规则解析
  -> 高置信度：生成计划草案，等待人工确认
  -> 中置信度：生成计划草案，提示“请确认理解是否正确”
  -> 低置信度或未命中：调用 DeepSeek
  -> DeepSeek 输出必须经过本地白名单校验
  -> DeepSeek 不可用或仍不确定：要求用户补充，不生成可执行计划
```

当前代码是勾选在线 AI 时先尝试 DeepSeek，再回退本地规则。阶段一智能体实现时建议改为“本地高置信度优先”，减少简单指令的延迟。

### 8.2 置信度分级

高置信度：

1. 用户文本完全等于模板名。
2. 用户文本完全等于流程名。
3. 命中明确别名，例如“移动到位置A”“去位置B”“抓取”“放下”。
4. 命中明确系统动作，例如“报警复位”“暂停”“继续”“急停”。

中置信度：

1. 文本包含唯一模板名。
2. 多动作拆分后每段都能唯一命中。
3. 语音识别文本有冗余词，但目标仍唯一明确。

低置信度：

1. 多个模板或流程都可能匹配。
2. 用户使用“那个位置”“和刚才一样”“慢一点”“差不多”等依赖上下文的表达。
3. 用户要求修改计划，但没有明确修改对象。
4. 本地规则未命中。
5. 语音识别结果为空、只有标点、或包含明显识别错误。

### 8.3 DeepSeek 使用边界

DeepSeek 只能做理解辅助，不能直接生成任意机械手动作。其输出必须满足：

1. `actionType` 只能是 `template`、`flow`、`system`、`unknown`。
2. `target` 必须存在于当前模板、流程或系统动作白名单。
3. 多动作计划中的每一步都必须通过白名单校验。
4. DeepSeek 不能绕过安全规则，不能直接确认执行。
5. DeepSeek 不可用、超时、402、返回 JSON 不合法或白名单校验失败时，必须写日志并回退本地规则或要求用户补充。

### 8.4 不确定时的处理

不确定时不得生成可执行计划，应追问：

```text
我没有唯一确定你的目标。你是要执行“位置A”模板，还是执行“流程A”？
```

或：

```text
你说“速度慢一点”，请确认要修改当前计划的全部移动步骤，还是只修改第 2 步？
```

## 9. 安全规则

强制规则：

1. `alarm=true` 或 `estop=true`：禁止普通运动计划执行，只允许解释状态、建议人工处理、生成复位建议。
2. `paused=true`：禁止直接下发普通运动，提示解除暂停后重新确认。
3. T0/T1 忙：计划可以生成，但执行前必须等待空闲或提示当前忙。
4. 目标点超出安全限位：计划标记为 blocked，不允许确认执行。
5. IO 输出、报警复位、停止动作必须在摘要里明确写出影响。
6. 执行前重新读取状态；如果状态和生成计划时不一致，必须重新让操作人确认。
7. 阶段一优先使用 GUI “确认执行”按钮作为最终确认；文本确认只作为辅助展示，不作为唯一确认来源。
8. 用户只说“嗯”“可以吧”等模糊表达时，不视为确认；确认词必须明确，例如“确认执行”“执行这个计划”“可以执行”。
9. 目标点超限检查应同时使用现有 `axis_ranges` 坐标范围和控制器安全限位；现有模板校验已有 Func108 X/Y/Z 范围检查，但智能体还应在计划层提前标记 blocked。

## 11. 建议新增模块

```text
robot_modbus_lite/
  agent_state_snapshot.py
    采集当前机械手状态，生成 RobotStateSnapshot。

  agent_models.py
    定义 AgentSession、AgentPlanDraft、AgentPlanStep、AgentTurn。

  agent_planner.py
    将用户输入、当前状态、已有模板/流程转换为计划草案。

  agent_safety.py
    集中执行安全判定。输入计划草案、生成时快照、确认时快照，输出 allowed、reason、warnings。

  agent_session.py
    管理多轮会话、状态机、确认词、取消词和计划修改。

  agent_audit_log.py
    持久化对话、状态快照、计划和执行结果。

  agent_mixin.py
    接入 GUI：处理用户输入、展示智能体回复、确认执行、取消执行。
```

桥接关系：

1. `agent_planner.py` 调用 `VoiceNlpAdapter.parse()` 得到 `VoiceNlpPlan`。
2. `agent_planner.py` 将 `VoiceNlpPlan` 转换成 `AgentPlanDraft`。
3. `agent_safety.py` 对 `AgentPlanDraft` 做状态和安全判定。
4. `agent_mixin.py` 在操作人确认后，把 `AgentPlanDraft.source_plan` 交给现有执行方法。

```text

当前机械手状态摘要

智能体回复

计划草案
1. ...
2. ...

```

早期可以复用现有自然语言输入框和日志表，只增加：

1. 智能体回复文本框。
2. 待确认计划摘要。
3. 确认执行按钮。
4. 取消计划按钮。
5. 当前模式指示，例如“安全确认模式”。

阶段一建议使用按钮确认，不使用纯文本确认作为最终执行许可。这样能避免“可以”“可以吧”“嗯”等模糊表达造成误判。

## 13. 分阶段实施计划

### 阶段一：确认型智能体

目标：先做到安全可用。

任务：

1. 新增状态快照采集。
2. 新增 AgentSession 状态机。
3. 用户输入先生成计划草案，不直接执行。
4. GUI 展示状态摘要和计划摘要。
5. 操作人点击确认后执行。
6. 执行前重新读取状态并复核。
7. 写入结构化智能体日志。
8. 5 分钟无操作自动取消待确认会话。

验收：

1. 查询状态能直接回答。
2. 移动类指令只生成计划，不自动执行。
3. 用户确认后才执行。
4. 报警/急停/暂停状态下不能执行普通运动。
5. 日志能还原用户输入、计划、确认、执行结果。
6. DeepSeek 不可用时有明确日志，且不会阻塞高置信度本地规则计划。

### 阶段二：修改型多轮对话

目标：支持用户对计划进行多轮修改。

任务：

1. 支持“速度慢一点”“加等待2秒”“删除第二步”“改到位置C”等修改。
2. 每次修改生成新 plan_version。
3. 修改后重新展示完整计划。
4. 模糊确认不执行，必须明确确认。
5. 每个会话默认最多保留 3 个待确认计划版本；超过后要求用户重新描述目标。

### 阶段三：建议型智能体

目标：开始给出安全和效率建议。

任务：

1. 根据安全限位和避障中间点建议路径。
2. 根据历史失败日志提示风险。
3. 根据当前状态建议先复位、等待、暂停解除或人工处理。
4. 支持从已有流程中推荐最接近的流程。
5. 所有建议仍必须进入计划草案和人工确认，不得自动执行。

### 阶段四：数据迭代

目标：沉淀可分析的数据。

任务：

1. 导出智能体会话数据集。
2. 标记成功/失败/人工修改原因。
3. 总结高频话术和高频流程。
4. 用数据优化解析规则和流程推荐。
5. 导出前脱敏敏感配置、API Key、授权信息和必要的现场坐标。

## 14. 初始落地建议

第一版不要追求大模型完全自动规划。建议用“规则 + 模板 + 安全确认”：

1. 只允许智能体从现有模板和现有流程中选择或组合。
2. 对不明确的目标，要求用户补充。
3. 对运动和 IO 必须人工确认。
4. 对危险状态只给建议，不执行。
5. 所有执行仍调用现有 V5.0 发送链路。

这样可以最快形成闭环，同时不降低现有系统的安全性。

## 15. 阶段一编码决策

本节记录进入阶段一实现前的具体决策，避免编码时出现两套路径或安全语义不一致。

### 15.1 待确认期间状态刷新

1. 进入 `WAITING_CONFIRM` 后，继续使用实时轮询缓存展示状态。
2. 等待确认期间每 30 秒做一次状态刷新检查。
3. 如果检测到报警、急停、暂停、通道忙闲变化、当前函数号变化、流程运行状态变化，应立即提示操作人，并暂停确认流程。
4. 如果只是低风险坐标漂移，例如坐标差异小于 1mm 且安全状态不变，可以写警告日志，不强制取消计划。
5. “暂停确认流程”不切换到新状态，会话保持 `WAITING_CONFIRM`，但设置 `pending_confirmation=False`，确认按钮置灰，智能体回复框显示“检测到状态变化，请重新评估后再确认”，并重新执行 `agent_safety.py` 判定。

### 15.2 AgentPlanStep 映射

`AgentPlanStep` 从 `VoiceNlpAction` 转换时由 `agent_planner.py` 完成查表映射：

1. `template`：通过 `table[target]` 获取 `QueryRecord`，并写入 `query_key`、`func_num`、`params`。
2. `flow`：没有单一 `func_num`，`func_num` 置空，步骤类型为 `flow`，执行时交给现有流程执行入口。
3. `system`：通过系统动作映射得到对应动作说明；如果能映射到本地 `QueryRecord` 或 V5.0 Func104 参数，应写入 `func_num=104` 和影响说明。系统动作执行时不走普通 `_execute_query_key()`，而是沿用现有 `_handle_system_action()` / `_execute_system_send()` 路径。
4. `unknown`：不得生成可确认执行的步骤。

### 15.3 PlanModification 执行边界

阶段二的计划修改由 `agent_planner.py` 接收 `PlanModification` 并生成新版本计划：

1. `set_speed`：clone 对应 `QueryRecord`，只修改内存中的 `spd_pct` 参数，不写回模板文件。`QueryRecord` 是 `frozen dataclass`，必须创建新实例，例如用原对象字段和新的 `params` 合成新 `QueryRecord`，不能原地改 `record.params` 后复用。
2. `insert_delay`：插入临时 Func110 延时步骤，参数为 `delay_sec`。
3. `delete_step`：删除指定步骤；如果删除后步骤数为 0，会话回到 `DRAFT_READY`，不允许确认执行，并要求用户重新输入目标。
4. `replace_target`：用新的模板或流程替换指定步骤。
5. `add_safe_point`：插入已配置的安全中间点步骤，不允许生成不存在的中间点。

### 15.4 智能体路径与现有 NLP 路径

阶段一不改变现有非智能体路径的行为：

1. 现有 `解析文本` / `执行解析` 路径继续使用 `VoiceNlpAdapter.parse()` 的当前策略，保持向后兼容。
2. 智能体路径由 `agent_planner.py` 额外实现“本地高置信度优先”的策略。
3. 两条路径可以共用 `VoiceNlpAdapter` 的规则解析、DeepSeek 调用和白名单校验，但策略由调用方参数化控制。
4. DeepSeek 白名单校验优先复用现有 `VoiceNlpAdapter._validate_deepseek_action()` 逻辑，不重复实现一套不一致的校验。
5. 阶段一建议在 `VoiceNlpAdapter` 增加 `parse_with_strategy(text, strategy)`，避免 `agent_planner.py` 直接调用私有方法；旧 `parse()` 行为保持不变。

### 15.5 置信度计算函数

阶段一实现时增加可编程置信度判定：

```python
def compute_confidence(plan, raw_text) -> tuple[str, str]:
    """返回 ("high" | "medium" | "low", reason)。"""
```

初始规则：

1. 完全等于模板名、流程名或明确别名：`high`。
2. 多动作拆分后每段唯一命中：`medium`。
3. 命中多个候选、依赖上下文、未命中或返回 `unknown`：`low`。
4. DeepSeek 来源的计划即使通过白名单校验，置信度最高也只能是 `medium`，必须提示“请确认理解是否正确”。

`low` 不允许直接进入可执行确认，应调用 DeepSeek 或追问用户。

### 15.6 限位检查

当前现有路径已经在 `_validate_record()` 中对 Func108 的 X/Y/Z 做 `axis_ranges` 范围检查，并且手动发送和流程执行都会调用该校验。

智能体仍需在 `agent_safety.py` 中提前做计划层检查：

1. 使用 `axis_ranges` 检查目标 X/Y/Z。
2. 使用控制器安全限位快照检查半径、高度、速度、加速度等约束。
3. 超限计划标记为 `blocked`，不允许点击确认执行。

### 15.7 安全确认模式下旧按钮行为

阶段一采用兼容策略：

1. 保留现有 `解析文本` 和 `执行解析` 按钮。
2. 当“安全确认模式”启用时，点击旧的 `执行解析` 必须弹窗提示：建议走智能体确认流程。
3. 操作人仍明确选择继续时，才允许走旧路径；该行为必须写日志。
4. 后续稳定后可改为禁用旧直接执行入口。

### 15.8 AgentSession 线程安全

`AgentSession` 状态变更必须统一在 GUI 主线程执行：

1. 后台线程只负责语音识别、DeepSeek 请求、状态读取等耗时任务。
2. 后台线程完成后通过 Qt 信号或现有 `_run_on_main_thread()` 回到主线程。
3. `AgentSession.state`、`plan_draft`、`plan_version`、`pending_confirmation` 等字段只在主线程修改。
4. 如果后续需要多线程读写，必须增加显式锁或不可变快照。

### 15.9 并发会话处理

阶段一不允许多个智能协同会话并发执行：

1. 当前会话处于 `COLLECTING_CONTEXT`、`DRAFT_READY`、`WAITING_CONFIRM` 或 `EXECUTING` 时，新的用户输入不创建第二个会话。
2. 新输入可暂存为 `pending_inputs` 列表，并提示用户当前已有待确认或执行中的计划。
3. 阶段一为避免堆积，只保留最新一条 pending 输入；新的 pending 输入会覆盖旧 pending 输入并写日志。
4. 当前会话完成、失败或取消后，用户可选择继续处理最新的 `pending_inputs[-1]`。

### 15.10 语音识别后的进入方式

阶段一不建议语音识别结果自动进入计划生成：

1. 语音识别完成后先写入自然语言输入框。
2. 智能体区域显示识别文本，提示操作人确认文本是否正确。
3. 操作人点击“生成计划”后才进入状态采集和计划草案生成。
4. 这样可以避免语音识别错误直接进入计划流程。
