## 一、评审概要

经逐项核实，当前实现与两份设计文档的核心差距如下。

当前项目已经实现 V4.3 协议的核心发送链路和主要状态解析，包括 IEEE 参数写入、回显等待、LONG(34) 状态解析、LONG(38) 报警解析、Func104 特例处理、mock 控制器中的 motion/program/system slot 互斥与并行行为。

严格按三份设计文档验收，当前实现已补齐回显失败参数重写、LONG(38).02 指令忙有限自动恢复、Func110 执行中覆盖更新时间，以及“先前置检查再写参数”的发送顺序。当前剩余事项主要是 Func111 预留状态位的文档一致性、mock stop 缓冲覆盖语义的逼真度，以及真机联调验证。

## 二、逐项核实结论

### 1. Func111 预留状态位

结论: 当前代码不实现 Func111；按 V4.3 主协议“预留”口径可接受，但文档必须统一标注为预留。

`上位机函数状态标志位使用指南.txt` 中定义了 `Func111` 的状态位:

| 函数 | 位号 | MASK | EXEC | DONE | ERR |
|---|---|---:|---:|---:|---:|
| Func111 | 34.12,13 | 0x00003000 | 0x1000 | 0x2000 | 0x3000 |

当前 `robot_modbus_lite/models.py` 的 `SixAxisStatus.FUNC_STATE_FIELDS` 未包含 `111`。`FUNC_NAME_MAP`、`service.py`、`mock_controller/controller.py` 中也没有 Func111 的完整命令构建和执行逻辑。

V4.3 主协议说明书已将 Func111 标为“预留”。统一后的口径是：已实现 104/106/107/108/109/110/11/120；Func111 为协议预留，当前 Qt 上位机不实现。

### 2. 回显容错参数重写

结论: 已实施。

文档要求的回显容错流程是:

1. 回显不匹配，等待 5ms 后重读。
2. 最多重读 3 次。
3. 3 次仍不匹配，重新写参数。
4. 重新写参数最多 2 轮。
5. 仍失败则判定通讯异常。

当前实现已改为配置驱动的回显容错：默认 5ms 重读 3 次，失败后重新写参数，最多 2 轮；浮点容差默认 0.001。

代码位置:

- `robot_modbus_lite/qt_gui.py` `_six_echo_settings()`
- `robot_modbus_lite/qt_gui.py` `_wait_six_command_echo_ready()`
- `robot_modbus_lite/qt_gui.py` `_write_six_command()`
- `robot_modbus_lite/system_config.py` `AxisRangeConfig`
- `data/system_config.json` 回显参数默认值

### 3. 前置检查顺序

结论: 已统一为“先前置检查，再写参数和回显”。

统一后的运动函数发送流程为:

1. 读 LONG(34)，检查目标函数状态、报警、急停、就绪。
2. 写 IEEE(0) 和参数。
3. 读回显校验。
4. 写 IEEE(32)=1 触发。
5. 等待 DONE/ERR。

当前 `qt_gui.py` 的实际顺序是:

1. `_write_six_command()` 先调用 `_precheck_six_command()`。
2. 前置检查通过后写 IEEE(0~30) 参数。
3. `_wait_six_command_echo_ready()` 等待 IEEE(280~312) 回显。
4. 回显匹配后写 IEEE(32)=1。

当前实现和统一后的文档一致。前置条件失败时不会写 IEEE(0~30)，也不会触发 IEEE(32)。

代码位置:

- `robot_modbus_lite/qt_gui.py` `_precheck_six_command()`
- `robot_modbus_lite/qt_gui.py` `_write_six_command()`

### 4. mock 缓冲区是行为模拟，不是真实队列模型

结论: 属实。

mock 控制器没有显式实现 stop/parallel/motion 三个缓冲队列对象，也没有真实的“1 深等待队列”。当前通过以下机制模拟可观测行为:

- `_six_slot_busy_locked()` 判断同 slot 是否已有线程或 EXEC 状态。
- `_dispatch_six_command()` 在同 slot busy 时将新函数置为 ERR。
- 同时写入 LONG(38) bit2 指令忙报警。
- Func104 不受 slot 限制。

因此更准确的描述是: mock 在行为上部分模拟了 1 深互斥和拒绝语义，但并非真实缓冲队列实现。

代码位置:

- `mock_controller/controller.py:559` `_six_slot_busy_locked()`
- `mock_controller/controller.py:661` `_dispatch_six_command()`
- `mock_controller/controller.py:671` 同 slot busy 时写 ERR/指令忙

### 5. Func110 执行中更新时间

结论: 已实施。

`指令缓冲机制与回显容错说明.txt` 明确写到:

> Func110 执行中可以更新延时时间（覆盖式更新）

- mock 侧 `_dispatch_six_command()` 在同 slot busy 时对非 Func104 函数执行 `_fail_six_func_locked(..., 1 << 2)`。

当前 mock/GUI 已支持 Func110 执行期间覆盖更新延时时间。Func110->Func120 仍按同 slot busy 拒绝。

### 6. 指令忙和 ERR 自动恢复

结论: LONG(38).02 指令忙已实现有限自动恢复；其他 ERR 仍按报警类型提示人工或上层策略处理。

文档要求发生 ERR 或 LONG(38).02 指令忙时:

1. 读取 LONG(38) 判断报警原因。
2. 对指令忙等待当前函数完成。
3. 必要时发送 Func104 reset_ctrl=1 清除报警。
4. 等待 34.28=1 且 34.24=0。
5. 重新发送被拒绝或出错的命令。

当前 `_wait_six_command_done()` 能读取 LONG(38) 并抛出结构化异常；`_execute_send_six()` 仅对 LONG(38).02 指令忙执行有限自动恢复。自动恢复最多 2 次，等待 slot 空闲 5s，Func104 reset 后等待就绪 5s。

说明：若本地 `_precheck_six_command()` 已判断同 slot 忙并拒绝发送，则不会产生控制器 LONG(38).02，自动恢复流程不触发。这是为了避免无意义重复下发。

代码位置:

- `robot_modbus_lite/qt_gui.py:3946` `_wait_six_command_done()`

### 7. 浮点回显容差

结论: 已统一为 0.001。

文档建议回显浮点比较使用 `0.001` 容差。当前 `data/system_config.json` 和 `qt_gui.py` fallback 常量均已使用 `0.001`。

## 七、修改方案

### 7.1 修改目标

目标是把当前“核心可用”的 V4.3 上位机链路补齐为“按文档可验收”的实现:

- 发送顺序符合文档: 先状态前置检查，再写参数和回显校验。
- 回显容错符合文档: 3 次重读失败后重写参数，最多 2 轮。
- 可恢复错误闭环: 指令忙和可恢复 ERR 能复位并有限重试。
- 特殊语义补齐: Func110 执行中允许更新时间。
- 协议范围明确: Func111 要么实现，要么标注预留/删除。
- 现场可调: 回显参数进入配置文件。

### 7.2 阶段一: 低风险协议顺序和回显改造

范围:

- `robot_modbus_lite/qt_gui.py`
- `robot_modbus_lite/system_config.py`
- `data/system_config.json`

改动:

1. 新增 `_write_six_params_only(client, six_cmd, record)`，只负责写 IEEE(0~30)。
2. 新增 `_verify_six_echo_once(client, expected_map)`，只负责单次读取 IEEE(280~312) 并返回 mismatch。
3. 将 `_write_six_command()` 调整为:
   - Func104: 跳过普通前置检查。
   - 非 Func104: 先调用 `_precheck_six_command()`。
   - 进入最多 2 轮写入循环。
   - 每轮写参数后按 5ms 间隔读回显，最多 3 次。
   - 两轮失败后抛“回显通讯失败”。
   - 回显成功后写 IEEE(32)=1。
4. 把回显参数加入 `AxisRangeConfig` 或新建协议配置对象:
   - `echo_retry_interval_sec`
   - `echo_retry_count`
   - `echo_write_rounds`
   - `echo_compare_epsilon`
5. 默认值按文档设置:
   - `echo_retry_interval_sec = 0.005`
   - `echo_retry_count = 3`
   - `echo_write_rounds = 2`
   - `echo_compare_epsilon = 0.001`

验收:

- 回显匹配时仍能正常发送 Func108/Func110/Func120。
- mock 中人为延迟或改错回显时，能看到 2 轮重写日志。
- 前置条件失败时不再写 IEEE(0~30)。

### 7.3 阶段二: 指令忙和 ERR 自动恢复

范围:

- `robot_modbus_lite/qt_gui.py`
- `robot_modbus_lite/models.py`
- `mock_controller/controller.py`

改动:

1. 新增 `SixAxisCommandError` 或内部结果对象，携带:
   - `status_raw`
   - `alarm_raw`
   - `alarm_detail`
   - `func_num`
   - `is_cmd_busy`
2. 将 `_wait_six_command_done()` 遇到 ERR 时，不只抛字符串，先构造结构化错误。
3. 在 `_execute_send_six()` 外层增加有限重试:
   - 仅对 `LONG(38).02 指令忙` 自动恢复。
   - 最大重试 1 到 2 次。
   - 单条命令生命周期内总自动恢复次数不超过 2 次。
   - 等待同 slot 当前 EXEC 变 DONE/ERR。
   - 发送 Func104 `reset_ctrl=1`。
   - 等待 34.28=1 且 34.24=0。
   - 等待就绪使用独立超时，建议默认 5s；超时后停止重试并提示人工处理。
   - 重新走完整发送流程。
4. 对半径/高度/速度/参数非法等非指令忙报警，仍抛错，不自动重试。

验收:

- Func108 执行中立刻发 Func106: 首次出现指令忙，自动等待/复位/重试策略符合预期。
- 非可恢复报警不自动反复重试。
- 自动恢复日志能说明每次重试原因和 LONG(34)/LONG(38)。
- 复位后 5s 内 34.28 未恢复为 1 时，流程停止并输出“等待就绪超时”。

### 7.4 阶段三: Func110 覆盖更新语义

范围:

- `tools/verify_v43_mock_m9.py`

   - Func110 执行中发 Func120 仍拒绝。
2. 在 mock `_dispatch_six_command()` 中增加同样特例:
   - Func110 正在 EXEC 且新命令也是 Func110，不置 ERR。
   - 更新内部延时截止时间或延时参数。
3. `_do_six_delay()` 从一次性 `sleep(min(delay_sec, 2.0))` 改为循环检查可更新的 deadline。
4. 增加验证场景:
   - Func110 执行中再次 Func110，不出现 LONG(38).02。
   - 延时时间以最新值为准。
   - Func110 执行中 Func120 仍指令忙。

验收:

- `tools/verify_v43_mock_m9.py` 新增场景通过。
- 原有 Func110 + Func120 mutex 场景仍通过。
