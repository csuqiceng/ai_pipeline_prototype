## 一、核心目标与基本交流要求

### 1.1 核心命题：用语言交互替代人机界面的信息传递

#### 1.1.1 从视觉界面到语言界面的根本转变

传统工业机械手的操作方式，操作者通过HMI触摸屏与设备交互。触摸屏的本质是**视觉信息常驻界面**——设备状态、轴位数据、报警信息、安全参数、执行进度，所有信息以图形、数字、指示灯的形式**持续呈现在屏幕上**，操作者只需"看一眼"就能获取所需信息，无需等待、无需请求、无需任何交互动作。

当我们将交互方式从"视觉界面"切换为"自然语言界面"时，一个根本性的问题立即出现：

**屏幕上的信息是"一直在那里的"，而语言信息是"说了才有、不说就没有的"。**

这意味着：
- 触摸屏上，设备状态是**被动可见**的——操作者不需要做任何动作，信息就在那里
- 语言交互中，设备状态是**主动请求**才能获得的——操作者必须开口问，系统才能回答
- 触摸屏上，多个信息可以**同时呈现**——位置、速度、报警、状态一目了然
- 语言交互中，信息只能**串行传递**——一次只能说一条，听一条

这就是自然语言交互系统必须解决的核心矛盾：**如何用串行的、请求式的语言通道，替代并行的、常驻式的视觉通道，确保操作者获取信息的及时性和完整性不低于触摸屏。**

#### 1.1.2 替代的目标与标准

本系统的根本目标不是"增加一个语音控制功能"，而是**用自然语言交互完整替代HMI触摸屏的信息传递功能**。这意味着：

| 信息传递维度 | HMI触摸屏 | 自然语言交互系统（目标） |
|-------------|----------|----------------------|
| 信息获取速度 | 看一眼<100ms | 开口问→得到回答，必须≤200ms |
| 信息完整度 | 全部信息同时可见 | 按需提供，关键信息主动播报 |
| 信息实时性 | 画面实时刷新 | 看板数据实时同步，回答基于最新状态 |
| 操作确认 | 按钮按下即有视觉反馈 | 语音指令发出即有语言回执 |
| 异常感知 | 报警灯/报警画面持续闪烁 | 报警信息主动语音播报 |
| 安全状态 | 急停/暂停指示灯常亮 | 安全状态随时可查、变化主动通知 |

**底线标准**：自然语言交互系统在信息传递的及时性、完整性、准确性上，不得低于HMI触摸屏。如果做不到，操作者就会失去对设备状态的感知，产生焦虑和误判，导致误操作或非正常关机，系统就失去了存在的意义。

### 1.2 即时回应：系统的生命线

#### 1.2.1 为什么即时回应是重中之重

在工业生产场景中，操作者与机械手进行语言交互时，**最不能容忍的是沉默**。

原因如下：

**第一，沉默=失控感。** 操作者发出一条指令后，如果系统没有任何回应，操作者会立即产生疑问："我说的话它听到了吗？""它在执行吗？""是不是出故障了？"这种失控感会在200~500ms内产生，超过1秒未回应，操作者就会开始重复指令或采取其他行动（如按急停），这本身就是一种误操作风险。

**第二，沉默=信息黑洞。** 触摸屏上，设备状态是持续可见的，操作者随时知道设备在干什么。语言交互中，如果系统不主动告知状态，操作者就处于"信息黑洞"中——不知道设备是在执行、在等待、还是出了故障。

**第三，沉默=误操作根源。** 操作者在不确定设备状态时，最可能的反应是：
- 重复发送指令→可能导致指令冲突
- 自行判断设备状态→可能判断错误
- 直接按急停→中断正常生产流程
- 放弃语言交互，回到触摸屏操作→系统失去价值

**结论：即时回应不是"体验优化"，而是"安全底线"。没有即时回应，自然语言交互系统在工业场景中毫无意义。**

#### 1.2.2 即时回应的定义与分级

"即时回应"不是要求所有问题都在50ms内给出最终答案，而是要求**系统在任何情况下都不沉默，在最短时间内确认收到信息，并持续同步处理进度**。

具体分为三个层次：

**层次一：回执应答——"我听到了"**

无论操作者说什么，系统必须在最短时间内确认收到：

| 输入方式 | 回执应答时间 | 回执内容 |
|---------|------------|---------|
| 文字输入 | ≤50ms | "收到，正在处理" |
| 语音输入 | ≤200ms（VAD触发） | "系统在线，正在识别" |
| 应急指令 | ≤30ms（编码命中后） | "收到授权应急指令，立即执行" |

回执应答的核心作用：**消除操作者的"我说了它听到没有"的疑虑**。哪怕后台运算需要几秒钟，回执应答也必须在毫秒级完成。

**层次二：进度应答——"我处理到这儿了"**

当后台运算需要较长时间（如流程预演、运动规划），系统必须主动或被动地同步处理进度：

| 场景 | 进度应答方式 | 示例 |
|------|------------|------|
| 后台预演算中 | 阶段性播报 | "进度50%，已完成前3步安全核验" |
| 操作者中途追问 | 即时回复当前进度 | "当前进度70%，正在确认时序适配性" |
| 等待控制器响应 | 告知等待状态 | "指令已下发，等待控制器响应，当前设备状态正常" |

进度应答的核心作用：**消除操作者的"它还在不在处理"的疑虑**。操作者不应该需要猜测系统在做什么。

**层次三：结果应答——"这是你要的答案"**

最终结果返回，根据复杂度分级：

| 结果类型 | 应答时间 | 示例 |
|---------|---------|------|
| 简单查询（位置/状态/参数） | ≤500ms | "J1当前15.3°，J2当前-28.7°" |
| 安全预检 | ≤2s | "目标位置安全核验通过，可执行" |
| 运动规划预演 | ≤5s+进度播报 | "运动规划完成，最优路径已选定，需经中点绕行" |
| 流程级预演 | ≤8s+进度播报 | "流程预演完成，8步全部安全核验通过" |

#### 1.2.3 安抚性回应：防止焦虑和误操作的关键机制

**安抚性回应**是本系统独有的、针对工业场景的关键设计。

当后台运算或数据读取需要时间时，系统不是沉默等待，而是**立即给出安抚性回应，同步当前已知的设备状态**：

> 操作者："各轴位置多少？"
> 系统（≤50ms回执）："收到查询，正在同步轴位数据。"
> 系统（同步已知状态）："当前设备处于运行状态，无报警，通讯正常，数据读取中。"
> 系统（≤500ms结果）："J1:15.3° J2:-28.7° J3:45.2° J4:0.0° J5:90.1° J6:0.0°"

安抚性回应的核心逻辑：
1. **先确认收到**——操作者知道系统在工作
2. **同步已知状态**——操作者知道设备当前是安全的
3. **告知正在处理**——操作者知道需要等待
4. **给出最终结果**——操作者得到完整信息

**如果省略安抚性回应**，操作者在发出指令后的200ms~500ms内会处于"信息真空"状态，这是工业场景中不可接受的。

### 1.3 五级语义的即时回应要求

自然语言交互的5个语义层级，每一级都有不同的即时回应要求，但**共同底线是：任何层级都不允许沉默**。

#### 1.3.1 L1 闲聊咨询层

| 要求 | 标准 | 原因 |
|------|------|------|
| 回执应答 | ≤50ms | 即使是闲聊，也不能让操作者觉得系统没反应 |
| 结果应答 | ≤1s | 闲聊不需要复杂计算，但需要自然语言生成 |
| 特殊要求 | 闲聊中如涉及设备关键词，需主动提醒 | "我注意到您提到了'急停'，如需执行应急操作请使用标准格式" |

#### 1.3.2 L2 工艺查询层

| 要求 | 标准 | 原因 |
|------|------|------|
| 回执应答 | ≤50ms | 确认收到查询请求 |
| 进度应答 | 每2s播报一次 | 安全预检可能需要数秒 |
| 结果应答 | ≤5s+进度播报 | 预检结果必须准确，但进度必须实时同步 |
| 特殊要求 | 预检不通过时，必须明确告知风险点和建议 | 不能只说"不安全"，必须说"为什么不安全、怎么改才安全" |

#### 1.3.3 L3 常规生产执行层

| 要求 | 标准 | 原因 |
|------|------|------|
| 回执应答 | ≤50ms | 确认收到指令，防止操作者重复发送 |
| 安全预检结果 | ≤2s | 发出指令前必须完成安全预检 |
| 执行状态同步 | 每1s更新 | 运动执行期间持续同步状态 |
| 完成应答 | 运动完成后≤200ms | 告知运动完成及最终位置 |
| 特殊要求 | 运动过程中如操作者询问状态，必须即时回答 | "J2正在运动中，当前32.5°，目标45°，速度50%" |

#### 1.3.4 L4 系统管理层

| 要求 | 标准 | 原因 |
|------|------|------|
| 回执应答 | ≤50ms | 确认收到管理指令 |
| 参数变更确认 | ≤500ms | 参数修改前必须确认，防止误改 |
| 执行结果 | ≤2s | 参数修改结果必须及时反馈 |
| 特殊要求 | 安全参数修改需二次确认 | "确认将速度上限从80%修改为75%？请再次确认" |

#### 1.3.5 L5 应急安全层

| 要求 | 标准 | 原因 |
|------|------|------|
| 编码命中应答 | ≤30ms | 应急指令不等待语义分析，编码命中即执行 |
| 执行确认 | ≤100ms | 告知应急动作已执行 |
| 无效编码应答 | ≤200ms | 明确告知编码无效，不执行任何动作 |
| 特殊要求 | 单独提及关键词不触发动作，但必须回应 | "已收到，未识别有效授权指令，日常提及不执行动作" |

### 1.4 七类看板：语言界面的"虚拟屏幕"

#### 1.4.1 看板存在的根本原因

触摸屏上，信息是"一直在那里的"。语言界面中，信息是"说了才有"的。

**七类看板的本质，就是用内存缓存的方式，把触摸屏上"一直在那里的信息"变成"随时可以说的信息"。**

看板不是数据库，不是日志，而是**语言界面的"虚拟屏幕"**——操作者问什么，系统从看板中即时调取对应数据，组装成语言回答，不需要临时计算、不需要等待读取、不需要任何延迟。

| 看板 | 对应触摸屏上的信息 | 语言交互中的作用 |
|------|-------------------|----------------|
| 设备基础状态看板 | 主画面的状态指示灯+位置显示 | "设备现在什么状态"→即时回答 |
| 动作可行性看板 | 运动画面的"可执行"指示 | "现在能发指令吗"→即时回答 |
| 安全边界看板 | 安全参数画面 | "当前位置安全吗"→即时回答 |
| 运动极限看板 | 速度/加速度显示 | "速度超限了吗"→即时回答 |
| 流程预演进度看板 | 无（新增能力） | "流程预演到哪了"→即时回答 |
| 工艺适配看板 | 无（新增能力） | "这个位置能到吗"→即时回答 |
| 通讯故障看板 | 通讯状态画面 | "通讯正常吗"→即时回答 |

#### 1.4.2 看板数据的主动播报

看板不仅是"被动回答"的数据源，还必须支持**主动播报**——当关键状态发生变化时，系统主动告知操作者，而不需要操作者询问。

| 触发条件 | 主动播报内容 | 优先级 |
|---------|------------|--------|
| 报警发生 | "注意：J2轴速度超限报警" | 最高 |
| 急停状态变化 | "设备已进入急停状态" | 最高 |
| 运动完成 | "J2运动完成，当前位置45.02°" | 高 |
| 通讯异常 | "EtherCAT通讯异常，请检查" | 高 |
| 预检不通过 | "目标位置超出安全范围，建议调整" | 中 |

**主动播报的意义**：在触摸屏上，报警灯闪烁是操作者"被动感知"的。在语言界面中，如果没有主动播报，操作者可能完全不知道发生了异常。主动播报是语言界面替代视觉界面的必要条件。

### 1.5 防止误操作的语言交互设计原则

#### 1.5.1 信息真空是误操作的根源

操作者误操作的常见模式：

| 误操作模式 | 触发原因 | 语言交互中的预防措施 |
|-----------|---------|-------------------|
| 重复发送指令 | 不确定指令是否被接收 | 回执应答≤50ms |
| 自行判断设备状态 | 系统未及时反馈状态 | 安抚性回应+已知状态同步 |
| 焦虑性急停 | 不确定设备是否安全 | 安全状态主动同步 |
| 放弃语言交互 | 系统响应太慢 | 所有交互≤200ms内有回应 |
| 误发危险指令 | 系统未做安全预检 | 指令安全网关强制预检 |

#### 1.5.2 语言交互的三不原则

**不沉默**：任何输入必须在最短时间内得到回应，无论后台处理是否完成。

**不模糊**：所有回答必须精确、具体，禁止模糊表述。

| 模糊表述（禁止） | 精确表述（要求） |
|----------------|----------------|
| "位置异常" | "J2轴超出负限位，当前-175.3°，限位-170°" |
| "速度有问题" | "指令速度80%，安全上限75%，超限5%" |
| "不太安全" | "目标位置R=850mm，安全上限R_max=800mm，半径超限50mm" |
| "处理中" | "安全预检进度60%，已完成限位检查和速度检查，正在进行空间范围核验" |

**不遗漏**：操作者需要知道的信息，系统必须完整提供，不能只给部分。

### 1.6 与未来AI迭代的关系

#### 1.6.1 当前阶段：人工语言交流是重中之重

本系统的第一阶段目标，是**实现可靠、即时、安全的自然语言交互**，替代HMI触摸屏的信息传递功能。这是系统的立身之本，如果这一步做不到，后续所有AI能力都无从谈起。

#### 1.6.2 未来阶段：生产工艺大模型的学习与迭代

当自然语言交互系统稳定运行后，将积累大量的交互日志、设备工况数据、预演算结果。这些数据是未来生产工艺大模型的训练基础：

- **对话日志**→大模型学习操作者的表达习惯和工艺需求
- **设备工况数据**→大模型学习设备在不同工况下的行为特征
- **预演算结果**→大模型学习安全边界和运动策略
- **执行结果**→大模型验证优化参数的实际效果

大模型的迭代闭环：数据采集→模型训练→参数优化→安全验证→效果反馈→持续迭代。

但这一切的前提是：**第一步，自然语言交互必须做到即时、准确、安全。**

### 1.7 本章结论

自然语言交互系统的核心价值，不在于"能用语音控制机械手"，而在于**用语言交互完整替代视觉界面的信息传递功能，并且在即时性、完整性、安全性上不低于视觉界面**。

要做到这一点，系统的核心能力是：

1. **即时回应**——任何输入≤200ms内有回应，消除信息真空
2. **安抚性回应**——后台运算期间持续同步状态，防止焦虑和误操作
3. **七类看板**——把视觉界面的常驻信息变成语言界面的即时可答数据
4. **主动播报**——关键状态变化主动告知，替代视觉界面的被动感知
5. **精确回答**——所有回答具体、量化、无模糊，确保操作者准确理解设备状态

这五项能力是后续所有技术架构、模块设计、开发实施的基础和出发点。如果这五项能力无法实现，本系统在工业场景中不具备应用价值。

### 3.2 L2运动规划预演的关键策略

**问题**：ZMotion控制器的运动学正逆解（FRAME_TRANS2）是固件黑盒，无法直接获取算法源码。纯Python复现逆解需大量验证工作，且存在与控制器结果不一致的风险。

**解决方案：调用控制器API**

| 方案 | 说明 | 优势 | 劣势 |
|------|------|------|------|
| **方案A（推荐）：调用控制器API** | Python通过ZMotion PC函数库发送FRAME_TRANS2指令，控制器返回逆解结果 | 精度100%一致、开发周期短 | 需控制器在线 |
| 方案B：纯Python实现 | 自行实现6轴DH正逆解 | 离线可用 | 需5~10天验证，有精度风险 |
| 方案C：混合方案 | 正解Python实现+逆解调用API | 正解可离线验证 | 复杂度略高 |

**推荐方案A**的具体实现：

```python
import zmotion

class KinematicsEngine:
    def __init__(self, controller_ip="192.168.1.11"):
        self.handle = zmotion.ZAux_OpenEth(controller_ip)
    
    def forward_kinematics(self, joint_angles, fstatus=0):
        """正解：关节角→笛卡尔位姿，调用FRAME_TRANS2(dir=1)"""
        for i, angle in enumerate(joint_angles):
            zmotion.ZAux_Direct_SetTable(self.handle, 550 + i, angle)
        zmotion.ZAux_Direct_SetTable(self.handle, 556, fstatus)
        zmotion.ZAux_Execute(self.handle, "FRAME_TRANS2(550,560,1)")
        result = [zmotion.ZAux_Direct_GetTable(self.handle, 560 + i) for i in range(6)]
        return result  # [x, y, z, rx, ry, rz]
    
    def inverse_kinematics(self, cart_pose, fstatus=0):
        """逆解：笛卡尔位姿→关节角，调用FRAME_TRANS2(dir=2)"""
        for i, val in enumerate(cart_pose):
            zmotion.ZAux_Direct_SetTable(self.handle, 550 + i, val)
        zmotion.ZAux_Direct_SetTable(self.handle, 556, fstatus)
        zmotion.ZAux_Execute(self.handle, "FRAME_TRANS2(550,560,2)")
        result = [zmotion.ZAux_Direct_GetTable(self.handle, 560 + i) for i in range(6)]
        return result  # [j0, j1, j2, j3, j4, j5]
```

MotionPlan的决策逻辑（FSTATUS遍历、评分、奇异点检测、中点策略）在Python侧实现，正逆解计算委托给控制器，确保结果100%一致。

#### 6.4.1 L1 即时安全检查（单动作级）

纯Python实现，无需调用控制器API：

| 检查项 | Python实现 | 数据源 |
|--------|-----------|--------|
| 球面半径 | `r_min < sqrt(x²+y²+z²) < r_max` | 看板3 |

**实现示例**：

```python
def l1_safety_check(target_pose, dashboard):
    results = {}
    results['spatial_ok'] = check_spatial_limits(target_pose, dashboard['safety'])
    results['speed_ok'] = check_speed_limits(target_pose, dashboard['speed'])
    results['limit_ok'] = check_soft_limits(target_pose, dashboard['safety'])
    results['system_ok'] = check_system_status(dashboard['status'])
    results['overall'] = all(results.values())
    return results
```

#### 6.4.2 L2 运动规划预演

**调用控制器FRAME_TRANS2 API**，Python侧实现决策逻辑：

| 检查项 | Python实现 | 控制器API调用 |
|--------|-----------|-------------|
| FSTATUS遍历 | 8次循环+评分 | `FRAME_TRANS2(dir=2, fstatus=i)` |
| 奇异点检测 | 插值5点+阈值判断 | `FRAME_TRANS2(dir=2)` |
| 中点规划 | RY偏移5° | `FRAME_TRANS2(dir=2)` |
| 运动规划决策 | MotionPlan决策树 | 依赖上述API结果 |

**FindBestFstatus Python实现**：

```python
def find_best_fstatus(target_pose, current_joints, kinematics, limits):
    best_score = float('inf')
    best_fstatus = -1
    best_joints = None
    
    for fstatus in range(8):
        joints = kinematics.inverse_kinematics(target_pose, fstatus)
        if joints is None:
            continue
        
        if not check_joint_limits(joints, limits):
            continue
        
        motion_cost = sum(abs(j - c) / r for j, c, r in zip(joints, current_joints, [320,230,272,540,250,900]))
        sing_penalty = 5 * (10 - abs(joints[4])) / 10 if abs(current_joints[4]) >= 10 and abs(joints[4]) < 10 else 0
        wind_penalty = abs(joints[3]) / 540 + abs(joints[5]) / 900
        total_score = motion_cost + sing_penalty + wind_penalty
        
        if total_score < best_score:
            best_score = total_score
            best_fstatus = fstatus
            best_joints = joints
    
    return best_fstatus, best_joints, best_score
```

## 七、配套界面设计规范

### 7.1 界面定位：语言交互的"脸"

配套界面不是替代HMI触摸屏的控制面板，而是语言交互系统的"脸"——操作者盯着这张脸交流，不需要鼠标键盘，一切操作都可以用语言完成。

核心定位：
1. **视觉伴侣**：补充语言"说了才有"的先天缺陷，让关键信息"一直在那里"
2. **对话伙伴**：显示语音识别文字+系统回应文字，让交流有"着力点"
3. **安全屏障**：安全关键操作提供双通道确认（语音+按钮）
4. **全语音可控**：界面上一切操作都有语音等价指令，鼠标键盘是可选的，不是必需的

## 十、关键风险与缓解方案

| 风险 | 影响 | 缓解方案 |
|------|------|---------|
| MODBUS TCP轮询延迟 | 核心数据可能偶尔超出50ms | 分组轮询+状态字优先+位置数据可容忍偶尔延迟 |
| PC与控制器状态同步 | 50ms stale data可能导致误判 | 安全关键操作强制调用Func13/14实时确认 |
| 语音识别噪音 | 工业现场ASR准确率下降 | 定向麦克风+降噪+文本/按钮为主要方式 |
| PC程序崩溃 | 交互系统失效 | 守护进程+看门狗+HMI始终可用作备用 |
| FRAME_TRANS2调用延迟 | L2预演可能较慢 | 缓存逆解结果+异步预演+进度播报 |
| 未来大模型对接 | 接口不兼容 | JSON格式统一+标准化接口定义 |
