# V4.3 真机回显等待改造方案

## 1. 背景

真机联调阶段发现，六轴标准函数在“写参数后立即校验回显”这一步仍存在误报。

当前协议链路是：

1. 写 `IEEE(0~30)` 参数区
2. 读 `IEEE(280~312)` 回显区
3. 回显正确后再做前置检查
4. 写 `IEEE(32)=1` 触发执行

控制器侧此前是 `50ms` 周期刷新回显区。当前已改为同步刷新，但上位机仍沿用“逐点短重试”的校验方式，仍可能出现以下问题：

- 读回显时机不稳定，可能刚好读到旧值
- 某个单点值短时间不一致，直接报“通讯异常”
- 只看单点，不足以判断整段回显区是否正在收敛
- 失败证据不足，难以区分是上位机、SDK 还是控制器程序问题

## 2. 已暴露的问题

### 2.1 旧逻辑只适合“短暂延迟”，不适合“等待收敛后再触发”

当前 `qt_gui.py` 的 `_write_six_command()` 在写参数后，会对 `expected_echo_points()` 返回的每个地址逐点读取并短重试：

- 重试次数：`30`
- 间隔：`0.02s`
- 单点窗口：约 `0.6s`

该模型只能覆盖“回显很快收敛”的情况，不能表达新的现场需求：

> 在报警时间内持续读回显；一旦回显正常且满足运行要求，就立即执行；超时才报警。

### 2.2 单点校验容易误判

真机现场已出现两类典型错误：

1. `IEEE(280)` 期望值正确，但上位机读到 `0`
2. `IEEE(282)` 期望 `1000`，连续多次实际读到 `1500`

第一类更像回显时机问题；第二类说明问题已不只是“等得不够久”，而可能是：

- 回显区整段尚未稳定
- 控制器回显区与上位机预期存在阶段性错位
- 正在读到上一条命令残留或未完成覆盖的数据

只报单点值不匹配，不足以判断根因。

### 2.3 失败判定模型仍需按通讯自检口径收紧

现场需求不是“某次读错就失败”，而是按通讯自检参数判定：

- 按设定的重试间隔持续读取
- 按设定的最大重试次数决定是否报警
- 在连续 `3~5` 次读取都不一致时，才记为稳定异常
- 达到最大重试次数仍未满足执行条件，才正式报警

也就是说，失败判定应从“单点短重试失败”改成“重试间隔 + 重试次数驱动的连续收敛等待失败”。

### 2.4 缺少等待过程证据

当前日志能看到：

- 哪个地址失败
- 期望值 / 实际值
- 重试次数

但现场排障真正需要的是：

- 回显等待总耗时
- 第几次轮询开始收敛
- 最后一帧完整回显区快照
- 哪些点始终不一致
- 是否在等待期内出现过短暂正确后又回退

没有这些数据，就无法判断是否需要修改控制器程序。

## 3. 新需求归纳

根据现场结论，上位机应改成以下行为：

1. 发送函数号和参数后，不立即触发
2. 进入“回显等待阶段”
3. 在设定的报警时间内，持续读取回显区
4. 如果回显正常，且运行前置条件满足，则立即触发执行
5. 如果达到最大重试次数仍未满足执行条件，则报警
6. 整个等待过程必须记录耗时和关键快照，方便判定是否需要改控制器程序

## 4. 目标行为

### 4.1 新执行顺序

标准函数（`11/106/107/108/109/110/120`）调整为：

1. 写参数区 `IEEE(0~30)` 或 `IEEE(400+)`
2. 进入回显等待阶段，持续读取 `IEEE(280~312)` 回显区
3. 回显区满足本次命令预期
4. 执行前置检查（`LONG(34)` / `LONG(36)`）
5. 一旦前置检查通过，立即写 `IEEE(32)=1`
6. 等待 `DONE/ERR`

### 4.2 失败条件

仅在以下任一条件满足时失败：

1. 达到最大重试次数，回显区仍未收敛
2. 达到最大重试次数，回显已正常但前置检查始终不满足

### 4.3 成功条件

在最大重试次数范围内，只要同时满足：

- 回显区与当前命令一致
- 前置检查通过

则立即触发，不再额外等待。

## 5. 解决方案

### 5.1 将“回显校验”改成“回显等待阶段”

当前逐点短重试逻辑，改为独立函数，例如：

- `_wait_six_command_echo_ready(...)`

职责：

1. 连续读取回显区
2. 判断整段回显是否满足本次命令
3. 返回等待耗时、轮询次数、最终快照

### 5.2 读取方式从“单点立即失败”改为“整帧快照采集”

每轮轮询都应形成一帧完整回显快照：

- `IEEE(280~312)` 对应 `17` 个 FLOAT 槽位
  - `280` = 函数号回显
  - `282 + i*2` = 参数 `i`
  - `312` = 触发位回显

优势：

- 能看到一整帧回显是否一致
- 能判断是单点异常还是整段尚未同步
- 失败日志可直接保存完整快照

实现说明：

- 为规避真机 `read_modbus_float(count>1)` 批量读取语义仍待确认的问题
- 第一版实现采用“每轮逐点读取、组装成完整快照”的方式
- 等真实硬件确认 `count>1` 读法稳定后，再决定是否切换为单次批量读取

### 5.3 引入“连续不一致计数”而不是单次立即失败

在整个重试过程中：

- 某一轮不一致，不立即失败
- 连续 `3~5` 次不一致，只记为“当前仍未收敛”
- 仍继续轮询，直到：
  - 收敛成功，或者
  - 达到最大重试次数

这里的“连续 `3~5` 次”用于降低单次通讯抖动误判，不代替最大重试次数。

当前第一版实现口径：

- 连续错误阈值默认取 `5`
- 连续错误阈值只用于预警和“稳定异常”识别
- 正式报警由“达到最大重试次数仍未成功”决定
- 连续错误计数必须具备明确语义：成功时归零，失败时累加，不允许把“累计失败轮数”误当成“连续失败次数”
- 最终失败分类不看“最后一轮失败种类”，而看“是否曾经回显成功”
  - 从未回显成功：`六轴回显通讯失败`
  - 回显曾成功但前置检查始终未过：`六轴回显正常但执行条件不满足`

### 5.4 成功后立即触发

一旦某轮满足：

- 回显区全部匹配
- 运行前置检查通过

则立刻执行触发，不做额外等待。

这与现场要求一致：

> 在报警时间内，回显正常且满足运行要求就马上执行。

### 5.5 日志增强

必须补充以下记录：

1. 回显等待开始
   - `dispatch_id`
   - `func_num`
   - 期望写入项
   - 总超时
   - 轮询间隔

2. 回显等待成功
   - 总耗时
   - 轮询次数
   - 成功时完整快照

3. 回显等待超时
   - 总耗时
   - 轮询次数
   - 最后一帧完整快照
   - 不匹配点列表

4. 回显等待期间的关键变化
   - 首次读到非零/非默认值
   - 首次全量匹配
   - 回显从正确又回退为错误时的异常记录
   - 连续失败计数何时开始、何时归零

## 6. 参数建议

第一版建议把“回显等待”参数独立出来，不复用运动超时：

- `echo_poll_interval_sec`
- `echo_max_retry_count`
- `echo_consecutive_mismatch_threshold`

建议默认值：

- `echo_poll_interval_sec = 0.05`
- `echo_max_retry_count = 100`
- `echo_consecutive_mismatch_threshold = 5`

说明：

- `0.05s` 与此前控制器 `50ms` 刷新周期兼容，也适合当前同步刷新场景
- `100` 次最大重试对应的派生等待窗口约为 `5s`，但真正的主参数应是“次数”，不是“秒数”
- `5` 次连续不一致更适合现场通讯抖动去抖；如后续验证控制器回显已完全稳定，可再收紧到 `3`

派生展示量：

- `derived_wait_sec = echo_poll_interval_sec * echo_max_retry_count`

该值用于日志展示和联调说明，不作为主报警判据。

## 7. 拟修改点

### 7.1 代码

计划修改：

- `robot_modbus_lite/qt_gui.py`
  - 用“回显等待阶段”替换现有逐点短重试
  - 移除写前 `ready/slot/ERR` 硬拦截，改为写参数后在等待阶段持续检查
  - 在触发前增加“回显正常 + 前置检查通过”的联合判断
  - 把报警主模型改为“重试间隔 + 最大重试次数”
  - 将失败出口拆成两类：
    - `六轴回显通讯失败`
    - `六轴回显正常但执行条件不满足`
  - 修正连续失败计数语义，确保成功时归零
  - 增强失败日志和整段快照记录

## 8. 验收方式

### 8.1 正常场景

写入参数后，控制器在最大重试次数内完成回显同步：

- 上位机持续轮询回显区
- 回显收敛后立即触发
- 不再出现“读一次不对就报错”

### 8.2 延迟场景

控制器回显存在数轮延迟：

- 上位机在等待期内继续轮询
- 日志记录轮询次数和派生等待耗时
- 收敛后立即执行

### 8.3 异常场景

控制器回显始终不正确：

- 上位机持续轮询直到最大重试次数
- 达到最大重试次数后报警
- 日志保留最后完整回显快照和不匹配点列表

### 8.4 前置条件异常场景

控制器回显已正确，但前置条件一直不满足：

- 上位机继续轮询直到最大重试次数
- 达到最大重试次数后报“执行条件不满足”
- 日志保留最后一次前置检查错误和对应快照

## 9. 当前结论

这次问题的核心，不再是“单纯把重试时间调长”。

真正需要改的是执行模型：

- 从“写完后短时间逐点验回显”
- 改成“写完后进入按重试间隔和最大重试次数驱动的连续回显等待阶段”

这样才能同时满足：

- 真机同步刷新场景
- 通讯抖动容错
- 现场排障可追溯
- 成功即触发，超时才报警
