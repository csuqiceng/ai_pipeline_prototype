# V4.3 M9 并行执行框架实施计划

## 1. 目标

实现 V4.3 1.3 节定义的并行执行模型:

```text
Func110(T1延时) 和 Func120(IO输出) 可与运动/标准函数同时执行。
Func110 和 Func120 之间串行执行，不能同时运行。
```

当前代码仍基本按单任务串行模型执行:

```text
mock_controller 只有一个 _exec_thread_six
_dispatch_six_command() 用全局 busy 阻塞所有非 Func104 函数
GUI _execute_send_six() 每次触发后等待该函数完成
```

M9 的目标是拆成 slot 模型:

```text
motion slot:
  Func106 / Func107 / Func108 / Func109 / Func11

program slot:
  Func110 / Func120

system command:
  Func104
```

## 2. 并行规则

### 2.1 motion slot

包含:

```text
Func106 关节点动
Func107 虚拟轴点动
Func108 直线插补/PTP
Func109 T0延时/检测
Func11  连续插补
```

规则:

```text
motion slot 内部互斥。
同一时间只能有一个标准函数执行。
```

### 2.2 program slot

包含:

```text
Func110 T1延时
Func120 IO输出/夹爪
```

规则:

```text
Func110 和 Func120 串行互斥。
不能同时执行。
```

### 2.3 Func109

V4.3 1.1 明确 `Func109` 属于标准函数执行逻辑，使用 `LONG(34)` 的独立状态位 `34.08/34.09`。

```text
Func109 纳入 motion/standard slot。
Func109 与 Func106/107/108/11 串行互斥。
Func109 不纳入 program slot，不与 Func110/120 互斥。
```

### 2.4 Func104

Func104 为系统控制命令:

```text
急停 / 暂停 / 取消 / 复位
```

规则:

```text
Func104 不受 slot 限制。
执行中也允许触发。
```

## 3. 修改范围

### 3.1 models.py

新增 slot 定义和状态判断工具。

建议新增:

```python
MOTION_FUNCS = {11, 106, 107, 108, 109}
PROGRAM_FUNCS = {110, 120}
SYSTEM_FUNCS = {104}

def six_func_slot(func_num: int) -> str:
    ...
```

修改或新增:

```python
SixAxisStatus.slot_busy(slot: str) -> bool
SixAxisStatus.can_send_for(func_num: int) -> bool
```

目标:

```text
Func106/107/108/109/11: 只检查 motion slot
Func110/120: 只检查 program slot
Func104: 永远允许
报警、急停、未就绪仍应阻止非 Func104 函数
```

注意:

```text
DONE 状态仍需在触发前清理。
ERR 状态必须复位后重试。
```

### 3.2 mock_controller/controller.py

当前问题:

```text
_exec_thread_six 是单线程
_dispatch_six_command() 用全局 busy 阻塞所有函数
Func104 下发前还会 join 旧线程，影响即时性
```

建议修改:

```python
self._exec_threads_six: dict[str, threading.Thread]
```

slot 映射:

```text
motion  -> 11 / 106 / 107 / 108 / 109
program -> 110 / 120
system  -> 104
```

调度规则:

```text
1. Func104 直接启动独立线程或同步执行，不等待 motion/program 线程结束
2. 标准函数只检查 motion 线程是否 alive
3. program 函数只检查 program 线程是否 alive
4. 同 slot busy 时:
   - 设置目标函数 ERR
   - 写 LONG(38).02 指令忙
5. 不同 slot busy 时允许并发
```

验收点:

```text
Func108 执行中可以触发 Func110
Func110 执行中不能再触发 Func120
Func108 执行中可以触发 Func104
```

### 3.3 qt_gui.py 执行层

当前 `_execute_send_six()` 是单命令同步等待完成。

M9 不需要一次性把所有 GUI 行为改成复杂异步队列，但需要支持并行触发的基础能力。

建议拆分:

```python
_precheck_six_slot(client, six_cmd)
_write_six_command(client, six_cmd, record)
_wait_six_function(client, six_cmd, record)
_read_six_feedback(client, six_cmd, record)
```

然后保留现有同步 API:

```text
普通单条执行仍等待本函数完成。
```

新增并行执行入口供流程使用:

```python
_trigger_six_no_wait(client, record) -> SixAxisCommand
_wait_six_command_done(client, six_cmd, record) -> None
```

这样流程层可以实现:

```text
trigger Func108 no-wait
trigger Func110 no-wait
wait Func110 done
trigger Func120 no-wait
wait Func120 done
wait Func108 done
```

### 3.4 流程执行器

当前流程大概率按 step 顺序串行调用 `_execute_send_six()`。

M9 最小可行方案:

```text
先不改自然语言和普通按钮执行。
只为流程执行器支持一个明确的并行场景:
标准函数后紧跟 Func110，然后 Func120。
```

推荐流程规则:

```text
如果当前 step 是 motion/standard 函数，且后续 step 是 Func110:
  1. 触发 motion/standard no-wait
  2. 触发 Func110 no-wait
  3. 等 Func110 DONE
  4. 如果下一步是 Func120，触发 Func120 并等待 DONE
  5. 等 motion DONE
  6. 继续后续流程

否则:
  保持串行执行
```

后续可扩展为通用 DAG/slot 调度，但第一版不建议过度设计。

## 4. 前置检查规则

### 4.1 非 Func104 通用条件

触发前仍需检查:

```text
34.24 = 0 无报警
34.25 = 0 未急停
34.28 = 1 系统就绪
```

### 4.2 slot 检查

motion/standard 函数:

```text
检查 11/106/107/108/109 中是否有 EXEC。
若有 EXEC，则 motion slot busy。
```

program 函数:

```text
检查 110/120 中是否有 EXEC。
若有 EXEC，则 program slot busy。
```

Func104:

```text
跳过 slot 检查。
```

### 4.3 DONE 清理

当前已有目标函数 DONE 自动 Func104 reset 的逻辑。

M9 需要注意:

```text
不能为了清理目标函数 DONE 而误清另一个正在运行 slot 的状态。
```

风险:

```text
Func104 reset_ctrl=1 会清所有函数状态位。
如果 motion 正在执行，program 下发前为了清 program DONE 触发 reset，会清掉 motion 状态。
```

建议改法:

```text
M9 后不要在另一个 slot 正在执行时自动发 Func104 reset 清 DONE。
DONE 状态按协议允许下次触发自动覆盖，mock 也应支持覆盖 DONE。
ERR 状态仍要求人工/显式复位。
```

因此需要修改:

```text
_execute_send_six() 中 AUTO_CLEAR_DONE 逻辑
```

建议:

```text
目标函数 DONE 时允许触发，不自动 reset。
目标函数 ERR 时阻止触发。
```

## 6. GUI/流程最小验收场景

### 6.1 mock 单元场景

场景 A: motion + program 并行

```text
1. 触发 Func108
2. 立刻触发 Func110
3. 期望:
   - Func108 状态可为 EXEC
   - Func110 状态可为 EXEC/DONE
   - 不出现 LONG(38).02
```

场景 B: program 内互斥

```text
1. 触发 Func110 delay=1s
2. 立刻触发 Func120
3. 期望:
   - Func120 ERR
   - LONG(38).02 指令忙
```

场景 C: motion 内互斥

```text
1. 触发 Func108
2. 立刻触发 Func106 或 Func109
3. 期望:
   - 后触发函数 ERR
   - LONG(38).02 指令忙
```

场景 D: Func104 即时触发

```text
1. 触发 Func108
2. 立刻触发 Func104 pause/estop/reset
3. 期望:
   - Func104 可响应
   - 不等待 Func108 线程 join
```

场景 E: reset_ctrl 清状态后的 slot 一致性

```text
1. 触发 Func108 或 Func110
2. 执行中触发 Func104 reset_ctrl=1
3. 期望:
   - LONG(34) 函数状态位被清除
   - LONG(38) 报警详情被清除
   - mock slot 线程引用不残留假忙
   - 后续新命令可正常触发
```

### 6.2 GUI/流程场景

典型 V4.3 场景:

```text

```

## 7. 风险点

### 7.1 Func104 reset 清所有状态

Func104 `reset_ctrl=1` 会清所有函数状态位。

并行执行时不能随意自动 reset，否则可能清掉另一个正在执行 slot 的状态。

### 7.2 单连接并发写入

GUI 通过同一个 controller client 下发命令。

如果真实 SDK/连接不支持多线程并发，需要:

```text
写入和读取仍串行加锁
但业务上允许不同 slot 的状态同时存在
```

也就是说:

```text
协议并行 != 多线程同时调用 SDK
```

### 7.3 IEEE(32) 单触发位

所有函数共用 `IEEE(32)` 触发位。

并行触发时必须保证:

```text
一次写完参数后再写 IEEE(32)=1
下一个函数写参数前，下位机已经锁存上一条命令
```

建议在连续触发不同 slot 时保留短暂间隔:

```text
20~50ms
```

### 7.4 当前函数号 IEEE(322)

并行时 `IEEE(322)` 只能显示一个当前函数号。

因此状态判断不能依赖 `IEEE(322)`，必须以 `LONG(34)` 各函数 2-bit 状态为准。

## 9. 验收标准

1. Func108 执行中可以触发 Func110，不报指令忙。
2. Func108 执行中可以触发 Func120，不报指令忙。
3. Func110 执行中触发 Func120，会报 `LONG(38).02 指令忙`。
4. Func108 执行中触发 Func106 或 Func109，会报 `LONG(38).02 指令忙`。
5. Func104 在 motion/program 执行中仍可触发。
6. GUI 普通单条执行行为不退化。
7. 流程可执行 V4.3 典型场景。
8. 不再用单个全局 `busy/can_send` 阻塞所有函数。
9. 状态判断以 `LONG(34)` 函数 bit 为准，不依赖 `IEEE(322)`。
10. 编译和 mock 冒烟全部通过。
