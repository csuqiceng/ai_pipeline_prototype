# 用户页面实现现状与缺口总结

**日期**：2026-05-20  
**评估范围**：Qt 用户页面 `robot_modbus_lite/operator_ui_mixin.py`，以及它依赖的自然语言、语音、实时轮询、系统命令链路。  
**对照依据**：《机械手自然语言交互系统_项目需求与技术路线建议书_V2.1.md》与对方 AI 评审结论。

---

## 一、结论概览

当前用户页面已经完成了“操作员工作台”的基本界面骨架，包含状态侧栏、对话区、场景区、完整状态页、快捷系统操作、文本自然语言入口、主要按钮语音等价指令、全屏/小窗口切换等能力。

但它还没有达到 V2.1 文档中“用自然语言交互替代 HMI 信息传递”的完整现场验收目标。核心差距不在界面壳，而在界面背后的真实设备闭环：真实 VAD 触发、50ms 真机级分组轮询、真机级 L2 运动预演、现场 TTS 验收、硬件/线程级独立应急通道和真机归档边界验证仍未完成。单动作和流程级中点绕行建议已具备离线逻辑骨架，但还没有经过控制器路径执行验证。

对方 AI 评审中“即时回应、七类看板、L1/L2/L3 预检、应急编码、主动播报缺失”的原始判断在评审当时基本成立；经过 2026-05-20 的 P0 实施后，应急编码、统一回应、主动播报队列、L1/L2/L3 基础预检预演已进入“基础实现”阶段，但仍未达到 V2.1 完整标准。它把“场景页、全屏/小窗口、部分语音等价、完整状态页”判为完全缺失，这一点与当前代码不符。

说明：本文中的“对方 AI 评审”指 2026-05-20 围绕 V2.1 需求文档与当前代码实现所做的外部实现对照评审。

实施进展补充：2026-05-20 已开始 P0 安全交互闭环实现，新增 `emergency_channel.py`、`response_builder.py`、`broadcast_queue.py`、`dashboard.py`、`safety_precheck.py`、`safety_suggestion.py`、`kinematics_engine.py`、`motion_plan.py`、`process_precheck.py`、`json_schema.py`，并接入用户页最小链路。当前“应急编码、统一回应、播报队列、看板快照、L1 基础预检、保守风险建议、L2 接口骨架、L3 流程预演骨架和 A/B/C JSON 结构”已从“完全缺失”推进到“基础模块已实现，仍需真机验证和50ms数据源”阶段。L2 已能基于用户页当前位姿和模板目标位姿执行 5 点插值奇异点检查骨架，失败结果会阻断确认执行；未配置逆解引擎时仍返回 `unavailable`，只提示不误判通过。L3 已能检查流程模板完整性、逐步 L1/L2、步间隔、累计误差预算和简化禁入包围盒，并已补阶段级进度事件。主动播报方面已补第一版 `context_id + dedupe_key` 去重，系统/应急/报警反馈日志不会再短时间重复刷屏。2026-05-21 已补 `OperatorSceneState`，真实场景切换有结构化日志，文本交互归档会写入 `input.scene_state`；`DashboardCache` 已增加 `feedback_age_ms/feedback_fresh/stale_after_ms`，可暴露实时反馈是否过期；`DashboardQueryService` 已能把通信 `stale` 状态回答为“实时反馈已过期”的高优先级告警。用户页看板快照刷新、重 UI 刷新、控制器实时轮询和 stale 阈值已配置化，默认分别为 50ms、500ms、500ms、1000ms；工程师后台保存配置后可立即应用到已启动 timer；控制器轮询已拆成关节/位姿高频反馈组和状态/报警低频详情组，并已把 MPOS/DPOS、AXISSTATUS、MOTIONTYPE 接入看板快照和完整状态页。即时回应验收方面，文本输入回执已写入 `ack_delay_ms/ack_limit_ms/ack_sla_passed`，按 50ms 标准归档；语音录音启动回执已记录 200ms SLA 字段；三段式应急编码快路径已直接发布回执并记录 30ms SLA 字段。预检等待体验方面，用户页已能在可执行计划预检前发布设备/通讯状态安抚回应，并按 L1 33%、L2 66%、预检完成 100% 发布阶段性进度，L2/L3 预演内部也已具备阶段级进度事件。长耗时任务等待体验已补第一版：用户页刷新循环检测到执行/暂停/流程运行等活跃状态时，会按默认 2 秒间隔发布设备/通讯状态安抚回应，空闲后自动重置。执行进度方面已补基础估算：优先使用控制器 `motion_percent`，其次按流程步数或自然语言动作序号估算，缺少可靠百分比但运行中时给出保守 50%。用户页主要按钮语音等价已新增集中规范表 `operator_voice_commands.py`，按钮语音处理和普通界面语音命令均已接入同一匹配入口，并已生成 `docs/用户页语音等价指令清单.md` 用于现场验收。完整状态内部查询已新增 `dashboard_query_specs.py` 规范表，并生成 `docs/用户页完整状态查询清单.md`。工艺解释型问答已补第一版，可回答“为什么不能执行/为什么有风险/建议怎么处理”。

二次原子函数封装补充：`VoiceNlpAdapter` 已接入“小正/小郑/校正”唤醒词门禁。普通生产指令无唤醒词会返回 `unknown`，不会进入模板、流程或系统动作；三段式“急停 授权码 急停”作为应急例外，仍可无唤醒词进入应急校验链路。2026-05-21 已补 V2.1 五级语义元数据基础版：闲聊咨询标记为 L1，看板/工艺查询标记为 L2，模板/流程执行标记为 L3，普通系统管理标记为 L4，三段式急停标记为 L5，并写入类型 A `command_intent.semantic_level`。同日新增 `semantic_response_policy.py`，集中维护 L1~L5 的回执时限、结果时限、进度播报间隔、预检/确认要求和应急快路径标记；Qt 用户页 NLP 归档会写入这些策略字段。2026-05-22 已补 `jieba` 可选分词层：环境安装 `jieba` 时会记录 tokens，并把 `nlp_engine=jieba_rule` 写入解析预览和类型 B 归档；tokens 已开始参与本地规则候选评分，例如“查一下安全范围”可通过分词命中看板3安全边界查询，三段式急停仍保持最高优先级。L2 工艺查询基础版已接入：通讯、状态、安全边界、运动极限、流程预演、工艺适配等问句会生成 `query` 动作，并从看板缓存直接回答，不进入执行链路；当前已能回答“为什么现在不能动”“流程预演到哪一步了”“报警后我该怎么处理”等常用现场问法。L4 系统管理已补第一版二次确认细分：暂停、继续、取消当前任务直接执行，报警复位需要确认；待确认计划不会再被父级 NLP 执行路径绕过。

当前完成度口径：

- Qt GUI + 离线逻辑 + 不含 Web + 不含真机/部署验收：约 98%。
- Qt GUI + 含真机/VAD/TTS/50ms 数据源验收：约 82%-85%。
- 完整 V2.1 全量口径：约 75%-80%。

## 二、用户页面已经实现的内容

### 2.1 页面主体结构已实现

用户页面由 `OperatorUiMixin._build_operator_page()` 构建，已经形成三栏式操作界面：

| 区域 | 当前实现 |
|---|---|
| 左侧状态栏 | 设备总状态、安全状态、关节/坐标、快捷操作 |
| 中间对话区 | AI 助手对话、文本输入、解析、执行、录音、清空 |
| 右侧场景区 | 待机、预检、执行、确认、报警、完整状态等场景页 |

代码依据：

- `operator_ui_mixin.py::_build_operator_page()` 已创建 `idle/precheck/execute/confirm/alarm/query` 六类场景。
- `operator_ui_mixin.py::_build_operator_status_bar()` 已实现左侧状态与快捷操作。
- `operator_ui_mixin.py::_build_operator_dialog_panel()` 已实现用户输入与对话区域。
- `operator_ui_mixin.py::_build_operator_right_sidebar()` 已实现右侧场景和快捷按钮。

### 2.2 状态展示已实现基础版本

用户页面已经显示：

- 总体状态：空闲、运行中、暂停、异常、离线。
- 安全状态：急停、暂停、报警三个徽标。
- 实时位置：J1-J6 关节值，X/Y/Z/RX/RY/RZ 位姿值。
- 当前任务：空闲、自然语言预检、自然语言动作序列、流程步骤、控制器执行中。

重 UI 状态刷新由 `operator_refresh_timer` 驱动，默认周期为 500ms；看板快照由独立 `operator_dashboard_timer` 驱动，默认周期为 50ms。实时数据来源于 `ControllerRuntimeMixin._poll_feedback_silent()`，控制器轮询默认周期为 500ms。

这里还有一个实现风险：用户页刷新定时器和控制器轮询定时器是两个独立 `QTimer`，启动时间和触发相位不保证一致。用户页可能在轮询更新前读取上一轮属性，最坏情况下可见数据滞后接近 500ms（上一轮数据）+ 500ms（下一轮 UI 刷新），约 1 秒。这不只是“不满足 50ms”的问题，也会影响语言查询回答的新鲜度判断。

这说明“用户页有状态展示”和“50ms 看板快照刷新”已经成立。当前已补实时反馈新鲜度标记，能区分 `online/stale/offline`；控制器采集也已具备分组骨架，配置为 50ms 时只会高频读取关节/位姿，状态/报警仍保持低频。

### 2.3 场景页 UI 已实现

当前已经存在以下场景页：

| 场景 | 当前状态 |
|---|---|
| 待机场景 | 已实现，显示系统在线与最近操作 |
| 预检场景 | 已实现 UI，显示检查项和进度条 |
| 执行场景 | 已实现 UI，显示执行详情、估算进度、当前位置 |
| 安全确认场景 | 已实现 UI，包含确认执行、采纳建议、取消 |
| 报警场景 | 已实现 UI，显示报警详情和复位按钮 |
| 完整状态场景 | 已实现 UI，显示“七类看板”样式的完整状态 |

需要注意：这些场景多数是 UI 骨架或状态推断展示，并不是严格按照 V2.1 的状态机和真实预检/预演结果驱动。
例如预检场景当前主要把检查项文案从“等待”切换到“进行中”，还没有由真实 L1/L2/L3 检查结果逐项驱动。

### 2.4 完整状态页已实现“展示版七类看板”

`_refresh_operator_full_status()` 已经拼装了 7 个 HTML 分区：

1. 看板1 设备健康状态
2. 看板2 位置与运动状态
3. 看板3 当前执行
4. 看板4 报警与安全
5. 看板5 工艺流程预演/执行进度
6. 看板6 安全参数
7. 看板7 对话与最近操作

这可以认为是“七类看板的用户页展示雏形”。2026-05-20 后已新增 `DashboardCache`，完整状态页的部分核心数据会优先读取看板快照；2026-05-21 后看板快照已能标记实时反馈新鲜度，并补入 MPOS/DPOS、AXISSTATUS、MOTIONTYPE。但这些数据底层仍需要真机验证，不具备完整字段覆盖和看板变化事件能力。

实现上已有一个基本优化：`_refresh_operator_full_status()` 会比较新旧 HTML 文本，未变化时不调用 `setHtml()`。但每 500ms 仍会重建完整 HTML 字符串；完整状态页打开时，需要后续评估低配置工控机上的 CPU 开销和滚动位置稳定性。

### 2.5 自然语言输入入口已实现

用户页面支持：

- 文本输入自然语言。
- “解析”按钮调用 NLP 解析。
- “执行”按钮解析并执行。
- 与工程师页 NLP 输入框同步。
- 对话气泡展示用户输入和系统回应。

底层使用：

- `NlpMixin`
- `VoiceNlpAdapter`
- 本地规则解析
- 可选 DeepSeek 解析
- 模板、流程、系统命令三类动作计划

当前语义能力更接近 `template / flow / system / unknown` 四类动作路由，还不是 V2.1 要求的 L1-L5 五级语义体系。

### 2.6 主要用户页按钮语音等价指令已实现

`_handle_operator_ui_command()` 已经支持一批界面语音/文本等价命令：

| 命令类型 | 已支持示例 |
|---|---|
| 安全确认 | 确认执行、确认、执行确认 |
| 建议处理 | 采纳建议、采用建议、接受建议 |
| 取消 | 取消、取消执行、取消计划 |
| 页面切换 | 用户页面、工程师页面 |
| 状态查看 | 显示完整状态、状态看板、七类看板 |
| 界面模式 | 全屏、放大界面、小窗口、缩小界面 |
| 记录滚动 | 上一条、下一条 |
| 安全参数 | 显示安全参数 |
| 系统控制 | 急停、暂停、继续、恢复、复位、报警复位 |
| 流程控制 | 停止流程、停止当前流程 |

因此，对方 AI 评审中“全语音控制完全缺失”“全屏/小窗口模式缺失”的说法需要修正：当前用户页主要按钮已经有集中规范表和基础实现，普通界面语音命令也已开始复用同一匹配入口。

但当前实现还不是“界面上一切按钮都可直接语音执行”。工程师页固定按钮已补 `engineer_voice_commands.py` 规范表，并生成 `docs/工程师页语音等价指令清单.md`；清单已标明“可直接语音执行 / 需二次确认 / 拒绝语音执行 / 仅清单保留”。当前已接入低风险工程师页语音动作，例如切换运行/后台/日志、打开系统参数/流程管理、读取反馈、刷新麦克风和刷新日志。`confirm` 级工程师动作已接入二次确认队列，例如保存系统配置、保存模板、保存流程等需要再说“确认工程师操作”才会执行；确认超时会取消待执行动作，新确认动作覆盖旧动作会写审计日志；也可查询“当前待确认后台操作是什么”。`danger/emergency` 级删除、清空日志、急停仍拒绝语音直接执行，但拒绝会进入语言回应/播报链路；急停文本优先进入独立应急通道。“仅清单保留”动作也会明确提示当前版本未接入执行，不再静默。工程师语音操作也已写入类型 B `interaction_record`，可追溯低风险执行、等待确认、确认、取消、超时、拒绝和未接入。用户也可以直接询问“现在语音能控制哪些工程师操作”，系统会按四类执行策略汇总回答。安全参数分层读写已新增 `param_manager.py` 和 `docs/系统参数分层读写清单.md`，AI 优化器只能写可优化区。复杂建议参数改写等还没有完整覆盖；完整状态内部七类查询已先整理为 `docs/用户页完整状态查询清单.md`。

### 2.7 全屏和小窗口模式已实现

用户页面已支持：

- 小窗口模式：`_operator_toggle_compact()`
- 全屏模式：`_operator_show_fullscreen()`
- 普通窗口恢复：`_operator_restore_normal_window()`
- 对应语音/文本命令：“全屏”“放大界面”“小窗口”“缩小界面”“退出全屏”“恢复窗口”

这部分已经超过“完全未实现”的状态，但还需要做现场显示适配和状态持久化验证。

当前小窗口尺寸为代码内固定值，尚未根据分辨率、任务栏位置或用户配置自适应。另一个交互细节是：“全屏”命令调用的是切换式逻辑，如果当前已经全屏，再说“全屏”会恢复普通窗口；这和用户预期可能不一致，后续应拆成“进入全屏”和“退出全屏”两个明确语义。

### 2.8 安全确认 UI 已实现，但业务闭环不足

当前确认页有：

- 确认执行
- 采纳建议
- 取消

`_operator_confirm_execute()` 会把待确认计划交给 `_execute_nlp_plan()` 执行。  
`_operator_accept_suggestion()` 目前只是提示“当前版本暂无参数改写建议，按原计划执行”，并没有真正根据风险项生成或应用建议参数。

所以它是“确认 UI 已实现，风险建议闭环未实现”。

## 三、部分实现但未达到 V2.1 标准的内容

### 3.1 状态刷新有了，但不是 50ms 看板

当前：

- 用户页重 UI 刷新周期：默认 500ms，可配置。
- 用户页看板快照刷新周期：默认 50ms，可配置。
- 控制器实时轮询周期：默认 500ms，可配置；内部已分成 `realtime_feedback` 和 `status_detail` 两组。
- 完整状态页优先从 `DashboardCache` 快照读取核心字段。

V2.1 要求：

- 七类看板独立内存缓存
- 核心状态 50ms 刷新
- 简单查询从缓存直接回答
- 状态变化触发主动播报

差距：当前已有 50ms 看板快照层和控制器分组轮询骨架，但默认配置仍是 500ms 控制器采集；还没有经过真机验证来证明 50ms 核心反馈读取不会造成总线压力或 UI 卡顿。
补充：当前已能通过 `_last_feedback_monotonic_sec` 计算反馈数据年龄，并在看板中暴露 `feedback_fresh`。这解决的是“过期可见”，不是“50ms 数据源已完成”。

### 3.2 预检场景有 UI，但没有真实 L1/L2/L3 预检流程

当前预检场景在 NLP 解析时显示：

- 指令接收：已收到
- 设备状态检查：进行中
- 安全参数检查：等待
- 运动规划预演：等待

原先这只是界面状态展示。2026-05-20 已新增 `SafetyPrecheckService` 并接入用户页解析后的可执行计划，能执行基础 L1 检查，包括急停、报警、暂停、连接、实时反馈、通道占用、当前 R/Z、目标 X/Y/Z 软限位、速度/加速度/减速度上限。

但这仍不是完整 L1/L2/L3 体系。FSTATUS 遍历、奇异点检测、运动规划预演、流程时序模拟、风险建议参数改写等还没有接入用户页。

### 3.3 场景切换有了，但不是严格状态机

当前 `_operator_desired_scene()` 会根据报警、待确认计划、NLP 解析中、NLP 执行中、控制器运行中等状态推断场景。

这比静态页面更进一步，但仍不是 V2.1 的完整状态机：

```text
待机 -> 预检 -> 安全确认/执行 -> 待机
任意状态 -> 报警 -> 待机
```

缺少明确的状态对象、事件流、状态切换日志、语音同步播报和异常恢复规则。

具体风险包括：

- 场景由多个属性即时推断，属性来自不同回调和定时器，可能短暂出现不一致。例如解析刚结束但待确认计划尚未写入时，页面可能从预检短暂跳回待机，再进入确认。
- 2026-05-21 已补第一版报警场景记忆：进入报警时保存报警前场景，报警清除后可一次性回到报警前场景。但整体仍不是完整显式状态机。
- 从执行回到待机只更新界面，不会自动形成“执行完成，当前位置为...”这类 V2.1 要求的语言同步播报。

### 3.4 语音输入有了，但没有 VAD 即时回执

当前已有讯飞语音识别和录音按钮，用户页可以触发录音。

但 V2.1 要求语音输入在 VAD 触发后 ≤200ms 回执“系统在线，正在识别”。当前录音链路更接近“开始录音 -> 停止录音 -> 等待识别结果”，没有实时 VAD 回执和不中断监听式交互。

### 3.5 自然语言解析已有五级语义元数据基础版

当前 `VoiceNlpAdapter` 支持：

- 模板动作
- 流程动作
- 系统动作
- unknown
- 可选 DeepSeek 解析并经本地白名单校验

V2.1 要求：

- L1 闲聊咨询
- L2 工艺查询
- L3 常规生产执行
- L4 系统管理
- L5 应急安全

当前已新增 `VoiceNlpPlan.semantic_level/semantic_label/response_deadline_ms/requires_precheck/requires_confirmation/priority`，基础映射为：L1 闲聊咨询、L2 看板/工艺查询、L3 模板/流程生产执行、L4 普通系统管理、L5 三段式应急安全。类型 A `command_intent` 会优先使用该层级字段。`semantic_response_policy.py` 已把 L1~L5 的 `ack_limit_ms/result_deadline_ms/progress_interval_ms/requires_precheck/requires_confirmation/emergency_fast_path/priority` 集中成策略表，用户页归档会写入策略结果。L2 查询计划会由用户页从 `DashboardCache` 快照回答，并切换到查询场景，不进入安全确认或执行链路。用户页确认/预检分支也已开始读取策略：L3 模板/流程强制预检和安全确认；L4 系统管理按动作细分，暂停、继续、取消当前任务直接执行，报警复位进入确认；L5 保持应急快路径。`_execute_nlp_plan()` 入口已增加待确认计划闸门，防止父级 NLP 执行调用绕过确认页。

仍未完整达到 V2.1 标准：L2 目前是看板查询和基础解释问答版，还没有覆盖全部工艺知识问答；层级响应策略已开始驱动用户页确认/预检分支，但还没有完全驱动所有后台调度分支；`jieba` 分词层已经可选接入，但还没有形成完整的“jieba 分词结果驱动候选召回 + 规则确认 + DeepSeek 兜底”三级分类流水线。

## 四、用户页面尚未实现的关键能力

### 4.1 即时回应体系已有基础，完整 VAD 与复杂进度仍未完成

V2.1 把“即时回应”定义为系统生命线。当前用户页已经从“只有解析开始提示”推进到基础回执验收阶段：文本输入会立即发布“收到，正在解析指令。”并归档 `ack_delay_ms/ack_limit_ms/ack_sla_passed`；语音录音启动会记录 200ms 回执 SLA；三段式应急编码命中路径会绕过普通 NLP 等待，直接发布高优先级回执并记录 30ms SLA。

已实现：

- 文字输入 ≤50ms 回执字段与验收测试。
- 语音录音启动 ≤200ms 回执字段与验收测试。
- 应急编码命中 ≤30ms 快路径回执字段与验收测试。
- 回执、进度、结果、告警四类 `ResponseMessage` 框架。
- 预检前设备/通讯状态安抚回应。
- L1/L2/预检完成阶段性进度回应。
- L2 运动规划预演细粒度进度基础版：开始、FSTATUS 遍历、候选评分、奇异点检查和完成事件已进入 Qt 预检进度条与播报队列。
- L3 流程级预演阶段进度基础版：模板完整性、逐步 L1/L2、时序、累计误差、简化干涉和完成事件已进入 Qt 预检进度条与播报队列。
- 执行/暂停/流程运行期间的周期性安抚回应基础版，默认 2 秒节流。
- 执行场景进度估算基础版：优先控制器百分比，其次流程步数/自然语言动作序号，最后运行中保守显示 50%。

仍缺少：

- 真正基于 VAD 的语音起点回执；当前是录音启动回执，不是实时 VAD 事件。
- 异步长任务进度、控制器真实执行百分比覆盖率和真机现场耗时验收。
- 现场硬件环境下的响应时延验收。

### 4.2 主动播报已接入第一版，TTS 可配置启用

当前状态变化会刷新 UI、写日志，并且系统命令、应急编码校验、反馈报警变化、连接失败、L1/L2 拒绝、自然语言动作完成/终止、用户页停止当前任务、无任务可停提示、报警确认、流程完成/失败、六轴执行完成/完成伴随报警等关键事件已经可以转换为语言层面的主动通知进入播报队列和对话区。第一版去重已经接入：`ResponseBuilder.from_log_entry()` 会生成稳定 `context_id`，`BroadcastQueue.publish_once()` 会按 `dedupe_key` 在时间窗口内抑制重复播报。第一版优先级消费也已接入：`BroadcastQueue.messages_since_for_delivery()` 会让 `high` 消息优先于普通消息，用户页可通过 `_operator_pending_broadcasts_for_delivery()` 读取后续 TTS 待播报列表，并可通过 `_operator_consume_pending_broadcasts_for_delivery()` 用独立游标确认消费。2026-05-20 已新增 `speech_broadcast.py`，提供可注入语音输出接口和可选 `pyttsx3` 本地 TTS 适配；用户页已有 `_operator_enable_local_tts()` 与 `_operator_deliver_pending_broadcasts_to_speech()`，失败时不推进游标，后续可重试。配置层已新增 `operator_tts_enabled`、`broadcast_dedupe_window_sec`、`tts_retry_delay_sec` 和 `tts_max_failures`。用户页构建时会按配置启用 TTS，并通过 1000ms 定时器自动投递待播报消息；右侧快捷区也已有“语音播报”开关，切换后会保存配置。工程师后台系统参数页已补齐 TTS 开关、播报去重窗口、TTS 重试间隔、最大连续失败次数、L3 最小步间隔和累计误差上限字段；后台保存后会同步用户页语音播报开关。自动投递失败后会按指数退避重试，连续失败达到上限后自动暂停 TTS。看板变化事件也已扩展：实时反馈 stale 会提示过期毫秒数，轴状态异常会播报当前轴状态，动作完成会播报函数、结果和当前位置摘要。

缺少：

- 部署环境的 `pyttsx3` 安装与发声设备验证。
- 自动暂停后的故障说明弹窗和恢复引导。
- 禁入包围盒仍主要通过 JSON 配置维护，暂未提供结构化表格编辑器。
- 更多细分事件源，例如并行流程步骤失败、通讯恢复后的健康摘要、驱动器详细故障恢复。

原有阻断点已修正：`_operator_add_chat_from_log()` 不再只处理 `category == "自然语言"` 的日志，系统、应急、反馈类日志现在可以通过 `ResponseBuilder.from_log_entry()` 进入主动播报链路。

### 4.3 三段式应急编码未实现

这是当前用户页最需要优先修正的安全问题之一。2026-05-20 已完成第一步修正：新增 `EmergencyChannel`，单独“急停/紧急停止”不再直接触发 `sys_estop`，三段式“急停 授权码 急停”通过后才会返回系统急停动作。2026-05-21 已补应急快路径回执，授权命中和无效编码都会先发布明确语言回应，再进入后续系统动作或拒绝分支。

原先 `"急停"` 或 `"紧急停止"` 会直接触发 `sys_estop`。这与 V2.1 “单独提及关键词不触发动作，必须三段式授权编码”的要求冲突。

同时，用户页左侧快捷“急停”按钮也直接绑定 `sys_estop`。这不一定错误，因为按钮急停可能本来就应作为上位机快速安全入口；但它需要在设计上明确：语音急停是否必须三段式授权，界面按钮急停是否直接执行，二者是否走同一个安全审计和回执链路。当前文档和代码还没有把这个边界说清楚。

缺少：

- 授权编码的现场配置治理和权限管理。
- 硬件/线程级独立应急通道；当前是用户页文本处理里的快路径，不等于脱离普通 GUI 事件循环。
- 编码命中 ≤30ms 的现场实测；单元测试已覆盖本地快路径字段。

### 4.4 独立七类看板缓存仍未完整实现

用户页有“七类看板展示”，并已新增 `DashboardCache` 作为第一版看板快照缓存。但它还没有达到 V2.1 要求的独立七类看板系统。

缺少：

- 七类看板的完整字段覆盖。
- 50ms 分组轮询的真机验证、压测和默认策略确认。
- 七类看板字段仍需继续扩充，例如 ECAT/驱动器详细故障、更多速度/加减速实时值、流程级绕行建议状态。
- 查询接口已有第一版，能回答通讯、状态、安全边界、执行可行性、运动极限、流程预演和工艺适配；还需要扩充更细的字段问答。
- 看板变化事件：供主动播报使用。
- Web/API/HTML 页面接口本阶段不纳入验收范围。

### 4.5 安全预检和运动预演未接入用户页

已有进展：`WebPrecheckService.run_l1()` 已迁移为委托 Qt/Web 共用的 `SafetyPrecheckService`。Qt 用户页解析到可执行计划后会运行基础 L1 检查，并在预检场景和确认页中展示结果。
L2 方面已新增 `KinematicsEngine` 接口和 `MotionPlanService` 骨架，可在注入逆解引擎后执行 FSTATUS 候选选择和 J4 奇异阈值检查；未配置逆解引擎时会返回 `unavailable`，不会误报通过。用户页已把当前 `robot_x/y/z/r` 位姿作为起点、模板目标位姿作为终点传入 L2 服务，并已将 L2 失败结果接入确认执行门禁。当前已补中点绕行建议骨架：当直线路径触发奇异风险且可找到 RY 偏移中点时，L2 结果会返回 `need_midpoint/midpoint_pose/midpoint_fstatus`，用户页摘要会展示建议中点，直接执行仍保持阻断，等待采纳绕行建议。
`FrameTrans2KinematicsEngine` 已按 V2.1 文档的推荐方式预留：写 `TABLE(550~556)`，执行 `FRAME_TRANS2(550,560,2)`，读 `TABLE(560~565)`。`ZMotionVrClient` 已补 `set_table/get_table/execute` 窄接口，但还未经过真机联调验证。
L3 方面已新增 `ProcessPrecheckService`，用户页解析到 `flow` 动作后会运行第一版流程级预演：检查流程步骤模板完整性，逐步调用 L1/L2，L1/L2 失败会阻断确认执行，L2 不可用只作为警告。现已补充可配置的流程步间隔状态机模拟、累计误差预算和简化禁入包围盒检查；当某个流程步骤的 L2 返回 `need_midpoint=True` 时，L3 会汇总步骤序号、模板 key、中点位姿和 FSTATUS，并在用户页 L3 摘要中提示流程级中点绕行建议。这些仍是保守骨架，不等于完整动力学/碰撞级仿真。

缺少：

- 风险项解释和建议生成。
- 真实控制器 `FRAME_TRANS2` 正逆解调用的真机验证。
- 更完整的路径预演；当前只有基于逆解的 5 点插值 J4 奇异阈值骨架。
- 真机级中点绕行策略验证；当前已有单动作和流程级纯逻辑建议骨架，但未经过控制器路径执行验证。
- 完整 L3 流程级预演；当前已有时序、累计误差、简化干涉和流程级中点建议骨架，但还没有真实仿真级验证。

### 4.6 安全确认建议闭环已有基础实现

原先确认页可以确认/取消，但“采纳建议”没有真实参数改写能力。2026-05-20 已新增第一版保守建议闭环：当 L1 发现目标 X/Y/Z 软限位或速度/加速度/减速度超限时，`SafetySuggestionService` 会把参数夹回配置边界；用户点击“采纳建议”后，用户页会生成临时模板记录、重跑 L1，通过后才继续执行。
2026-05-22 已补确认闭环一致性：确认执行、确认超时、采纳建议和取消确认都会同步更新状态栏、用户对话区、日志和类型 B `interaction_record`。报警恢复场景也已补保护，报警解除后只恢复仍然有效的上一个场景，避免执行已结束后误回到“执行中”。

缺少：

- 更复杂风险项的结构化展示。
- FSTATUS、奇异点相关建议的真机级验证；当前已有 L2 中点绕行建议骨架，但还没有控制器路径执行验证。

### 4.7 标准 JSON 数据结构已有基础归档

用户页当前仍主要依赖 Qt 字段、日志和 `VoiceNlpPlan`。已新增 `json_schema.py`，提供 V2.1 类型 A/B/C 数据结构和基础字段校验；已新增 `command_intent_adapter.py`，可把现有 `VoiceNlpPlan` 转为类型 A `command_intent`；已新增 `interaction_archiver.py`，用户页文本提交时会写入类型 B `interaction_record` JSONL，并在 NLP 解析、L1/L2/L3 预检、确认执行阻断/接受、主动取消确认、看板/工艺查询回答、忙碌拒绝新动作、自然语言/流程/六轴/系统关键执行日志时按同一 `msg_id` 回填关键字段。文本交互归档已包含当前场景状态 `input.scene_state`，可审计交互发生时的场景、上一个场景和切换原因；`response` 字段已回填回执文本、`ack_delay_ms`、`ack_limit_ms`、`ack_sla_passed`、最终响应和 `final_delay_ms`；语音识别成功日志会写入 `source=voice` 的记录并保存 `asr_confidence`；执行日志中的 `command_snapshot.writes` 会进入 `execution.modbus_write`，`state_before/state_after` 会分别写入交互输入时和执行结果回填时的设备快照；`exec_duration_ms` 会根据准备/完成日志的 `monotonic_ms` 差值计算，且发送失败/系统命令失败等异常分支不会被后续自然语言终止日志清零。本阶段先不关注 Web API / HTML 页面接口。

缺少：

- 结合真机日志验证少数边界条件。
- 类型 C `device_snapshot` 已开始对齐 50ms 看板快照，包含 MPOS/DPOS、AXISSTATUS、MOTIONTYPE；仍需补更多控制器诊断字段和真机边界验证。

## 七、最终判断

用户页面当前已经完成“可操作的 UI 原型 + 部分自然语言入口 + 状态展示”的阶段，不能再简单判定为页面未做。

但它还不是 V2.1 定义的完整自然语言交互系统。下一阶段重点不应继续堆界面控件，而应补齐用户页背后的四个基础设施：

1. 即时回应与进度播报框架。基础回执、预检安抚、L2/L3 预演阶段进度、运行期周期安抚和执行进度估算已完成，下一步重点是真实 VAD、控制器真实百分比覆盖率和现场耗时验收。
2. 独立七类看板缓存。
3. 三段式应急安全通道。
4. L1/L2/L3 预检预演服务。

这四项完成后，用户页面才真正具备替代 HMI 信息传递的基础。
