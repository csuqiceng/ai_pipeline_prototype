六轴机械手 — 指令缓冲机制与回显容错说明
版本: V1.0
日期: 2026-05-14
适用: 上位机程序开发

==========================================================
一、指令缓冲机制概述
==========================================================

控制器内部采用"调度器+缓冲区"架构，上位机发送的指令经调度器
统一接收后，按优先级分发到不同缓冲区，由对应任务消费执行。

1.1 三个缓冲区

  缓冲区        处理的函数           深度   满时策略
  ──────────   ──────────────────   ────   ──────────────
  stop缓冲区    Func104(急停/复位)    无限   覆盖（最新生效）
  parallel缓冲区 Func110/120(延时/IO)  1深   拒绝+写指令忙
  motion缓冲区  106/107/108/109/11等   1深   拒绝+写指令忙

1.2 缓冲区满的标志

  当parallel或motion缓冲区已满（有指令等待执行），新指令被拒绝时：
  控制器写入 LONG(38) 的 bit2（指令忙标志），掩码 = 0x04

  上位机检测方法：
    读LONG(38)，如果 (LONG(38) AND 0x04) <> 0，表示指令被拒绝

1.3 各缓冲区行为详解

  ┌─────────────────────────────────────────────────────────┐
  │ stop缓冲区（Func104 急停/复位）                          │
  │                                                         │
  │ 特点：覆盖式，永远不满                                    │
  │ 行为：新指令覆盖旧指令，最新参数生效                        │
  │ 原因：急停是安全指令，必须能随时下发，不能被拒绝             │
  │                                                         │
  │ 示例：                                                   │
  │   急停中 → 上位机发复位 → 覆盖急停参数 → 执行复位          │
  │   急停中 → 上位机再发急停 → 覆盖 → 仍是急停（无影响）       │
  └─────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────┐
  │ parallel缓冲区（Func110 T1延时 / Func120 IO输出）        │
  │                                                         │
  │ 特点：1深缓冲，满了拒绝                                   │
  │ 行为：缓冲区有指令时，新指令被拒绝，写LONG(38) bit2=1      │
  │ 特殊：Func110执行中可以更新延时时间（覆盖式更新）           │
  │                                                         │
  │ 示例：                                                   │
  │   Func110执行中 → 上位机发Func110更新延时 → 成功更新       │
  │   Func110执行中 → 上位机发Func120 → 被拒绝（缓冲区满）     │
  │   Func110完成 → 缓冲区空 → 上位机发Func120 → 成功         │
  └─────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────┐
  │ motion缓冲区（Func106/107/108/109/11等运动函数）          │
  │                                                         │
  │ 特点：1深缓冲，满了拒绝                                   │
  │ 行为：缓冲区有指令时，新指令被拒绝，写LONG(38) bit2=1      │
  │                                                         │
  │ 示例：                                                   │
  │   Func108执行中 → 上位机发Func106 → 被拒绝（缓冲区满）     │
  │   Func108完成 → 缓冲区空 → 上位机发Func106 → 成功         │
  │   Func108执行中 → 上位机发Func104急停 → 成功（stop独立）   │
  └─────────────────────────────────────────────────────────┘

1.4 缓冲区满时上位机的处理

  当检测到 LONG(38) bit2 = 1（指令忙）时：

  注意：上位机应优先通过本地前置检查避免在同slot执行中重复下发。
  若本地前置检查已判断slot未就绪并拒绝发送，则控制器不会产生新的
  LONG(38) bit2，本节自动恢复流程不触发。
  本节适用于控制器已接收并明确返回 LONG(38).02 指令忙的场景
  （例如状态竞态、外部HMI/其他上位机并发写入等）。

  步骤1：等待当前函数完成
    读LONG(34)，等待对应函数位变为DONE(10)或ERR(11)

  步骤2：清除报警码
    如果LONG(38) bit2仍为1，发送Func104报警复位：
    IEEE(0)=104, IEEE(8)=1, IEEE(32)=1

  步骤3：重新发送被拒绝的指令
    按正常七步握手流程重新发送

  ⚠️ 不要连续重发！等待至少100ms再重试，避免频繁触发被反复拒绝。

==========================================================
二、回显机制与容错处理
==========================================================

2.1 回显机制说明

  控制器调度器（task_dispatch.bas）以1ms周期持续将
  IEEE(0~30)的值镜像到回显区IEEE(280~312)：

    IEEE(280) = IEEE(0)       函数号回显
    IEEE(282) = IEEE(2)       参数0回显
    IEEE(284) = IEEE(4)       参数1回显
    ...以此类推...
    IEEE(312) = 触发标志回显
    IEEE(324) = IEEE(0)       当前函数号

  上位机写完参数后，读回显区验证参数是否正确写入控制器。

2.2 回显时序问题

  由于上位机写参数和控制器更新回显之间存在时间差，
  可能出现"刚写完就读，回显还是旧值"的情况。

  典型场景：
    t0: 上位机写 IEEE(0)=104, IEEE(2)=1（急停）
    t1: 上位机读 IEEE(280) → 可能还是旧函数号（如108）
    t2: 上位机认为写入失败，不写触发位

  时间差通常在1~5ms之间。

2.3 回显容错机制（上位机必须实现！）

  ┌─────────────────────────────────────────────────────────┐
  │ 回显验证容错规则：                                        │
  │                                                         │
  │ ① 读回显后不匹配 → 等待5ms → 重读回显                    │
  │ ② 最多重试3次（总等待约15ms）                             │
  │ ③ 3次都不匹配 → 认为写入失败 → 重新写参数                 │
  │ ④ 重写参数最多2轮                                        │
  │ ⑤ 2轮后仍失败 → 通讯异常，提示用户                        │
  └─────────────────────────────────────────────────────────┘

  伪代码：
    def writeAndVerify(addr_value_map, max_retries=3):
        for write_round in range(2):        # 最多重写2轮
            # 写入参数
            for addr, value in addr_value_map:
                write_IEEE(addr, value)

            # 验证回显
            for retry in range(max_retries):
                delay_ms(5)                 # 等待5ms
                all_match = True
                for addr, value in addr_value_map:
                    echo_addr = 280 + addr  # 回显地址映射
                    echo_val = read_IEEE(echo_addr)
                    if abs(echo_val - value) > 0.001:  # 浮点比较用误差范围
                        all_match = False
                        break
                if all_match:
                    return SUCCESS          # 回显匹配，可以触发

            # 回显3次都不匹配，重新写参数

        return FAIL                         # 2轮都失败

2.4 浮点数回显比较注意事项

  MODBUS_IEEE是32位浮点数，精度约7位有效数字。
  回显值与写入值之间可能有微小误差。

  ⚠️ 不要用精确相等(==)比较浮点数！
  ✅ 用误差范围比较：|回显值 - 写入值| < 0.001

  示例：
    写入: IEEE(2) = 1.0
    回显: IEEE(282) = 0.9999999
    判断: |0.9999999 - 1.0| < 0.001 → 匹配 ✅

2.5 急停指令的回显特殊性

  急停场景下，上位机可能快速连续发送多条Func104指令
  （急停→解除急停→复位），每条指令的参数不同。

  此时回显区会快速变化，可能出现：
    写IEEE(2)=1（急停）→ 读回显IEEE(282)=2（上一条是解除急停）

  处理方式：
  - 按上述容错规则重试
  - 如果重试后回显与最新写入值匹配，正常触发
  - 如果重试后回显与最新写入值不匹配，但与更早的值匹配，
    说明控制器正在处理前一条指令，等待前一条完成后再重试

2.6 回显验证失败不等于指令未写入

  重要认知：回显验证失败 ≠ 参数没写入控制器

  控制器的MODBUS寄存器是实时更新的，上位机写入后
  参数已经在控制器内存中。回显区只是镜像，有1~5ms延迟。

  所以即使回显验证失败，参数大概率已经写入成功。
  但为了安全起见，不建议跳过回显验证直接触发（除非常规
  容错机制确认通讯正常的情况下）。

三、完整发送流程（含容错）
==========================================================

3.1 运动函数发送流程（含缓冲区满检测和回显容错）

  ┌─────────────────────────────────────────────────────────┐
  │ 步骤1：检查前置条件                                      │
  │   读LONG(34)                                            │
  │   ① 对应函数位 = 00(空闲) 或 10(完成)                    │
  │   ② 34.24 = 0（无报警）                                  │
  │   ③ 34.25 = 0（未急停）                                  │
  │   ④ 34.28 = 1（系统就绪）                                │
  ├─────────────────────────────────────────────────────────┤
  │ 步骤2：写入函数号和参数                                    │
  │   写 IEEE(0) = 函数号                                    │
  │   写 IEEE(2)~IEEE(30) = 参数                             │
  ├─────────────────────────────────────────────────────────┤
  │ 步骤3：读回显校验（含容错）                               │
  │   读 IEEE(280~312)                                       │
  │   不匹配 → 等5ms重读，最多3次                             │
  │   3次不匹配 → 重新写参数，最多2轮                         │
  │   2轮失败 → 通讯异常提示                                  │
  ├─────────────────────────────────────────────────────────┤
  │ 步骤4：触发执行                                          │
  │   写 IEEE(32) = 1                                       │
  ├─────────────────────────────────────────────────────────┤
  │ 步骤5：等待完成                                          │
  │   循环读LONG(34)，间隔50ms                                │
  │   函数位 = 01(EXEC) → 继续等待                            │
  │   函数位 = 10(DONE) → 执行成功                            │
  │   函数位 = 11(ERR)  → 读LONG(38)查报警码                  │
  │     如果LONG(38) bit2=1（指令忙）→ 等待后重试              │
  ├─────────────────────────────────────────────────────────┤
  │ 步骤6：处理指令忙（LONG(38) bit2=1）                      │
  │   ① 等待当前函数完成（LONG(34)函数位=DONE）               │
  │   ② 发送Func104报警复位清除LONG(38)                       │
  │   ③ 等待34.28=1(就绪), 34.24=0(无报警)                   │
  │   ④ 从步骤1重新开始                                      │
  └─────────────────────────────────────────────────────────┘

3.2 急停函数（Func104）发送流程

  与运动函数流程相同，但注意：
  - Func104不受缓冲区满限制（stop缓冲区覆盖式）
  - 任何状态下都可以触发
  - 回显验证同样需要容错机制
  - 快速连续发送时（急停→解除→复位），每条都要等回显确认

==========================================================
四、LONG(38)报警码速查
==========================================================

  位号    掩码    含义                    上位机处理
  ──────  ──────  ──────────────────      ──────────────────
  38.00   0x01    半径超限                 修改目标位置
  38.01   0x02    高度超限                 修改目标位置
  38.02   0x04    指令忙（缓冲区满）       等待完成后重试
  38.03   0x08    速度超限                 降低速度百分比
  38.04   0x10    加速度超限               降低加速度百分比
  38.05   0x20    减速度超限               降低减速度百分比
  38.06   0x40    EtherCAT通讯故障         检查硬件连接
  38.07   0x80    驱动器报警               检查驱动器状态
  38.08   0x100   函数号非法               检查函数号
  38.09   0x200   参数非法                 检查参数范围

  ⚠️ 指令忙(0x04)是唯一可以通过"等待+重试"自行恢复的报警。
  其他报警需要发送Func104复位后才能继续操作。
