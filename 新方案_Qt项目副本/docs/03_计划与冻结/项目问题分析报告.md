## 1. 优先处理项

### 问题 1：每次操作都创建新连接，无连接复用  ✅ 已修复

**位置**: `qt_gui.py` — `_read_feedback_once()` (行 2833), `_read_realtime_once()` (行 2849), `_execute_query_key()` (行 2335), `_make_client()` (行 2759)

**现象**: 每次轮询、每次发送指令、每次读取反馈都会 `client = self._make_client(host); client.connect(); ... client.disconnect()`。

```python
def _read_feedback_once(self) -> tuple[list[float], VrReadRequest]:
    host = self.host_edit.text().strip()
    client = self._make_client(host)  # 每次新建
    client.connect()                   # 每次重连
    try:
        ...
    finally:
        client.disconnect()            # 每次断开
```

**影响**:
- 轮询定时器每 500ms 执行一次，每次都重新连接/断开
- 标准协议模式下，一次轮询要连接 2 次（status + monitor）
- 对真实控制器：`ZAux_OpenEth` 是 TCP 连接建立，频繁连接/断开会导致延迟、端口耗尽、控制器拒绝连接
- 与问题 8（SDK 反复加载改 CWD/PATH）叠加后更严重

**建议修复**: 维护一个持久连接的 client 实例，在连接断开或切换控制器类型时重新创建。

**修复方式（2026-04-12）**: 新增 `_get_client(host)` 缓存连接复用，`_disconnect_client()` 清理缓存。host 变化或连接失败时自动重建。新增 `closeEvent` 清理。用 `_client_cache_lock` 保护缓存生命周期。

### 问题 2：系统命令缺少执行完成等待  ✅ 已修复

**位置**: `qt_gui.py:2607-2638` — `_handle_system_action()`

**现象**: 系统按钮（上电/启动/停机/暂停/继续/急停）在标准协议模式下，已经走了完整的镜像确认 + 执行触发流程（`write_vr` → `read_vr` 镜像 → `_wait_for_mirror_match` → `write_vr` 执行触发），但**最后一步只读了一次反馈就结束**，没有像普通指令那样调用 `_wait_for_execution_complete()` 等待控制器真正执行完毕：

```python
# 普通指令（行 2468）有完整的等待流程
values = self._wait_for_execution_complete(client, read_request, record.query_key)

# 系统命令（行 2638）执行触发后只读了一次反馈，没有等待执行完成
feedback = client.read_vr(read_request)
```

注意：问题不是系统命令没走标准协议，而是走完镜像确认和执行触发后，缺少对执行结果的等待确认。

**影响**: 系统命令发送后，可能读到的是上一次的执行状态，而不是当前命令的执行结果。特别是急停（4002）等关键命令，如果读到旧状态，可能导致急停未真正生效的误判。

**建议修复**: 为系统命令也增加 `_wait_for_execution_complete` 调用，或至少在发送后增加短暂延时再读取。

**修复方式（2026-04-12）**: `_handle_system_action` 中执行触发写入后的单次 `read_vr` 替换为 `_wait_for_execution_complete`。

### 问题 7：轮询与手动操作之间的竞态条件  ✅ 已修复

**位置**: `qt_gui.py:2774-2830`

**现象**: `_poll_feedback_silent` 通过 `_polling_feedback` 标志防止重入，但 `_execute_query_key` 发送指令时没有检查或等待轮询完成。两者可能同时创建 client 并操作同一个控制器。

```python
def _poll_feedback_silent(self) -> None:
    if self._polling_feedback:
        return  # 只防止轮询重入，不防止发送重入
```

**影响**: 在真实控制器上，两个并发连接可能互相干扰。

**建议修复**: 发送指令前暂停轮询定时器，发送完成后恢复。

**修复方式（2026-04-12）**: 新增 `_pause_polling()`/`_resume_polling()`。`_execute_query_key` 和 `_handle_system_action` 发送前停定时器，完成后恢复。Qt 单线程事件循环下 `timer.stop()` 已足够，无需额外等待当前轮询结束。

### 问题 10：`_wait_for_execution_complete` 在主线程阻塞  ✅ 已修复

**位置**: `qt_gui.py:88-89`（常量定义），`qt_gui.py:2899`（调用）

```python
EXECUTION_RETRY_COUNT = 100
EXECUTION_RETRY_INTERVAL_SEC = 0.1
```

**现象**: 最多等待 `100 × 0.1 = 10秒`，且整个等待过程在 GUI 主线程中通过 `time.sleep` 阻塞，会导致界面冻结。

**影响**: 用户体验差，界面可能长时间无响应。

**建议修复**: 将发送和等待逻辑移到后台线程，通过信号通知 UI 更新。

**修复方式（2026-04-12）**: `_execute_query_key`、`_handle_system_action` 的 SDK 操作移到 `threading.Thread` 后台执行。新增类级 `Signal(object)` + `_run_on_main_thread` 实现跨线程回调。`_append_log` 拆为线程判断：主线程直接写，后台线程通过 Signal 调度。所有 UI 和状态更新（`_after_send`、日志、历史）统一在主线程回调中处理。

### 问题 16：流程执行在主线程中同步阻塞，且递归调用 `_execute_query_key`  ✅ 已修复

### 问题 17：Mock 系统命令状态语义与真实控制器可能不一致  ✅ 已修复

**位置**: `mock_controller/controller.py:346-358` — `_do_sys_resume()`, `_do_auto_start()`

**现象**: `_do_sys_resume()` 和 `_do_auto_start()` 在执行过程中会把 `STATUS` 置为 `STATUS_RUNNING`（1），但 `_execute_command` 的 `finally` 块会在命令结束时统一把 `STATUS_RUNNING` 重置为 `IDLE`。这样会导致 Mock 对系统命令的状态表达更接近“执行一个瞬时动作后回空闲”，而不一定符合真实控制器对“启动/恢复后持续运行态”的定义。

```python
# _do_sys_resume
def _do_sys_resume(self) -> None:
    with self._lock:
        self._set_result(RESULT_OK)
        self._set_alarm(ALM_NORMAL)
        self._set_status(STATUS_RUNNING)
    time.sleep(0.05)
# 但 _execute_command 的 finally 会把 STATUS_RUNNING 统一重置为 IDLE
```

**影响**: 在 Mock 控制器上，`sys_resume` 和 `auto_start` 执行后的状态可能迅速回到 `IDLE`（0），而不是保留为“运行中”。真实控制器是否如此，取决于下位机状态机实现；因此这条问题的核心不是“Mock 一定错”，而是“Mock 与真实控制器的状态语义可能不一致”，会影响测试结论。

**建议修复**: 明确系统命令在 Mock 中的目标状态语义。如果希望与真实控制器一致，可让系统命令走独立状态流，不复用动作类命令的 `STATUS_RUNNING → IDLE` 收尾逻辑。

**修复方式（2026-04-12）**: `_execute_command` 的 `finally` 块中，对系统命令（`SYS_RESET`、`SYS_ESTOP`、`SYS_PAUSE`、`SYS_RESUME`、`AUTO_START`、`AUTO_STOP`、`EMG_RESET`）跳过 `STATUS_RUNNING → IDLE` 重置。系统命令的状态由各自的 handler 自行决定，不再被 `finally` 覆盖。动作类命令（`MOVE_ABS` 等）仍保留原有的 `STATUS_RUNNING → IDLE` 收尾逻辑。

### 问题 18：`_save_record` / `_delete_record` / `_clone_record` 每次都重建 `RobotModbusService` 实例  ✅ 已修复

**位置**: `qt_gui.py` — `_save_record()`、`_clone_record()`、`_delete_record()`、导入模板

```python
# 旧写法（每次重建）
self.service = RobotModbusService(self.json_path, flows_path=self.flows_path)

# 当前写法（共享引用 + reload）
self.service = RobotModbusService(self.json_path, flows_path=self.flows_path, table=self.table)
# 保存/删除/克隆后：
self.service.reload()
```

**现象**: 每次保存/删除/克隆模板都会 `new RobotModbusService(...)`，而构造函数会重新 `load_query_table(self.csv_path)` 和 `load_flows_json(...)`。这意味着：
1. 每次模板编辑都会触发两次磁盘 I/O（保存 JSON + 重建 service 重新加载）
2. 如果 `self.table` 与磁盘文件不同步（例如并发修改），service 的内部 table 会覆盖内存中的修改

**建议修复**: 为 `RobotModbusService` 添加 `reload()` 方法，或者直接让 service 引用 `self.table`，而不是在构造时加载独立副本。

**修复方式（2026-04-12）**: `service.py` 新增 `reload()` 方法，当前只重载 `flows`；`table` 由外部共享引用管理（见问题 25）。同时在 `__init__` 中初始化 `standard_*` 标准协议地址属性，确保新建实例后无需先调 `reload()` 也可直接使用标准协议方法。`qt_gui.py` 中 `_save_record`、`_clone_record`、`_delete_record`、导入模板等操作改用 `self.service.reload()` 替代 `RobotModbusService(...)` 重建。

### 问题 20：NLP 流程执行跳过了规避判断  ✅ 已修复

**位置**: `qt_gui.py:1855-1858`

```python
if action.action_type == "flow" and action.target:
    self.flow_combo.setCurrentText(action.target)
    self._start_flow()
```

**现象**: 当 NLP 解析出"执行流程X"时，直接调用 `_start_flow()`。但 `_start_flow` 内部通过 `_run_current_flow_step` → `_execute_query_key` 执行每步，而 `_execute_query_key` 内部有规避逻辑。这部分没问题。

**建议修复**: 在 `_start_flow` 中增加预检查，遍历所有步骤确认 `self.table` 中存在对应的 key，如有缺失提前警告。

**修复方式（2026-04-12）**: `_start_flow` 方法在启动前新增预检查逻辑：遍历所有步骤 key，检查是否存在于 `self.table`，如有缺失则弹窗警告并列出无效步骤名称，阻止流程启动。

### 问题 22：`DeepSeekClient` 每次调用都重新加载 `.env` 文件  ✅ 已修复

### 问题 23：`_poll_feedback_silent` 中标准协议轮询只读 10 个状态 VR，但 `_apply_feedback_values` 要求 10 个才走标准协议解析  ✅ 已修复

### 问题 24：`MockZMotionVrClient` 的 `axis_ranges` 参数只在初始化时设置一次  ✅ 已修复

**位置**: `mock_controller/client.py:18-25`

**现象**: 每次 `_make_client` 创建新的 `MockZMotionVrClient` 时，都会调用 `self._ctrl.set_axis_ranges(...)`。但 `_ctrl` 是全局单例 `MockController`，所以每次新建 client 都会覆盖全局的轴范围。如果用户在运行时修改了系统配置并保存，下一次创建 client（例如轮询或发送时）会更新范围——这部分是正确的。

但问题是：**多个 MockZMotionVrClient 实例共享同一个 MockController**，如果两个 client 使用不同的 `axis_ranges`（理论上不会，因为都从 `self.axis_ranges` 取），后创建的会覆盖先创建的设置。

**影响**: 当前不会触发，因为所有 client 都使用相同的 `self.axis_ranges`。但设计上有隐患。

**建议修复**: 轴范围应只在 MockController 初始化或显式 `set_axis_ranges` 时设置，不应在每个 client connect 时重复设置。

**修复方式（2026-04-12）**: `MockController.__init__` 新增 `x_range`/`y_range`/`z_range` 可选参数，初始化时直接设置。`MockZMotionVrClient` 创建 `MockController` 时将 `axis_ranges` 传入构造函数，不再事后调用 `set_axis_ranges`。每个 controller 实例的轴范围在创建时确定，不会被其他实例覆盖。`set_axis_ranges` 方法保留供外部显式调用。

### 问题 25：`_save_record` 保存后未同步 `self.table` 到 `self.service`  ✅ 已修复

**位置**: `qt_gui.py:2226-2233`

**现象**: `_save_record` 将 record 写入 `self.table` 并保存 JSON，然后重建 `RobotModbusService`。但 `_execute_query_key` 使用 `self.table[query_key]` 获取记录，而 `service.parse()` 内部也调用自己的 `self.table`（是构造时加载的）。如果用户编辑模板后没有保存就执行，`self.table` 和 `service.table` 可能不一致。

**影响**: 实际影响有限——因为 `_execute_query_key` 使用 `self.table` 而不是 `service.table`（只通过 `service.build_standard_command_from_record(record, ...)` 传入 record），所以 `service.table` 主要影响 `parse()` 和 `resolve()` 方法。但在 NLP 解析路径中，`service.parse(text)` 依赖 `service.table`，如果模板刚被编辑但 service 未重建，NLP 可能找不到新模板。

**建议修复**: 将 service 的 table 改为引用 `self.table`，或在每次模板变更后更新 service 的 table。

**修复方式（2026-04-12）**: `RobotModbusService.__init__` 新增 `table` 可选参数，外部可传入共享引用。`qt_gui.py` 创建 service 时传入 `table=self.table`，使 `service.table` 和 `self.table` 指向同一个字典对象。`reload()` 不再重新加载 table（因为外部已管理），只重载 flows。NLP 解析路径的 `service.parse()` 现在与 GUI 编辑操作共享同一份 table 数据。
