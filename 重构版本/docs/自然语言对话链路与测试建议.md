# 自然语言对话链路与测试建议

本文基于当前代码和 `data/exported_logs/interaction_session_20260607_*.jsonl` 的真实对话日志，说明自然语言输入从 UI 到 Agent、旧 NLP、执行、归档的处理逻辑，并给出针对当前对话问题的测试方案。

## 1. 当前处理链路

### 1.1 交互记录先创建为 pending

用户在操作员界面输入文本后，`OperatorUiMixin._operator_archive_text_input()` 会调用 `InteractionArchiveWriter.append_input_record()` 写入一条 `interaction_record`。

初始记录默认是：

- `nlp_result.engine = "pending"`
- `nlp_result.intent = "pending"`
- `execution.result = "pending"`
- `response.final = ""`

也就是说，日志里的 `pending` 不是一种最终业务状态，而是“记录已创建，但后续处理还没把结果写回去”的初始状态。

相关代码：

- `robot_modbus_lite/interaction_archiver.py`
  - `append_input_record()` 初始化 `nlp_result`、`safety_check`、`execution`、`response`
- `robot_modbus_lite/operator_ui_mixin.py`
  - `_operator_archive_text_input()`
  - `_operator_archive_nlp_result()`
  - `_operator_archive_execution_result()`

结论：如果一条日志最后仍是 `engine=pending` 或 `execution.result=pending`，说明某个处理分支没有完整归档结果。

### 1.2 UI 命令优先于 NLP

文本执行入口在 `OperatorUiMixin._execute_nlp_text()`，主要顺序是：

1. 预处理流程创建 follow-up 文本
2. `_handle_operator_ui_command(text)`
3. `_operator_reject_new_action_while_busy(text)`
4. 尝试后台 Agent 解析
5. 同步调用 `_operator_try_agent_orchestrator_plan(text)`
6. 如果 Agent 返回 `None`，退回 `NlpMixin._execute_nlp_text()`，即旧的 `VoiceNlpAdapter`

`_handle_operator_ui_command()` 又包含很多本地状态处理：

- 待确认修改
- 待澄清回答
- 待流程草案编辑
- 待流程草案命令
- 待流程草案查询
- 流程列表查询
- 本地流程创建请求
- 上下文查询
- 看板状态查询

这意味着系统不是单一 Agent 管线，而是“UI 状态处理 + 新 Agent + 旧 VoiceNlpAdapter”的组合。

### 1.3 新 Agent 管线

`_operator_try_agent_orchestrator_plan()` 创建 `AgentOrchestrator`，挂载多个子 Agent：

- `ChatExplanationAgent`
- `DashboardQueryAgent`
- `FlowDraftAgent`
- `RegisteredFlowAgent`
- `PositionQueryAgent`
- `MemorySettingAgent`
- `PositionMemoryAgent`
- `AtomicTemplateAgent`
- `RestrictedAgentService`
- 可选 `LlmFallbackAgent`

`AgentOrchestrator.handle()` 的路由顺序大致是：

1. 先做 command understanding
2. 尝试复合指令
3. 尝试记忆/位置/原子模板
4. 尝试看板查询
5. 尝试流程草案
6. 尝试已注册流程
7. 如果 `needs_model`，可选 LLM fallback
8. 如果 `intent == unknown`，走位置查询或 chat
9. 如果命中受限 Agent 意图，进入 `RestrictedAgentService`
10. 都不命中，则返回 `fallback_legacy`

在 UI 层，如果 result 是：

- `restricted_agent`
- `compound_plan_draft`
- `unsupported_compound`

会把 `result.payload` 交给 `AgentPlanAdapter`。其他 result 直接交给 `AgentPlanAdapter`。

如果 result 是 `fallback_legacy`，UI 记录一条“统一Agent交回旧路径”的日志，然后返回 `None`，让旧 NLP 接手。

### 1.4 旧 VoiceNlpAdapter 管线

当新 Agent 返回 `fallback_legacy` 或异常时，代码会退回 `NlpMixin._execute_nlp_text()`，由 `_build_voice_nlp_adapter().parse()` 处理。

旧管线包含：

- jieba/rule 模板匹配
- 已注册流程匹配
- 系统动作
- DeepSeek chat 或复杂流程草案
- 原子记忆/位置模板

这就是日志里出现 `agent_orchestrator`、`jieba_rule`、`deepseek`、`pending` 混在一起的原因。

### 1.5 计划落地和状态更新

一旦得到 `VoiceNlpPlan`，`OperatorUiMixin._set_nlp_result_plan()` 会：

1. 调用父类更新 UI 文本框
2. `_operator_archive_nlp_result(plan)` 写回日志的 `nlp_result`
3. 根据 plan 类型决定：
   - 查询：直接回答并归档 execution/result
   - 可执行动作：可能做预检、设置待确认 plan
   - 非执行动作：作为 chat/clarification/unknown 回复

对于 LLM 结构化意图，`_operator_handle_llm_context_intent_plan()` 会把 `flow_create`、`flow_append_step`、`flow_query` 等映射成本地 UI 操作。

其中 `flow_create` 会调用 `_operator_start_local_flow_create_draft()`，创建 `_operator_pending_flow_draft`，但这只是本地草案，不会写控制器。

### 1.6 执行和确认

真正执行动作在 `NlpMixin._execute_nlp_plan()` 和 `_run_next_nlp_action()`：

- `template` / `atomic_template` -> `_execute_query_key()`
- `system` -> `_handle_system_action()`
- `flow` -> `_start_flow()`
- `memory` -> 更新本地记忆

需要确认的 plan 会先进入 `_operator_pending_confirm_plan`，等待用户确认。确认逻辑由 `_operator_confirm_execute()` 等 UI 命令处理。

流程草案是另一套状态：`_operator_pending_flow_draft` 和 `ExecutionPlanService.pending_flow_draft()`。它和控制器写入不是一回事。

## 2. 当前对话问题如何产生

### 2.1 pending 和空回复

6月7日 4 个 interaction session 共 31 条记录，其中大量记录最终停在 `engine=pending` 或 `execution.result=pending`。

结合代码看，根因不是“Agent 返回 pending”，而是：

1. 日志初始状态就是 pending
2. 某条处理路径返回了 `True` 或异步中断
3. 但没有调用 `_set_nlp_result_plan()` 或 `_operator_archive_execution_result()`
4. 记录就永久保持 pending

因此测试必须禁止“输入非空但最终 response.final 为空”。

### 2.2 两条 NLP 管线交替导致语义不一致

例如 session `172840`：

1. “你好，我先创建一个新的流程。”走 `agent_orchestrator`，回复“请问新流程的名称是什么？”
2. “现在流程名字叫测试。”退回旧 `jieba_rule/chat`，回复“已确认新流程名称测试登记成功”

这两轮看起来是连续对话，但实际不是同一套状态机在处理。第一轮的新 Agent 问了名字，第二轮旧管线把回答当闲聊生成了自然语言回复。

用户看到“登记成功”，但系统未必创建了 `_operator_pending_flow_draft`。

### 2.3 chat 文本可能像动作承诺

`ChatExplanationAgent` 和旧管线 chat 本质是解释/回复，不应产生执行动作。`LlmFallbackAgent` 的系统提示也明确要求不能输出可执行参数和寄存器写入。

问题是：chat 或 context reply 里可能出现“已创建”“已登记”“已添加”这类动作承诺。如果这些文字没有绑定到真实状态更新，就会形成虚假成功。

注意：不能用 `modbus_write` 判断流程草案是否创建。流程草案本来不应写控制器。正确判断应检查：

- `_operator_pending_flow_draft`
- `ExecutionPlanService.pending_flow_draft()`
- `flows.json` / flow registry

### 2.4 多轮流程创建状态不完整

代码里已经存在一些局部状态：

- `_operator_pending_flow_creation_followup`
- `_operator_pending_flow_draft`
- `ExecutionPlanService.current_clarification()`
- `ExecutionPlanService.pending_flow_draft()`

但从日志看，真实链路没有稳定覆盖下面这种多轮任务：

1. 创建流程
2. 询问名称
3. 用户给名称
4. 进入草案
5. 添加步骤
6. 缺坐标时追问
7. 用户补坐标
8. 查看草案
9. 保存或执行

尤其是“名称回答”“坐标回答”“查看刚刚流程”容易掉到旧管线或 pending。

### 2.5 中文数字和 ASR 噪声

`CommandUnderstandingAgent._parse_cartesian_params()` 使用的坐标正则只识别阿拉伯数字：

```python
re.search(rf"{source_key.upper()}(-?\d+(?:\.\d+)?)", compact)
```

所以 `X一百` 不匹配 `target_x=100`。

真实语音日志里还有：

- “小镇” -> “小正”
- “点投” -> “点头”
- “速度二” -> “步骤二”
- “AVG” 等误识别

这些不能全部交给 LLM 自由解释。至少要有一层确定性归一化和“不确定就澄清”的规则。

### 2.6 忙碌拒绝可能掩盖前序失败

`_operator_reject_new_action_while_busy()` 会在 `nlp_sequence_running`、`flow_running`、`busy/run_state` 为运行或暂停时拒绝新动作，并归档 `blocked`。

如果前一轮解析/执行异常后没有正确收尾 busy 状态，下一轮用户输入就可能被误判为“任务未完成，拒绝新动作”。

这解释了日志里“上一轮 pending 空回复，下一轮被 blocked”的体验。

## 3. 测试策略

### 3.1 第一优先级：日志收尾测试

目标：任何输入都不能停在初始 pending。

断言：

- `nlp_result.engine != "pending"`
- `execution.result != "pending"`，或者至少有明确的处理中状态和超时收敛
- `response.final` 非空
- 异常路径也必须归档 failure/clarification/blocked

重点用例：

- `现在状态怎么样？`
- `直行点头流程。`
- `测试。`
- `我觉得坐标是 X 一百， Y 0， Z 100，速度 50。`
- `对呀，那肯定用我的坐标呀。`

### 3.2 第二优先级：流程创建状态机测试

固定多轮脚本：

```text
你好，我先创建一个新的流程。
现在流程名字叫测试。
添加第一步是移动到位置 A。
我觉得坐标是 X 一百，Y 0，Z 100，速度 50。
我想看一下刚刚的流程。
保存并执行。
确认执行。
```

每轮断言：

- 第 1 轮：进入等待流程名或已开始流程草案
- 第 2 轮：必须创建 `_operator_pending_flow_draft.flow_name == "测试"`
- 第 3 轮：必须添加一个缺坐标或待补全的移动步骤
- 第 4 轮：必须把坐标补到上一轮步骤，不能当状态查询或闲聊
- 第 5 轮：必须展示当前草案
- 第 6 轮：必须进入保存/执行前确认或预检
- 第 7 轮：必须消费待确认状态

### 3.3 第三优先级：禁止 chat 动作承诺

断言：

- 如果 `action_type == "chat"`，回复不能包含：
  - 已创建
  - 已登记成功
  - 已添加
  - 已保存
  - 已执行
  - 确认执行成功
- 如果回复包含这些词，必须能在状态层找到对应事实：
  - flow draft 存在
  - flow registry 已保存
  - pending confirm 存在
  - execution result success

### 3.4 第四优先级：新旧引擎边界测试

断言：

- 创建/编辑流程链路不允许在关键轮次退回无状态 chat
- `fallback_legacy` 允许存在，但必须生成明确 fallback 结果，不能静默
- 同一 session 中若处于流程草案状态，优先 `_operator_handle_pending_flow_draft_edit/query/command`

### 3.5 第五优先级：ASR 噪声回归

固定用例：

```text
小镇执行点头流程。
小镇直行点头，流程。
我想咨询点投流程。
我觉得坐标是 X 一百，Y 0，Z 100，速度 50。
速度二，等待 2 秒。
我的 AVG 去哪里了？
```

断言：

- 可确定纠正的要纠正，例如“小镇”作为“小正”
- 不确定的要澄清，不能编造上下文
- 任何噪声输入都不能空回复

## 4. 修复建议顺序

### 4.1 先修归档兜底

在 `_execute_nlp_text()`、后台 Agent done callback、旧 NLP fallback、UI 命令 handler 等所有返回路径上加统一兜底：

- 如果本轮已有 interaction record
- 且最终仍是 pending
- 则归档为 failure/clarification/unknown，并给用户最终回复

这是体验底线。

### 4.2 再统一流程创建事实源

把“创建流程”的事实源固定为 `_operator_pending_flow_draft` / `ExecutionPlanService`。

任何回复“已开始创建/已创建/已登记流程名”的路径，都必须同时写入这个状态。

### 4.3 限制 chat 承诺

chat agent 和 LLM fallback 的 `suggested_reply` 进入 UI 前做安全过滤：

- chat 只能解释、建议、询问
- 不能说已经完成某个状态变更
- 如果 LLM 返回 `flow_create` 等结构化 kind，必须走 `_operator_handle_llm_context_intent_plan()`，不能只展示文字

### 4.4 加中文数字和语音归一化

在进入 `CommandUnderstandingAgent` 和 pending flow draft edit 前，增加归一化：

- 一百 -> 100
- 五十 -> 50
- 小镇 -> 小正
- 点投 -> 点头，置信不足时澄清
- 速度二 -> 步骤二，需结合上下文判定

### 4.5 最后收敛新旧管线

短期可保留旧 `VoiceNlpAdapter`，但要明确边界：

- 流程创建/编辑/确认状态中不允许退到旧 chat
- 旧管线只能返回可解释的 `VoiceNlpPlan`
- 旧 chat 的动作承诺必须过滤

长期建议让 `AgentOrchestrator` 成为唯一入口，旧管线作为子 Agent，而不是 UI 层 fallback。

## 5. 测试脚本建议

建议新增 `tools/replay_interaction_loops.py`，不要依赖 LLM 随机生成。

输入：

- 固定场景 YAML/JSON
- 或从 `interaction_session_*.jsonl` 抽取用户输入序列

输出：

- 每轮输入
- engine
- action_type
- execution.result
- final response
- pending draft 摘要
- pending confirm 摘要
- pass/fail 原因

最低断言集：

```text
NO_PENDING
NO_EMPTY_FINAL
NO_CHAT_ACTION_PROMISE
FLOW_DRAFT_EXISTS_AFTER_CREATE
FLOW_STEP_APPENDED
COORDINATE_ANSWER_APPLIED
FLOW_QUERY_SHOWS_DRAFT
CONFIRM_CONSUMES_PENDING_PLAN
```

这套测试比 AI 自由对话更适合作为回归门禁。AI 多轮测试可以保留，但只用于探索新说法，不用于判定通过。
