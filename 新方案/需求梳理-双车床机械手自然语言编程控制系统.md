# 双车床机械手自然语言编程控制系统需求梳理

## 1. 项目目标

本项目目标是建设一套面向双车床上下料场景的机械手控制系统，支持：

- 自然语言输入任务
- 上位机解析为结构化指令
- 通过 ZMotion VR 寄存器与控制器通信
- 控制器执行运动、IO、模式切换等动作
- 上位机实时监控状态、报警和安全等级
- 后续逐步扩展语音交互、视觉定位、焊接循迹

当前阶段重点不是一次性做完全部功能，而是先完成：

- 通信链路稳定
- 固定 20 个 VR 寄存器协议
- 简单 QT 界面
- 自然语言编程逻辑基础版
- 指令和参数映射后台配置

## 2. 当前确认的总体方向

### 2.1 系统分层

系统按四层理解：

- 操作层：QT 上位机界面
- 解析与安全层：自然语言解析、JSON 结构、安全校验、状态机
- 通信层：ZMotion VR 寄存器协议
- 执行层：RTBasic 控制器逻辑

### 2.2 当前实施顺序

按当前聊天结论，实施顺序应为：

1. 先把通信完全跑通
2. 固定 20 个寄存器协议
3. 做简单 QT 页面，先能演示
4. 做自然语言到结构化指令的映射
5. 做后台管理页面，维护指令和参数关系
6. 下游工程师配合做运动合法性校验、报警检测与反馈
7. 后续再扩展语音、视觉、焊接循迹

## 3. 第一阶段产品定位

第一阶段不是完整工业平台，而是可试验、可演示、可逐步扩展的样机版。

### 3.1 第一阶段要实现

- QT 简单界面
- 控制器连接与状态显示
- 自然语言输入
- 固定指令解析
- JSON 结构化命令
- VR[0]~VR[19] 固定长度通信
- 执行结果回读
- 后台管理页面配置指令和参数映射

### 3.2 第一阶段暂不深做

- 复杂视觉联动
- 焊接循迹
- 高级 UI 美化
- 完整自由对话式大模型调度
- 复杂多任务并发调度

## 4. QT 界面需求

### 4.1 用户前台页面

最终用户页面先以简单、易实现、便于试验为主，不强调视觉美化。

当前理解的前台页面应包含：

- 自然语言输入框
- 指令历史列表
- 一键执行
- 暂停
- 继续
- 紧急停止
- 当前机械手坐标显示
- 当前姿态 RX/RY/RZ 显示
- 当前速度百分比、加速度百分比显示
- 控制器连接状态显示
- 运行状态显示
- 安全等级显示
- 机床 1 / 机床 2 状态显示
- 夹爪状态显示
- 报警信息显示

### 4.2 工程师后台页面

后台管理页面用于维护“指令与参数关系”，这是当前阶段的核心配置页面。

至少需要支持：

- 添加指令类型
- 编辑指令码
- 维护指令名称
- 维护自然语言关键词
- 维护是否有参数
- 维护参数模板
- 维护工位坐标与姿态
- 保存和加载 JSON

当前聊天里已经明确：

- 前台页面只需要展示诸如“绝对移动到 A 点”这一类简单指令
- 更复杂的参数映射、指令类型、工位参数在后台管理页维护

## 5. 通信协议需求

### 5.1 协议选型

当前已明确：

- 使用 ZMotion VR 寄存器通信
- 先不用 Modbus
- 后续如需循迹，再考虑 table 通信

### 5.2 固定长度要求

当前已明确：

- 采用固定 20 个寄存器
- 固定长度便于提升传输效率
- 固定长度便于检测通信是否成功

### 5.3 当前固定映射

当前确认的主映射为：

- VR[0]：命令码
- VR[1]：X
- VR[2]：Y
- VR[3]：Z
- VR[4]：RX
- VR[5]：RY
- VR[6]：RZ
- VR[7]：速度百分比
- VR[8]：加速度百分比
- VR[9]：工位 ID / 设备 ID
- VR[10]~VR[15]：扩展参数
- VR[16]：执行结果
- VR[17]：忙闲状态
- VR[18]：任务 ID 回传
- VR[19]：安全等级

### 5.4 数据特点

- 所有数据统一按 Float 传输
- 逻辑上采用固定 20 寄存器结构
- 上位机负责写命令区、读反馈区
- 控制器负责执行并回写状态

## 6. 指令体系需求

### 6.1 核心原则

- 无参数指令原则上剔除
- 但允许增加一类“固定函数型无参数指令”
- 例如 `5001` 可表示控制器内部已固化的一类固定动作函数

这说明当前系统应同时支持两类指令：

- 带参数指令
- 固定函数指令

### 6.2 当前通用指令类型

#### 移动类

- MOVE_ABS
- MOVE_REL
- MOVE_SAFE

#### 夹爪类

- CLAW_GRIP
- CLAW_RELEASE
- CLAW_CHECK

#### 机床类

- LATHE_DOOR_OPEN
- LATHE_DOOR_CLOSE
- LATHE_CHUCK_CLAMP
- LATHE_CHUCK_RELEASE
- LATHE_START
- LATHE_STOP

#### 系统类

- SYS_RESET
- SYS_ESTOP
- SYS_PAUSE
- SYS_RESUME

#### 模式类

- MODE_AUTO
- MODE_MANUAL
- MODE_DEBUG

#### 自动化类

- AUTO_START
- AUTO_STOP
- AUTO_SPEED

#### 配置类

- POS_SAVE
- POS_LOAD
- POS_EXPORT

### 6.3 指令码标准

当前已给出一版指令码标准，后续建议作为统一字典维护：

## 7. 自然语言编程需求

### 7.1 当前目标

现在的重点已经从“纯通信测试”转向“自然语言编程逻辑”。

当前自然语言层要实现的是：

- 将自然语言解析为结构化 JSON 指令
- 与业务工位、动作模板建立映射
- 支持流程表达
- 支持简单连续任务

### 7.2 当前不是重点的能力

- 自由对话式复杂推理
- 复杂流程自动优化
- 视觉大闭环决策

### 7.3 当前推荐做法

先做受控语法和模板化解析，例如：

- “绝对移动到 A 点”
- “机床 1 开门”
- “夹爪 2 夹紧”
- “进入自动模式”

然后由后台配置页面维护：

- 自然语言关键词
- 对应指令码
- 参数模板
- 工位和设备映射

## 8. JSON 结构需求

### 8.1 作用定位

JSON 是上位机内部统一指令格式，不是最终直接传到底层的通信格式。

它主要用于：

- 自然语言解析结果承载
- 页面预览
- 日志记录
- 指令队列
- VR 映射前的中间结构

### 8.2 当前建议标准结构

```json
{
  "taskId": 1001,
  "cmd": "MOVE_ABS",
  "code": 1001,
  "params": {
    "x": 120.5,
    "y": 80.0,
    "z": 45.0,
    "rx": 0.0,
    "ry": 0.0,
    "rz": 0.0,
    "speedPercent": 30,
    "accPercent": 40,
    "posId": 2
  },
  "safetyLevel": 5,
  "desc": "绝对移动到原料1号取料位"
}
```

当前分工已经比较明确：
