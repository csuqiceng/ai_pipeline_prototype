# V4.3 协议迁移实施计划

> 生成日期: 2026-05-11
> 目标协议: `上位机通讯协议说明书V4.3.txt`
> 依据报告: `V4.1协议差距分析报告.md`（历史文件名保留，内容已按 V4.3 更新）
> 目标: 将当前上位机和 mock controller 从旧 IEEE(34) 单状态模型迁移到 V4.3 的 IEEE + LONG 通讯方案。

---

## 一、实施原则

1. 先改协议底座，再改 GUI。
2. 先保证 104/106/107/108 按 V4.3 跑通，再新增 109/110/120/11。
3. `read_modbus_long` 是 P0 必需；`write_modbus_long` 只作为 mock/test 辅助，不在生产流程主动写 LONG 状态区。
4. 先串行跑通，再做并行调度。Func110/Func120 最终进入 program slot，不占用 motion slot。
5. 每个阶段都要让 mock 和真实控制器接口抽象保持一致，避免 GUI 依赖 mock 特例。

---

## 二、阶段计划

### M0.5 Modbus 地址映射验证

目标: 在进入代码改造前确认 ZAux SDK 对 IEEE/LONG 地址参数的实际解释，避免把 V4.3 文档中的地址规则理解错后批量改错。

前提:
- 不在真实运行程序中直接写 `IEEE(34)`、`LONG(34)`、`LONG(36)`、`LONG(38)`、`LONG(40~46)`。
- 真实硬件验证必须使用下位机提供的临时测试程序或专用空闲测试地址。
- 如果暂时没有硬件或安全测试地址，本阶段记录为硬件待确认风险，但不阻塞 mock 侧接口改造。

建议测试项:
- 由下位机提供一组安全测试 IEEE 地址和 LONG 地址，避免与生产协议区重叠。
- 写入测试 IEEE 浮点值后，用 IEEE 读取确认 float 往返正确。
- 写入测试 LONG 整数值后，用 LONG 读取确认 32-bit int 往返正确。
- 交叉读取 IEEE/LONG 测试地址，确认二者不会被上位机误当成同一数据类型解析。
- 验证 `ZAux_Modbus_Get4x_Long(start, count)` 返回值类型、符号位和 count 行为。
- 验证 `ZAux_Modbus_Get4x_Float(start, count)` 多点读取时，对 IEEE 地址序列的实际步进行为。

验收:
- 明确记录真实 SDK 中 IEEE/LONG 的 start 参数解释。
- 明确记录 `Get4x_Long` 和 `Get4x_Float` 的 count 行为。
- 若硬件未验证，后续 M1/M2 只能先在 mock 侧实现，真实控制器联调前必须补测。

### M2 V4.3 状态模型重构

目标: 用 `LONG(34)` 的 2-bit per function 状态模型替代旧 `IEEE(34)` 单状态模型。

涉及文件:
- `robot_modbus_lite/models.py`
- `robot_modbus_lite/service.py`
- `robot_modbus_lite/qt_gui.py`
- `mock_controller/protocol.py`
- `mock_controller/controller.py`

任务:
- 重写 `SixAxisStatus`，输入从 float 改为 int。
- 同步修正 `SixAxisCommand` 的 fuzzy 字段语义:
  - `fuzzy_pos`
  - `fuzzy_spd`
  - `fuzzy_acc`
  - `fuzzy_dec`
  - 字段类型从 float 改为 int，值域为 0/1；写入 IEEE 时再转换为 float。
- 增加函数状态枚举:
  - `0 = IDLE`
  - `1 = EXEC`
  - `2 = DONE`
  - `3 = ERR`
- 增加函数状态掩码表:
  - Func104: shift 0, mask `0x00000003`
  - Func106: shift 2, mask `0x0000000C`
  - Func107: shift 4, mask `0x00000030`
  - Func108: shift 6, mask `0x000000C0`
  - Func109: shift 8, mask `0x00000300`
  - Func110: shift 10, mask `0x00000C00`
  - Func11: shift 14, mask `0x0000C000`
  - Func120: shift 18, mask `0x000C0000`
- 统一提取规则:
  - `val = (LONG(34) & mask) >> shift`
  - `val == 0` → IDLE
  - `val == 1` → EXEC
  - `val == 2` → DONE
  - `val == 3` → ERR
- `can_send(func)` 改为:
  - 目标函数状态为 IDLE
  - `34.24` 报警为 0
  - `34.25` 急停为 0
  - `34.28` 就绪为 1
- Func104 跳过上述前置状态检查。
- mock controller 状态写入改为更新 `LONG(34)` 对应函数 2-bit。

验收:
- GUI 轮询目标函数状态时按函数掩码判断 DONE/ERR。
- 报警、急停、暂停、取消、就绪都从 `LONG(34)` 全局位解析。
- mock 中可模拟不同函数同时处于不同状态。

### M3 Func104 与报警复位重构

  - `estop_ctrl: int = 0`
  - `pause_ctrl: int = 0`
  - `cancel_ctrl: int = 0`
  - `reset_ctrl: int = 0`
- Func104 写入:
  - `IEEE(0)=104`
  - `IEEE(2)=estop_ctrl`
  - `IEEE(4)=pause_ctrl`
  - `IEEE(6)=cancel_ctrl`
  - `IEEE(8)=reset_ctrl`
  - `IEEE(32)=1`
- 系统命令映射:
  - 急停: `estop_ctrl=1`
  - 解除急停: `estop_ctrl=2`
  - 暂停: `pause_ctrl=1`
  - 解除暂停: `pause_ctrl=2`
  - 结束/取消: `cancel_ctrl=1`
  - 解除取消: `cancel_ctrl=2`
  - 报警复位: `reset_ctrl=1`
- 删除或绕开 `BIT(151)` 报警复位路径。
- `read_modbus_bit()` / `write_modbus_bit()` 标记为旧协议兼容接口，V4.3 执行路径不得调用。
- `ControllerClient` Protocol 中 BIT 方法保留时需注明 deprecated；后续完全移除前先确保没有旧功能依赖。
- mock 的 `_do_six_stop()` 从旧 `IEEE(2)=stop_mode` 单参数模型改为读取 `IEEE(2/4/6/8)` 四个控制字，并按 V4.3 1.2 节语义更新 `LONG(34)` 的 `34.24~34.28` 和 Func104 状态位 `34.00,34.01`。
- mock 的 `_apply_six_stop_cmd_locked()` 继续只服务于运动函数 `Func106/107/108` 的 `IEEE(20)=stop_cmd`，不要和 Func104 四控制字混用。
- `service.py:build_six_system_command()` 改为标准 Func104 控制字映射:
  - `4002` → `func_num=104, estop_ctrl=1`
  - 解除急停命令 → `func_num=104, estop_ctrl=2`（如有对应系统 code，需在 UI/配置中明确）
  - `4003` → `func_num=104, pause_ctrl=1`
  - `4004` → `func_num=104, pause_ctrl=2`
  - `1008/4001` → `func_num=104, reset_ctrl=1`
  - `6001/6002` → 旧系统本地流程命令，V4.3 不再下发到控制器；执行层遇到时应明确报错。
- mock 中 Func104 按控制字更新 `LONG(34)` 的 `34.24~34.28` 和函数状态位。

验收:
- 报警复位不再调用 `write_modbus_bit(151, ...)`。
- Func104 在任何状态下可触发。
- mock 中报警复位能清除报警位和所有函数状态位。

### M5 清理冲突反馈地址与已有函数跑通

目标: 清理 `IEEE(40~46)` 与 `LONG(40~46)` 的冲突，并让 106/107/108 先按 V4.3 跑通。

涉及文件:
- `robot_modbus_lite/service.py`
- `robot_modbus_lite/qt_gui.py`
- `robot_modbus_lite/models.py`
- `mock_controller/controller.py`

任务:
- 停止从 `IEEE(40~46)` 读取位姿。
- 位姿/关节反馈优先切到协议定义区，并确认语义:
  - DPOS: `IEEE(1500~1522)`，需求位置
  - MPOS: `IEEE(1600~1622)`，实际位置
  - 当前 `_execute_send_six` 执行完成后的实际回传位姿优先使用 MPOS
- DPOS/MPOS 轴段映射:
  - 关节轴 DPOS(0~5): `IEEE(1500,1502,1504,1506,1508,1510)`
  - 关节轴 MPOS(0~5): `IEEE(1600,1602,1604,1606,1608,1610)`
  - 虚拟/笛卡尔轴 DPOS(6~11): `IEEE(1512,1514,1516,1518,1520,1522)`
  - 虚拟/笛卡尔轴 MPOS(6~11): `IEEE(1612,1614,1616,1618,1620,1622)`
- 确认 DPOS/MPOS 的刷新时机:
  - 是否在运动完成后立即更新
  - 是否在点动/直线插补/连续插补中保持一致
  - mock `_sync_six_realtime_locked()` 需要同步写入 DPOS 和 MPOS 地址
- mock 内部可短期保留临时运动变量，但对外反馈必须同步写入 DPOS/MPOS；GUI 和 service 不再直接依赖 `SIX_RT_J_START(IEEE58~68)` 或 `SIX_RT_XYZ_START(IEEE40~50)`。
- 如果真实固件暂不实时刷新 DPOS/MPOS，则只能临时使用 `IEEE(50~72)` 扩展反馈区，并要求补充协议语义定义。
- `IEEE(50~72)` 扩展反馈逐项确认清单:
  - `IEEE(52)` 当前速度: 尝试从协议定义区域替代；如无替代，需固件确认语义和刷新周期。
  - `IEEE(54)` 剩余距离: 尝试从协议定义区域替代；如无替代，需固件确认语义和刷新周期。
  - `IEEE(56)` 运动状态: 如固件提供可临时保留；否则 GUI 中相关显示需降级或移除。
  - `IEEE(58~68)` J1~J6 关节角度: 迁移至 DPOS/MPOS 关节轴段后废弃该地址段。
  - `IEEE(70)` ECAT 通讯状态: 需确认固件是否提供；不提供则暂时移除 GUI 显示。
  - `IEEE(72)` FRAME 坐标系: 需确认固件是否提供；不提供则暂时移除 GUI 显示。
- 当前函数号改读 `IEEE(322)`，不再读 `IEEE(36)`。
- 系统状态改读 `LONG(36)`。
- 报警码改读 `LONG(38)`。
- 修正 mock `read_modbus_float()` 多点读取步进，使其匹配实机 IEEE 地址语义。
- 同步修正 mock `write_modbus_float()` 的批量写入步进；当前多数写入是单值，但 Func11 点数据和未来批量写入会依赖正确行为。
- 106/107/108 的速度、加速度、减速度按 V4.3 `0~150` 百分比校验。

验收:
- 106/107/108 在 mock 下完成完整发送、回显、触发、DONE/ERR 轮询。
- 不再使用 `IEEE(36/38/40~46)` 作为 V4.3 状态和反馈来源。
- `IEEE(50~72)` 如继续使用，必须标记为待固件确认的扩展反馈，不作为协议必需路径。

## 五、风险与注意事项

1. `IEEE(2~30)` 参数值仍是 float 存储，但函数号、fuzzy、stop_cmd 等语义是整数，模型层应保持 int 语义。
2. 速度、加速度、减速度需从当前绝对值习惯切换到 V4.3 的 `0~150` 百分比语义。
3. `IEEE(50~72)` 目前只可作为待确认扩展反馈，不应作为 V4.3 必需实现。
4. Func104 必须避免等待旧运动线程结束；mock 中不能用 `join(timeout=5.0)` 阻塞急停响应。
5. 新增函数进入 query table 后，要避免拼写错误静默落回默认值；建议后续增加参数 key 严格校验日志。
6. 并行执行不要提前做，必须等单函数协议稳定后再实现。
7. M0.5 不得直接写协议状态区验证地址映射，真实硬件验证必须使用安全测试地址。
