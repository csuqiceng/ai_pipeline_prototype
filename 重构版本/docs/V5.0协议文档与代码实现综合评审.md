## 1. 总体结论

当前项目与 V5.0 通讯寄存器说明书高度相关，核心六轴 Modbus 主链路已经存在：函数参数建模、IEEE 参数写入、回显比对、LONG(34) 状态解析、T0/T1 通道互斥与并行、真实控制器读写封装、模拟控制器回归测试均已覆盖。

截至 2026-05-17，本轮代码整改已把评审识别出的安全时序、接受确认、暂停自动恢复、参数地址、寄存器地址口径、状态位归属、IO 反馈语义和扩展诊断读取全部在代码侧落地。

**当前可判定为：V5.0 文档要求已在代码和 mock 中实现，专项验证已通过；最终验收仍依赖真实 VPLC516E 控制器联调记录。**

本轮已修复的高优先级差异：

1. 缺少独立的第三道门：回显比对通过后、触发 `IEEE(32)=1` 前，没有再次读取 `LONG(34)` 检查报警/急停/暂停。

3. `Func109` / `Func110` 参数地址与 V5.0 文档不一致。
4. 暂停状态未纳入普通命令阻断条件，且未实现文档要求的暂停自动等待策略。

## 5. 关键差异清单

### P0：安全时序差异

#### 5.1 缺少第三道门

V5.0 文档要求：

1. 写参数前读取 `LONG(34)`。
2. 写入参数并比对 `IEEE(280~310)`。
3. 触发前再次读取 `LONG(34)`，确认报警、急停、暂停均未发生。
4. 再写 `IEEE(32)=1`。

当前 `_write_six_command()` 中，回显成功后直接写触发寄存器，没有独立的触发前二次检查。

影响：

- 如果回显比对期间发生急停、报警或暂停，代码仍可能触发执行。
- 这与 V5.0 安全流程不一致，应优先补齐。

#### 5.2 未显式等待 `IEEE(312)=1`

V5.0 文档要求触发后先等待 `IEEE(312)=1` 表示命令已被接受，再等待对应函数 DONE。

当前 `_wait_six_command_done()` 主要通过 `LONG(34)` 的函数状态判断 `received/executing/done`，没有单独读取 `IEEE(312)`。

影响：

- 如果控制器回显区和状态位之间存在刷新时序差异，日志无法明确区分“触发已写入但控制器未接受”和“已接受但未执行”。
- 建议增加 `_wait_six_command_accepted()`，读取 `IEEE(312)`，超时后再结合 `LONG(34)` 给出诊断。

### P1：阻塞与异常处理策略差异

#### 5.5 暂停状态未阻断普通命令

代码已经解析 `LONG(34).bit26`，但 `SixAxisStatus.can_send_for()` 未把 `is_paused` 纳入普通命令不可发送条件。

V5.0 文档要求暂停属于可自动恢复阻塞：暂停中不触发普通命令，应轮询等待暂停解除，或由上位机主动发送 `104` 恢复。

建议：

- `can_send_for()` 对非 `104` 函数增加 `is_paused` 阻断。
- `_precheck_six_command()` 检测暂停时进入可配置等待，超时后提示。

#### 5.6 通道忙的自动等待不完全符合文档

当前代码有两套机制：

- `_precheck_six_command()` 发现 slot 未就绪时抛异常。
- 如果真实触发后出现 `LONG(38).bit2` 指令忙，`_execute_send_six()` 会执行有限自动恢复：等待槽释放、发送 `104` 复位、等待就绪。

V5.0 文档要求在第一道门发现同槽执行中时，直接进入自动轮询等待，DONE 后继续三道门流程，而不是先走失败/复位恢复。

建议：

- 在 `_precheck_six_command()` 前或内部增加同槽忙等待。
- 区分“正常忙等待”和“异常 cmd_busy 恢复”，避免把正常连续流程当成报警恢复处理。

#### 5.7 急停/报警缺少人工确认闭环

V5.0 文档明确要求急停/报警属于需人工处理状态，不应自动恢复。

当前实现可检测急停/报警并报错，也支持 `104` 复位，但没有形成严格的“通知、等待人工确认、确认后继续”的状态机。GUI 层更多是日志和提示，安全闭环不完整。

### P1：IO 与反馈语义差异

#### 5.8 `LONG(42)` 未按文档作为 IO 输出状态主读取

V5.0 文档：

- `LONG(42)`：IO 输出状态。
- `LONG(44)`：IO 输出状态回显，与 `LONG(42)` 相同。
- `LONG(46)`：X0~X23 输入状态位图。

当前代码：

- Func120 反馈读取 `LONG(44)` 和 `LONG(46)`。
- mock 中 Func120 操作写 `LONG(44)`，没有同步 `LONG(42)`。
- mock 中 `LONG(46)` 写成 `io_no`，不是输入状态位图。

建议：

- mock 中 Func120 同步写 `LONG(42)` 和 `LONG(44)`。
- `LONG(46)` 保持输入位图语义，不应写端口号。
- GUI 反馈显示同时读取 `LONG(42/44/46)`，便于现场对照。

#### 5.9 `IEEE(322/324)` 当前函数号口径不一致

代码使用 `IEEE(322)` 作为当前函数号读取地址，mock 也同步写入 `322`。

V5.0 文档 7.1 节回显区表格中没有 `IEEE(322)` 这一行，只明确列出 `IEEE(324)` 为当前内部函数号。按文档验收口径，代码读取的是文档未定义地址，因此这是直接冲突，应按 P1 处理。

可选处理方式：

- 若真实 VPLC516E 固件使用 `IEEE(324)`：代码和 mock 应改为读取/写入 `324`，或过渡期同时兼容 `322/324`。
- 若真实固件使用 `IEEE(322)`：V5.0 文档应修正为 `322`，并说明 `324` 是否保留或废弃。
- 在最终确认前，建议真实控制器联调日志同时采集 `IEEE(322)` 和 `IEEE(324)`。

#### 5.10 `LONG(38)` bit8/bit9 归属错误

V5.0 文档中：

- `LONG(36).bit8`：函数号无效。
- `LONG(36).bit9`：120 参数无效。
- `LONG(38)` 报警代码只定义 bit0~bit7。

当前 `SixAxisAlarmDetail.from_value()` 把 `LONG(38).bit8` 解析为 `func_id_invalid`，把 `LONG(38).bit9` 解析为 `param_invalid`。这会把系统状态寄存器的含义错误归入报警代码寄存器。

建议：

- `SixAxisAlarmDetail` 只保留 `LONG(38).bit0~bit7` 的报警解析。
- 新增或扩展 `SixAxisSystemState`，从 `LONG(36)` 解析 `func_id_invalid` 和 `func120_param_invalid`。
- mock 控制器中函数号非法、120 参数非法也应同步写 `LONG(36).bit8/bit9`，而不是写 `LONG(38).bit8/bit9`。

### P2：扩展反馈与诊断差异

#### 5.11 `IEEE(314/316/318/320)` 未作为诊断快照完整读取

文档定义：

- `IEEE(314)`：`LONG(34)` 浮点回显。
- `IEEE(316)`：`LONG(36)` 浮点回显。
- `IEEE(318)`：`LONG(38)` 浮点回显。
- `IEEE(320)`：系统状态字。

当前回显比对只关注命令写入回显 `280~310`；`_read_six_echo_snapshot()` 实际读取到 `312`，不包含 `314`。

建议：

- 触发前后诊断快照可扩展读取 `314~320`。
- 不建议把这些状态回显纳入参数一致性比对；更适合作为日志和异常诊断。

#### 5.12 `IEEE(1740/1742)` 未实现

文档定义当前 R3D 距离和 Z 高度。当前代码和 mock 未实现该反馈。

建议：

- mock 可按当前 X/Y/Z 计算半径与高度。
- GUI 实时监控可显示或记录这两个值。

#### 5.13 `109 DONE` 手动清除未实现

V5.0 文档注意事项写明：`109` 延时完成标志需要上位机写 `IEEE(8)=1` 清除 DONE。

当前代码没有该清除逻辑。是否必须实现取决于真实控制器固件行为：

- 如果 DONE 会被下一次函数状态覆盖，可作为低优先级。
- 如果 DONE 长时间保持并影响后续判断，应补充 `Func109` 完成后的清除动作。

### P2：速度百分比范围差异

V5.0 文档要求速度、加速度、减速度参数统一为 `0~100%`。

当前代码和 mock 对部分函数允许 `0~150%`。

建议先确认真实固件口径：

- 如果 V5.0 确认为 `0~100%`，应调整 GUI 校验、mock 限制、默认模板和文档。
- 如果现场允许 `150%`，应修正文档中的范围说明。
