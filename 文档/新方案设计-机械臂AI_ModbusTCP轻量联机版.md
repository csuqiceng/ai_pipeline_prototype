# 新方案设计：机械臂 AI Modbus TCP 轻量联机版

## 1. 背景

当前原型项目主要目标是验证：

`语音/视觉输入 -> AI 理解 -> 任务规划 -> 调度执行 -> Motion SDK -> 控制器`

但在真机联调阶段，为了先尽快跑通“上位机到控制器”的稳定数据链路，现决定采用更轻量的方案：

- 不在上位机侧实现复杂运动控制流程
- 不直接调用现有的复杂运动执行接口
- 只保留最小功能映射和参数传输能力
- 由上位机负责“语义理解 + 查表 + 参数组包”
- 由控制器负责“收到命令后执行对应函数”

该方案优先解决“先试机、先跑通、先联通”的目标。

## 2. 新方案目标

第一阶段最小目标：

1. 上位机可连接控制器 `192.168.1.11`
2. 通过 `Modbus TCP` 向控制器写入一组命令参数
3. 首版先发送 `函数序号 + 寄存器1~7`
4. 控制器下游程序收到后自行解析
5. 第一阶段只先支持 `移动 / 抓取 / 放下`
6. GUI 可编辑查询表、选择功能、查看发送内容、手动发送
7. 上位机先支持固定规则解析，不依赖 DeepSeek
6. 后续新增功能和工位时，只需在上位机表格中增加记录

## 3. 核心设计思想

新方案采用“上位机做理解，控制器做执行”的分层方式。

### 3.1 上位机负责

- 接收文本或语音指令
- 识别用户意图
- 查询固定查询表
- 生成标准参数包
- 通过 DLL / SDK 与控制器通讯
- 将参数写入 Modbus 寄存器

### 3.2 控制器负责

- 接收参数
- 读取第一个参数，判断函数序号
- 根据函数序号调用对应 ZBasic 函数
- 使用后续参数作为动作执行输入
- 不负责复杂语义理解和多条件流程判断

### 3.3 不再由控制器负责

- 自然语言理解
- 复杂任务推理
- 多条件比较流程
- 上层工艺语义解析

## 4. 通讯方式

### 4.1 连接方式

- 控制器地址：`192.168.1.11`
- 通讯协议：`Modbus TCP`
- 通讯用途：写入动作参数和功能标识

### 4.2 SDK 的角色

`ZMOTION SDK` 在该方案中只用于：

- 连接控制器
- 向 Modbus 寄存器写入数据
- 必要时读取状态或回读数据

不再使用其现有的复杂运动控制接口作为主执行方式。

也就是说，该方案中：

- 上位机直接连接控制器
- 上位机直接发送已经处理好的命令参数
- SDK 只是通讯层，不承担任务规划和动作决策

### 4.3 当前拟采用的数据写入方式

根据仓库内 `zmcdll` 封装，当前可重点考虑以下接口：

- `ZAux_OpenEth`
- `ZAux_Modbus_Set4x_Float`
- `ZAux_Modbus_Set4x`
- `ZAux_Modbus_Set4x_String`
- `ZAux_Direct_SetVrf`

第一阶段优先方案：

- 优先尝试 `ZAux_Modbus_Set4x_Float`
- 直接向约定好的 Modbus 浮点寄存器写入一组浮点数

## 5. 第一阶段数据协议

## 5.1 目标

先不定义复杂 JSON 协议，也不先绑定复杂工艺流程。

第一阶段只约定：

- 上位机发送 `函数序号 + 寄存器1~7`
- 控制器收到后自行解析

## 5.2 数据定义

根据最新地址表中的“机械手跑过的有效数据”，第一阶段协议更新为：

1. 第 1 个值：函数序号
2. 第 2 个值：寄存器 1
3. 第 3 个值：寄存器 2
4. 第 4 个值：寄存器 3
5. 第 5 个值：寄存器 4
6. 第 6 个值：寄存器 5
7. 第 7 个值：寄存器 6
8. 第 8 个值：寄存器 7

即：

```text
[func_id, reg1, reg2, reg3, reg4, reg5, reg6, reg7]
```

## 5.3 关于速度参数的说明

最新地址表中的有效数据已经明确采用了：

- 函数序号
- 寄存器 1~7

因此第一阶段不再按“总共 7 个值”理解，而是按“总共 8 个值”理解。

例如：

```text
位置A -> [3, 1400, -1, 1380, 1, 80, 1, 10]
抓取  -> [9, 1, 0, 0, 0, 0, 0, 0]
放下  -> [10, 0, 0, 0, 0, 0, 0, 0]
```

说明：

- `速度` 当前位于寄存器 7
- CSV 中的 `10%` 在程序读取时应转为纯数值 `10`
- 后续如果控制器要求的是浮点 `10.0`，则由发送端统一转换

但根据最新地址表，第一阶段更适合直接采用“有效数据查询表”，而不是先拆成“功能表 + 位置表”。

- 适合尽快试机
- 中间映射层更少
- 出问题时更容易核对

### 6.4 第一阶段功能范围

根据当前聊天确认，第一阶段建议只先落这三个动作：

1. 移动
2. 抓取
3. 放下

其中“移动”对应的目标位置可来自查询表中的：

- 归零
- home
- 位置A
- 位置B
- 位置C
- 位置D
- 位置E
- 位置X

这样可以把第一阶段目标收敛到“先联通、先试机、先验证查表发送”。

## 7. 第一阶段查询表策略

为减少第一阶段实现复杂度，当前方案不再把“功能表”和“位置表”作为主执行数据源。

第一阶段统一采用：

- `有效数据查询表`

也就是：

- 用户输入一个固定查询键
- 上位机直接查到 `函数序号 + 寄存器1~7`
- 不再经过额外的二次映射

### 7.1 第一阶段实际做法

当用户输入：

- “移动到位置A”
- “移动到位置B”
- “归零”
- “抓取”
- “放下”

上位机优先直接查“有效数据查询表”，然后发送整条记录对应的参数。

### 7.2 第二阶段再考虑的抽象

当第一阶段链路稳定后，再考虑把数据拆成：

- 功能表
- 位置表

以便支持更灵活的组合式组包。

## 8. 上位机处理流程

新方案推荐流程如下：

1. 用户输入文本或语音指令
2. 上位机解析出功能类型
3. 上位机解析出目标查询键
4. 上位机查询“有效数据查询表”
5. 上位机得到 `函数序号 + 寄存器1~7`
6. 上位机组装 8 个发送值
7. 上位机通过 Modbus TCP 写入控制器
8. 控制器收到数据后按函数序号执行

第一阶段建议优先支持固定规则，例如：

- “移动到位置A”
- “移动到位置B”
- “归零”
- “抓取”
- “放下”

这一阶段不要求自由对话理解，也不要求复杂工艺流程拆解。

### 8.1 当前推荐的发送逻辑

当前推荐按以下逻辑实现：

```text
用户指令 -> 上位机规则解析 -> 查有效数据表 -> 组装8个值 -> Modbus TCP写入 -> 控制器按函数号执行
```

### 8.2 关于“移动”功能的当前歧义

当前 CSV 中存在一个必须确认的实现问题：

- `归零 -> 函数序号 1`
- `位置A -> 函数序号 3`
- `位置B -> 函数序号 4`
- `抓取 -> 函数序号 9`
- `放下 -> 函数序号 10`

这意味着当前“函数序号”的业务语义还未最终统一，存在两种可能：

#### 方案 A

函数序号表示“动作类型”

例如：

- `1 = 移动`
- `9 = 抓取`
- `10 = 放下`

此时：

- “位置A / 位置B / 位置C”只是不同参数
- 上位机发送时，移动类目标应统一发同一个移动函数号

#### 方案 B

函数序号表示“查询项或动作项编号”

例如：

- `1 = 归零`
- `3 = 位置A`
- `4 = 位置B`
- `9 = 抓取`
- `10 = 放下`

此时：

- 控制器端可能需要按不同编号分别分支处理

当前聊天记录后半段虽然更倾向“函数序号 + 参数”的结构，但还不能仅凭现有 CSV 最终断定采用 A 还是 B。

因此第一阶段编码前，必须先与下位机工程师确认“函数序号”的最终语义。

## 9. 第一阶段指令解析建议

第一阶段不追求复杂大模型自由理解，建议先做固定规则解析。

例如支持：

- `移动到位置A`
- `移动到位置B`
- `移动到位置C`
- `归零`
- `home`
- `复位`
- `抓取`
- `放下`
- `延时`

### 9.1 解析输出建议

上位机内部先转成这样的结构：

```json
{
  "query_key": "位置A"
}
```

或：

```json
{
  "query_key": "抓取"
}
```

随后再映射成最终的 8 值发送协议。

由于新需求与当前原型 GUI 差异较大，建议新建一个轻量独立 GUI 项目。

### 10.1 GUI 第一阶段功能

  - IP 地址
  - 端口
  - 连接/断开按钮

- 功能表查看
  - 功能名称

  - 零位

  - 各轴位置

  - 第一阶段仅支持固定短句和固定关键词

- 参数预览区
  - 显示即将发送的函数序号和寄存器 1~7

- 手动发送区

## 12. 与当前原型项目的关系

当前 `ai_pipeline_prototype` 项目不建议直接作为该方案的继续演化基础，原因：

- 当前项目侧重 AI 原型验证
- 已有较多调度、规划、执行器逻辑
- 与新方案的“极简传参联机”目标不完全一致
- 强行改造会增加维护复杂度

因此建议：

- 当前项目保留，用于原型研究和历史参考
- 新方案单独新建项目，用于真机轻量联机

## 13. 第二阶段可扩展方向

在第一阶段稳定跑通后，再逐步增加：

1. 语音输入
2. 位置表的可视化编辑
3. 工艺流程文本说明解析
4. 多步任务执行
5. 状态回读与执行确认
6. 报警读取与联机状态监控

## 14. 关于“工艺流程说明书 -> AI 解析执行”的可行性

该方向是可行的，但不建议作为第一阶段目标。

更合理的节奏是：

### 第一阶段

- 先跑通固定命令
- 先跑通有效数据查询表查值
- 先跑通函数序号 + 7 参数发送

### 第二阶段

- 再支持“把工件移动到 A 工位，再抓取，再放到 B 工位”这类多步文本

### 第三阶段

- 再支持更复杂的工艺说明书自动解析

原因：

- 先确保数据链路稳定
- 先确保控制器可正确执行
- 再叠加 AI 复杂度，风险更低

## 15. 评审时需要重点确认的事项

为了避免后续联调时反复返工，评审时建议重点确认以下内容：

1. 第一阶段最终协议是否确定为 `8` 个值：
   - `函数序号 + 寄存器1~7`

2. 第一个字段到底采用哪种方案：
   - 方案 A：整数函数序号
   - 方案 B：`VRSTRING`

当前聊天记录后半段更偏向“整数函数序号”，建议文档和实现统一按整数方案推进。

3. 函数序号的业务语义是否最终采用：
   - 方案 A：动作类型编号
   - 方案 B：查询项编号

4. Modbus 寄存器起始地址是多少：
   - 例如 `start=0`
   - 或由下位机另行指定

5. `寄存器1~7` 的数据类型是否统一按浮点发送：
   - 即使某些值本质上是 `bool/int`
   - 第一阶段也统一按浮点或 IEEE 写入，减少实现分支

6. `10%` 这类速度值是否统一在上位机转换为纯数字 `10`

7. 第一阶段是否只做以下功能：
   - 移动
   - 抓取
   - 放下

8. 第一阶段是否只做以下查询键：
   - 归零
   - home
   - 位置A
   - 位置B
   - 位置C
   - 位置D
   - 位置E
   - 位置X
   - 抓取
   - 放下
   - 延时

9. Python 侧首版是否只需完成：
   - 连接控制器
   - 写入 8 个值
   - 不要求状态回读
   - 不要求复杂任务队列

10. 是否需要最小状态回读位：
   - 若需要，建议单独约定一个状态寄存器
   - 若当前只为试机，可延后到第二阶段

## 16. 当前结论

该新方案是明确可行的，且比当前复杂执行链更适合真机早期联调。

当前最优先事项不是继续扩原型，而是：

1. 新建轻量联机项目
2. 固化有效数据查询表
3. 打通 `Modbus TCP -> 函数序号+寄存器1~7发送 -> 控制器接收`
4. 完成第一轮试机

当第一轮试机成功后，再继续补语音和流程解析能力。
