# 豆包语音成本优化实施方案

## 1. 结论

当前豆包费用高的主要原因不是麦克风一直开启，而是输出音频 token 占比过高。根据账单截图，`API调用token-输出音频` 约 9.21 元，占总费用约 85%。因此优化重点应放在减少豆包 TTS 合成的文本长度和调用次数。

核心方案：

```text
屏幕显示完整内容
豆包只播短摘要
固定短句优先使用本地 PCM 缓存
执行安全仍由本地 Agent / 安全预检 / 确认链路裁决
```

DeepSeek 可以继续负责上下文理解和建议，但不能让豆包为完整回答全文合成语音。

## 2. 文档与代码事实

### 2.1 豆包文档事实

《豆包语音》文档中说明：

- QPM 的 query 对应 `StartSession` 事件。
- TPM 是一分钟内消耗的全部 token。
- 控制台会展示输入音频、输入文本、输出音频、输出文本等 token 用量。
- 文档正文仍列出 `UsageResponse` 事件 154，但修订记录写明：`25.06.04 删除服务端返回的 UsageResponse 事件，客户可以在火山控制台查看用量`。

因此客户端不能依赖服务端返回 `UsageResponse` 做精确计费统计，只能做本地估算和趋势分析。

### 2.2 当前代码事实

当前 TTS 链路：

```text
BroadcastMessage.text
  -> SpeechBroadcastDeliveryService.deliver()
    -> sink.speak(message.text)
      -> DoubaoSpeechSink
        -> DoubaoVoiceClient.stream_synthesize_text()
          -> StartConnection
          -> StartSession
          -> SayHello
          -> TTSResponse 音频流
          -> FinishSession
          -> FinishConnection
```

关键现状：

- `BroadcastMessage` 目前只有 `text`，没有独立的 `speech_text`。
- `SpeechBroadcastDeliveryService.deliver()` 同步逐条调用 `sink.speak(message.text)`。
- `DoubaoSpeechSink` 当前没有 PCM 缓存。
- `DoubaoVoiceClient._send_start_session()` 对 ASR 和 TTS 都发送 TTS 配置。
- 当前 TTS 请求格式为 `pcm`，播放端按 `float32` 播放。
- `_send_chat_tts_text()` 已存在，但当前实际 TTS 合成走的是 `SayHello`。

## 3. 已采纳的评审修正

### 3.1 UsageResponse 不作为客户端统计依据

原先建议采集 `UsageResponse`，但文档修订记录已说明该事件被删除。需要注意：文档正文的服务端事件表仍保留 `154 UsageResponse` 及其 schema，和修订记录存在内部矛盾。

实施策略：

```text
如果服务端仍返回事件 154：优先采集官方 usage 字段。
如果服务端不返回事件 154：使用本地估算。
```

本地估算字段：

```text
TTS 调用次数
StartSession 次数
播报文本长度
播报文本 UTF-8 字节数
返回音频字节数
缓存命中次数
播放是否被打断
```

本地估算数据只能用于趋势分析，不能当作官方计费明细。

### 3.2 短时间播报合并放后

评审指出合并窗口不是简单参数改动。当前 delivery 是同步逐条播报，如果做 300-800ms 合并窗口，需要新增 `SpeechMergeBuffer` 或改造异步 delivery。

因此合并播报放到缓存之后实施。

### 3.3 PCM 缓存必须带格式版本

PCM 缓存不能只按文本和音色做 key。后续如果从 `pcm` 切到 `pcm_s16le`，旧缓存不能按新格式播放。

缓存 key 或元数据必须包含：

```text
文本
speaker
sample_rate
audio_format
cache_schema_version
```

格式变更时应自动失效旧缓存。

### 3.4 纯 TTS 精简 StartSession 需要保留回退

纯 TTS 模式去掉 `system_role` / `speaking_style` 有节省输入文本 token 的价值，但文档没有明确保证所有最小 dialog 配置都能正常工作。

实施时应提供开关：

```text
DOUBAO_TTS_MINIMAL_SESSION=1
```

如果现场发现兼容问题，可以回退到当前完整 StartSession。

额外硬约束：

```text
dialog.extra.model 是文档标注的必传字段。
无论 ASR-only、纯 TTS 还是 minimal_dialog 模式，都必须传递 model。
默认建议先使用 O2.0 版本值：1.2.1.1。
```

`include_tts=False` 时还要避免触发 `42000020`：

```text
正确：完全不发送 tts key。
错误：发送 "tts": {}。
错误：发送 "tts": {"extra": null}。
```

实施前需要用最小 StartSession payload 做握手测试，确认省略 `tts` 节点不会触发 `42000020`。

### 3.5 P0/P1 合并实施

语音摘要层和固定短句清单本质上是同一任务：前者是机制，后者是内容规则。实施时合并为一个 P0，避免先改机制再重复改调用点。

### 3.6 摘要 fallback 必须在统一入口完成

`_operator_publish_ai_answer_for_speech()` 当前有多处调用，逐个调用点补 `speech_text` 成本高且容易遗漏。因此该函数必须提供 fallback：

```text
调用方传 speech_text：直接使用
调用方未传 speech_text：由 _operator_generate_speech_summary(text, context_id) 自动压缩
```

这样即使 DeepSeek 的 `speech_reply` 还没完成，P0 也能先减少豆包播报长度。

### 3.7 PCM 缓存先不改流式播放语义

当前 `DoubaoSpeechSink.speak()` 优先走 `stream_synthesize_text()`，音频 chunk 边返回边播放。若要缓存完整 PCM，需要先收全 chunk 再播放，会牺牲首包播放延迟。

因此第一版 PCM 缓存采用保守策略：

```text
固定短句缓存只在 batch synthesize_text 模式生效；
如果仍使用 stream_synthesize_text，则先不缓存；
后续如需缓存流式结果，再单独评估“边播边收集 chunk 并落缓存”。
```

如果固定短句缓存收益明显，可以为固定短句专门走 batch 模式，长句仍走 stream 模式。

### 3.8 ChatTTSText 不直接强切，先做实验开关

文档语义上，`SayHello` 是“客户端提交打招呼文本”，`ChatTTSText` 是“指定文本合成音频”，长期看 TTS 合成应优先使用 `ChatTTSText`。

但文档修订记录也提到：`ChatTTSText` 一定要在收到 `ASREnded` 之后发送。当前项目的纯 TTS 模式未必存在完整 ASR 流程，直接替换存在兼容风险。

因此实施策略：

```text
P0 不强制切换 SayHello。
新增 DOUBAO_TTS_USE_CHAT_TTS_TEXT 实验开关。
验证 ChatTTSText 在纯 TTS 场景稳定后，再替换 SayHello。
```

验收时记录：

```text
SayHello 模式是否正常
ChatTTSText 模式是否正常
是否需要等待 ASREnded
首包延迟和失败率是否变化
```

## 4. 目标架构

### 4.1 文本分层

新增两类文本：

```text
display_text: 给 GUI 聊天框和右侧面板显示的完整内容
speech_text: 给豆包 TTS 播报的短摘要
```

示例：

```text
display_text:
流程“点头”共 10 步：
01 移动到位置A...
02 移动到位置B...
...

speech_text:
流程详情已显示，共 10 步。
```

### 4.2 本地安全边界

语音摘要层只影响播报，不影响执行链路。执行类动作仍必须经过：

```text
唤醒词检查
本地意图/Agent 解析
参数补全
安全预检
人工确认
Modbus 写入
执行监控
```

DeepSeek 和豆包都不能直接决定机械手执行。

### 4.3 具体接入链路

当前代码链路是：

```text
_operator_publish_ai_answer_for_speech(text)
  -> BroadcastQueue.publish_once(kind, text, context_id="chat:ai_answer")
    -> BroadcastMessage(kind, text, ...)
      -> _operator_filter_broadcasts_for_speech()
        -> SpeechBroadcastDeliveryService.deliver(messages)
          -> sink.speak(message.text)
```

目标改造后：

```text
_operator_publish_ai_answer_for_speech(text, speech_text="")
  -> speech_text 或 _operator_generate_speech_summary(text, context_id)
  -> BroadcastQueue.publish_once(kind, text, speech_text, context_id="chat:ai_answer")
    -> BroadcastMessage(text=display_text, speech_text=speech_text)
      -> _operator_filter_broadcasts_for_speech()
        -> SpeechBroadcastDeliveryService.deliver(messages)
          -> sink.speak(message.speech_text or message.text)
```

`text` 始终是 GUI 显示文本，`speech_text` 只用于语音播报。

## 5. 实施计划

### P0 前置：StartSession 协议合规修复

目标：先补齐豆包文档标注的必传字段，避免后续优化建立在不合规 payload 上。

当前代码 `dialog.extra` 未传 `model`：

```python
"extra": {"strict_audit": False, "recv_timeout": self.config.recv_timeout, "input_mod": input_mod}
```

文档标注 `dialog.extra.model` 是必传字段，用于区分端到端模型版本。当前默认音色 `zh_male_yunzhou_jupiter_bigtts` 属于 O 系列音色，默认应使用 O2.0 版本：

```text
model = "1.2.1.1"
```

改造点：

- `DoubaoVoiceConfig` 增加：

```python
dialog_model: str = "1.2.1.1"
```

- `from_env()` 支持环境变量：

```text
DOUBAO_DIALOG_MODEL=1.2.1.1
```

- `_send_start_session()` 在所有模式下都传：

```python
"extra": {
    "strict_audit": False,
    "recv_timeout": self.config.recv_timeout,
    "input_mod": input_mod,
    "model": self.config.dialog_model,
}
```

约束：

```text
无论 ASR-only、纯 TTS、minimal_dialog、ChatTTSText 实验模式，都必须传 dialog.extra.model。
```

验收：

- StartSession payload 始终包含 `dialog.extra.model`。
- 默认值为 `1.2.1.1`。
- 环境变量可覆盖为 `2.2.0.0`。
- ASR 和 TTS 均能正常启动会话。

### P0：语音摘要层（机制 + 场景规则 + fallback）

目标：所有进入豆包的文本都必须先压缩。

改造点：

- `BroadcastMessage` 增加 `speech_text: str = ""`。
- `BroadcastQueue.publish()` / `publish_once()` 支持传入 `speech_text`。
- `SpeechBroadcastDeliveryService.deliver()` 优先使用 `message.speech_text`，为空时 fallback 到 `message.text`。
- `_operator_publish_ai_answer_for_speech()` 签名改为：

```python
def _operator_publish_ai_answer_for_speech(
    self,
    text: str,
    *,
    speech_text: str = "",
) -> BroadcastMessage | None:
    ...
```

- 增加 `_operator_generate_speech_summary(text, context_id="")`，作为 40+ 个调用点的统一 fallback。
- 同时定义本地场景规则：

`_operator_generate_speech_summary()` 必须是本地零成本逻辑，不调用 DeepSeek，不增加新的 AI 调用。推荐顺序：

```text
1. context_id 模板匹配
2. 关键词模板匹配
3. 固定短句归一化
4. 未命中时截断前 60 字并追加省略号
5. P1 speech_reply 上线后，优先使用 speech_reply 替代 fallback
```

场景规则：

```text
流程/参数/帮助类：只播“详情已显示”
等待确认：只播“请确认执行”
安全失败：只播“安全检查未通过，请查看屏幕”
执行完成：只播“执行完成”
普通问答：最多 60 字
```

固定短句规则：

```text
请确认执行。
已取消。
执行完成。
正在处理。
请补充目标位置。
当前正在执行，请稍候。
安全检查未通过，请查看屏幕。
缺少唤醒词，请说小正或小兵。
详情已显示在屏幕上。
```

验收：

- 长流程详情显示完整，但豆包只播摘要。
- 参数列表显示完整，但豆包不全文播。
- 所有豆包播报文本长度可在日志中看到。

### P1：DeepSeek 增加 speech_reply

目标：DeepSeek 返回界面文本和语音摘要两份内容。

结构示例：

```json
{
  "kind": "chat_answer",
  "suggested_reply": "给界面显示的完整回答",
  "speech_reply": "给豆包播报的短句，30字以内",
  "confidence": 0.9
}
```

约束：

- `speech_reply` 只能是自然语言短句。
- 本地仍要强制截断。
- 如果模型没有返回 `speech_reply`，本地从 `suggested_reply` 生成摘要。

具体改造点：

- `robot_modbus_lite/agent/llm_fallback.py` 的 `_system_prompt()`：增加 `speech_reply` 字段说明和字数限制。
- `robot_modbus_lite/agent/llm_fallback.py` 的 `_validate_payload()`：structured kinds 分支提取 `speech_reply`。
- `robot_modbus_lite/agent/orchestrator.py`：构造 `chat_answer` / `suggestion` 结果时保留 `speech_reply` 到 payload。
- `robot_modbus_lite/operator_ui_mixin.py`：处理 LLM payload 时，如果存在 `speech_reply`，调用 `_operator_publish_ai_answer_for_speech(text, speech_text=speech_reply)`。

`_validate_payload()` 中应显式保留顶层 `speech_reply`，避免模型返回后被丢弃：

```python
speech_reply = str(payload.get("speech_reply", "") or "").strip()
if speech_reply:
    result["speech_reply"] = speech_reply
```

该逻辑放在 structured kinds 分支中，和 `suggested_reply` / `text` 的提取并列处理。`speech_reply` 不参与 `reply = suggested_reply or text` 的界面展示选择，只作为语音播报候选。

验收：

- 普通问答界面可以显示完整回答。
- 豆包只播 `speech_reply` 或本地摘要。
- 模型返回超长 `speech_reply` 时本地截断。

### P2：固定短句 PCM 缓存

目标：重复固定短句不再调用豆包。

放置位置：

```text
DoubaoSpeechSink.speak()
```

流程：

```text
查缓存
  命中 -> 直接播放 PCM
  未命中 -> 调豆包 -> 保存 PCM -> 播放
```

缓存 key：

```text
hash(text + speaker + sample_rate + audio_format + cache_schema_version)
```

建议先做内存 LRU，稳定后再考虑落盘缓存。

流式模式处理：

```text
第一版缓存只对 batch synthesize_text 生效；
stream_synthesize_text 仍保持边合成边播放；
固定短句可选择强制走 batch 模式，以便缓存命中后完全跳过豆包。
```

验收：

- 第二次播“请确认执行。”不产生豆包请求。
- 缓存命中有日志。
- 改音色或格式后旧缓存不复用。

### P3：本地用量估算日志

目标：不用 `UsageResponse`，本地记录趋势数据。

每次 TTS 调用记录：

```json
{
  "type": "tts",
  "text_len": 12,
  "text_utf8_bytes": 36,
  "pcm_bytes": 38400,
  "speaker": "zh_male_yunzhou_jupiter_bigtts",
  "sample_rate": 24000,
  "audio_format": "pcm",
  "session_count": 1,
  "cache_hit": false,
  "interrupted": false
}
```

说明：

- 如果服务端仍返回 `154 UsageResponse`，优先记录官方字段。
- `pcm_bytes` 只代表服务端返回音频体积，不能等同官方 output audio token。
- 用于比较优化前后趋势。

### P4：ASR-only 和纯 TTS StartSession 精简

目标：减少无意义输入文本 token 和请求体。

具体改造点：

- `DoubaoVoiceClient._send_start_session()` 增加参数：

```python
async def _send_start_session(
    self,
    ws,
    session_id: str,
    *,
    input_mod: str,
    include_tts: bool = True,
    minimal_dialog: bool = False,
) -> None:
    ...
```

- `DoubaoStreamingAsrSession._run_async()` 调用时传：

```python
await client._send_start_session(ws, session_id, input_mod="audio", include_tts=False)
```

- `_transcribe_pcm_async()` 的 `audio_file` 模式也传 `include_tts=False`。
- TTS 模式保留 `include_tts=True`，并由 `DOUBAO_TTS_MINIMAL_SESSION` 控制是否精简 `system_role` / `speaking_style`。
- 所有模式都必须在 `dialog.extra` 中传递 `model`。

ASR-only：

```text
只发 asr + dialog.extra
不发 tts speaker/audio_config
不发 system_role/speaking_style
dialog.extra.model 必传
```

纯 TTS：

```text
保留 tts 配置
dialog 只保留必要 extra
去掉长 system_role/speaking_style
dialog.extra.model 必传
提供开关回退
```

验收：

- 流式 ASR 正常识别。
- 纯 TTS 正常合成。
- 关闭 minimal 开关后能回到旧行为。
- ASR-only 省略 `tts` key 时不触发 `42000020`。
- 不允许发送空 `tts` 对象或 `tts.extra = null`。

### P5：pcm_s16le

目标：减少音频传输体积和播放延迟。

改造点：

- `DoubaoVoiceConfig` 增加 `tts_audio_format: str = "pcm"`，从环境变量 `DOUBAO_TTS_AUDIO_FORMAT` 读取。
- TTS 请求 `audio_config.format` 从 `pcm` 改为 `pcm_s16le`。
- `DoubaoSpeechSink` 根据 `tts_audio_format` 选择播放 dtype：

```text
pcm       -> np.float32 / RawOutputStream dtype="float32"
pcm_s16le -> np.int16   / RawOutputStream dtype="int16"
```

- TTS 请求格式、缓存 key、播放 dtype 必须一致。

`DoubaoSpeechSink` 不一定需要改构造函数签名。实现时可以在 `speak()` 中通过当前 client 读取配置：

```python
client = self._client
if client is None:
    from .doubao_voice_client import DoubaoVoiceClient

    client = DoubaoVoiceClient()
    self._client = client

audio_format = getattr(getattr(client, "config", None), "tts_audio_format", "pcm")
```

然后 `_default_player()` 和 `_default_stream_player_factory()` 都要拿到同一个 `audio_format`，分别选择 `np.float32/int16` 和 `RawOutputStream(dtype="float32"/"int16")`。不能只改请求格式而不改播放 dtype。

注意：

- 该项不一定减少 output audio token 计费。
- 主要收益是网络体积减半和传输压力下降。
- 首包延迟是否下降需要实测，不能仅凭位深变化推断。

验收：

- TTS 播放音质正常。
- 不爆音、不变速。
- float32 和 int16 可通过配置切换。
- 对比 `pcm` 和 `pcm_s16le` 的首包延迟；如果无差异，则收益只按带宽和本地处理量计算。

### P6：短时间播报合并

目标：减少短时间内连续多次 TTS 合成调用，合并为一次，从而减少重复输出音频和 StartSession 次数。

建议新增：

```text
SpeechMergeBuffer
```

行为：

```text
300-800ms 内多条低优先级播报合并成一句
高优先级报警/急停不等待，直接播
用户新输入时清空待播报
```

该项涉及异步调度，放在摘要层和缓存稳定之后。

### P7：gzip 微优化

目标：减少小 payload 膨胀和 CPU 开销。

规则：

```text
payload 小于 100 字节时不压缩
音频 payload 是否 gzip 做配置开关
```

该项收益较小，最后处理。

## 6. 测试计划

### 6.1 成本相关回测

用同一组对话回测：

```text
现在有哪些命令和流程
查看点头流程
新建流程
移动到位置A
位置A X475 Y0 Z545 RX0 RY0 RZ0 速度30%
保存并执行
```

检查：

- GUI 显示完整内容。
- 豆包播报为短摘要。
- TTS 文本长度明显下降。
- 固定短句第二次缓存命中。

### 6.2 安全相关回测

检查：

- 无唤醒词执行类指令仍拒绝。
- 急停/暂停/停止当前不等待 DeepSeek。
- 安全预检失败只播摘要，完整原因显示在界面。
- 豆包播报优化不改变 QueryRecord / Modbus 执行链路。

### 6.3 兼容性回测

检查：

- 豆包 ASR 正常。
- 豆包 TTS 正常。
- sounddevice 播放正常。
- `pcm` 和 `pcm_s16le` 两种格式可切换。
- minimal StartSession 失败时可回退。

## 7. 不立即做的事项

以下事项暂不优先：

- 直接无验证地用 `ChatTTSText` 替换 `SayHello`。
- 长连接复用作为第一降本方案。
- 依赖服务端 `UsageResponse`。
- 为 gzip 微优化提前大改协议层。
- `ChatRAGText` 口语化改写。
- `UpdateConfig` 动态切换音色。
- opus 上行音频格式。

原因：

```text
当前最大费用来自输出音频 token。
摘要层、speech_reply、固定短句缓存能直接减少输出音频。
连接复用和 gzip 优化主要降低延迟或小幅减少请求体，不是第一矛盾。
ChatRAGText / UpdateConfig / opus 属于后续能力探索，不阻塞第一阶段降本。
```

## 8. 最终实施顺序

```text
0. StartSession 协议合规修复：DoubaoVoiceConfig 增加 dialog_model="1.2.1.1"，dialog.extra 始终传 model
1. 语音摘要层：BroadcastMessage 增加 speech_text，delivery 优先播 speech_text，并在 _operator_publish_ai_answer_for_speech 内做 fallback 摘要
2. ChatTTSText 实验开关：新增 DOUBAO_TTS_USE_CHAT_TTS_TEXT，验证纯 TTS 场景兼容性，未验证前继续默认 SayHello
3. DeepSeek speech_reply：模型返回完整回答和语音摘要
4. 固定短句 PCM 缓存：DoubaoSpeechSink 内部缓存，第一版仅对 batch 模式生效
5. 本地用量估算日志：文本长度、PCM 字节、session、缓存命中
6. ASR-only / 纯 TTS StartSession 精简：include_tts + minimal_dialog，带回退开关
7. pcm_s16le：DoubaoVoiceConfig 增加 audio_format，请求格式和播放 dtype 同步切换
8. 短时间播报合并：新增 SpeechMergeBuffer
9. gzip 微优化：小 payload 不压缩
```

## 9. 验收标准

完成后应满足：

- 豆包不再全文播报流程详情、参数表、帮助说明。
- GUI 内容不缩水，用户仍能看到完整信息。
- 固定短句重复播报不再重复调用豆包。
- 本地日志能看到 TTS 调用次数、缓存命中、播报文本长度趋势。
- 执行安全链路不受影响。
- 输出音频 token 在控制台账单中明显下降。
