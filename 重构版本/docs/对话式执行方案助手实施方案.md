# 对话式执行方案助手实施方案

更新时间：2026-05-26

## 最终评审结论

方案方向成立，但不能直接从 UI 层继续堆逻辑。实施前必须先补齐三个基础件：

1. 统一的 `ExecutionPlan` 数据模型，用来承载单步动作、复杂流程草案、预检结果和用户修改。
2. 明确的方案生命周期状态机，避免“草案、已预检、可执行、执行中”等状态混在自由 dict 里。
3. 结构化的反问状态 `PendingClarification`，把“缺什么参数、正在问什么、回答回填到哪里”记录下来。

落地原则：

- DeepSeek 负责理解、问答、草案生成和编辑意图结构化，不直接控制机械手。
- 本地规则优先处理高置信编辑命令和安全关键参数。
- 所有执行前必须经过本地白名单、参数校验、L1/L2/L3 预检和用户确认。
- `operator_ui_mixin.py` 只做 UI 编排，草案编辑、状态转换、追问逻辑应拆到独立模块。

## 目标

将当前“自然语言解析 -> 安全确认 -> 执行”的单向链路，升级为“AI 与用户多轮协商执行方案”的闭环。

目标流程：

```text
用户说话/打字
  -> AI 理解意图并拆解步骤
  -> 匹配 Func 并补全参数
  -> 参数缺失或歧义时反问
  -> 运行 L1/L2/L3 安全预检
  -> 结构化展示执行方案
  -> 用户修改/确认
  -> 修改后重新预检
  -> 确认后执行并展示进度
```

## 目标能力

### 1. 意图理解与步骤拆解

支持单步、多步、顺序动作和口语流程：

| 场景 | 示例 | 目标行为 |
|---|---|---|
| 单步操作 | 从 home 移动到焊接位置 | 生成 1 个 Func108 移动步骤 |
| 多步操作 | 先去取料点，等 3 秒，再到焊接位置 | 拆为移动、延时、移动 |
| 含速度/方式 | 先回零，然后慢速移动到 A 点 | 拆为回零 + 慢速移动 |
| 口语动作 | 打个招呼的小流程 | 结合动作别名和位置库生成草案 |
| 上下文引用 | 把上次那个流程再做一遍 | P2 后续能力：关联当前会话/最近流程 |

### 2. Func 映射与参数补全

目标 Func 范围：

| Func | 用途 |
|---|---|
| Func104 | 停止、暂停、急停、复位等系统动作 |
| Func106 | 关节点动 |
| Func107 | 虚拟轴点动 |
| Func108 | 直线插补/PTP 移动 |
| Func109 | 纯延时等待 |
| Func110 | 等待条件/并行辅助动作，按当前协议语义接入 |
| Func120 | IO 开关 |

系统应优先从位置库、流程库、模板表、当前记忆参数中补全参数。对于关键缺失参数，不应总是静默使用默认值，应进入反问。

反问示例：

- “焊接位置未找到，请先示教位置，或告诉我 XYZ/RX/RY/RZ。”
- “移动方式未指定，使用直线还是 PTP？”
- “速度未指定，使用慢速、中速还是当前默认速度？”
- “IO 对象未指定，请说明打开哪个 IO。”

### 3. 安全预检

生成方案后自动执行：

| 层级 | 检查内容 |
|---|---|
| L1 | 急停、报警、暂停、软限位、球面半径、速度钳位 |
| L2 | 可达性、FSTATUS、奇异区、中点建议 |
| L3 | 每步 L1/L2、步间隔、累计误差、禁入包围盒 |

失败时应给出中文原因和可采纳建议，例如：

- “目标 X=900 超出限位 800，建议改为 780。”
- “路径接近奇异区，建议加入中间点。”
- “当前有报警，请先确认报警原因并复位。”

### 4. 执行方案展示

目标展示形式：

```text
执行方案：打招呼

步骤1：Func108 移动到 home
目标：home (1475, 0, 1545, 0, 0, 0)
速度：50%

步骤2：Func107 小臂上移
轴号：8
距离：50mm
速度：50%

步骤3：Func107 小臂上移
轴号：8
距离：50mm
速度：50%

风险：
- L2 建议中点绕行

可操作：
采纳建议 / 修改参数 / 确认保存 / 保存并执行 / 取消
```

### 5. 修改确认循环

用户可在执行前多轮修改：

- “把第 2 步速度改成 30%”
- “步骤 2 的延时改成 5 秒”
- “删除第 3 步”
- “最后加一步回 home”
- “整体速度降到 30%”
- “采纳建议”
- “确认保存”
- “保存并执行”

每次修改后应重新运行预检并刷新方案。

### 6. 执行与进度

执行阶段展示：

```text
当前状态：执行中
进度：步骤 1/3，移动到 home
进度：步骤 2/3，延时等待 3.0 秒，剩余 1.2 秒
进度：步骤 3/3，移动到焊接位置
完成：全部 3 步执行完毕
```

## 执行方案数据模型

在进入阶段 1 前，先定义统一执行方案模型，避免继续在 `VoiceNlpPlan.flow_draft` 和 `_operator_pending_flow_draft` 的自由 dict 上堆逻辑。

建议新增模块：

```text
robot_modbus_lite/execution_plan.py
```

建议数据结构：

```python
@dataclass
class ExecutionPlan:
    plan_id: str
    name: str
    status: str
    steps: list[ExecutionStep]
    risks: list[RiskItem]
    suggestions: list[SuggestionItem]
    source: str
    created_at: str
    updated_at: str
    version: int = 1

@dataclass
class ExecutionStep:
    step_id: int
    action: str
    func_id: int
    params: dict[str, Any]
    target_label: str = ""
    description: str = ""
    precheck: StepPrecheckResult | None = None

@dataclass
class StepPrecheckResult:
    l1_status: str   # pass | warn | fail | skipped
    l2_status: str   # pass | warn | fail | unavailable | skipped
    l3_status: str   # pass | warn | fail | unavailable | skipped
    blocking: bool
    items: list[dict[str, str]]
    suggestions: list[dict[str, Any]]
    midpoint: dict[str, Any] | None = None

@dataclass
class RiskItem:
    level: str
    source: str
    step_id: int | None
    message: str

@dataclass
class SuggestionItem:
    suggestion_id: str
    source: str
    step_id: int | None
    message: str
    patch: dict[str, Any]
```

兼容策略：

- 初期从现有 `flow_draft["expanded_steps"]` 转换为 `ExecutionPlan`。
- 保存流程时仍可落回现有 `FlowEntry` / `FlowStep` / `query_table`。
- UI 层逐步改为展示 `ExecutionPlan`，而不是直接展示 dict。

## 方案生命周期状态机

执行方案必须有明确状态，避免 UI、NLP、预检、执行层各自判断。

建议状态：

```text
draft
  -> need_clarification
  -> modified
  -> prechecking
  -> precheck_failed
  -> ready
  -> confirmed
  -> executing
  -> completed
  -> failed
  -> cancelled
```

状态含义：

| 状态 | 含义 | 可接受用户操作 |
|---|---|---|
| `draft` | 已生成草案，尚未预检或保存 | 查询、修改、取消、预检 |
| `need_clarification` | 缺关键参数或动作映射 | 回答追问、取消 |
| `modified` | 用户修改后尚未重预检 | 查询、继续修改、重预检、取消 |
| `prechecking` | 正在运行 L1/L2/L3 | 等待、取消 |
| `precheck_failed` | 预检失败或有阻断风险 | 修改、采纳建议、取消 |
| `ready` | 预检通过，可确认 | 确认保存、保存并执行、取消 |
| `confirmed` | 用户已确认，准备执行 | 执行、取消 |
| `executing` | 已下发执行 | 查看进度、暂停、继续、停止 |
| `completed` | 执行完成 | 查看结果、保存模板 |
| `failed` | 执行失败 | 查看原因、重新修改 |
| `cancelled` | 用户取消 | 无 |

退出条件：

- 用户说“取消/不要了/放弃草案”进入 `cancelled`。
- 追问超时进入 `cancelled` 或回到 `draft`，由 UI 提示用户重新发起。
- 执行前设备状态变化为急停/报警时，方案保持但状态回到 `precheck_failed`。
- 用户确认执行前，必须处于 `ready` 或可即时重预检通过的状态。

## 反问状态机

通用参数追问需要结构化状态，不能只依赖 DeepSeek 自然语言输出。

建议新增模块：

```text
robot_modbus_lite/clarification_state.py
```

建议数据结构：

```python
@dataclass
class PendingClarification:
    clarification_id: str
    plan_id: str
    step_id: int | None
    missing_field: str
    question: str
    accepted_answer_types: tuple[str, ...]
    attempts: int
    expires_at: float
```

状态持有策略：

- `VoiceNlpAdapter` 不持有追问状态，避免 adapter 重建后状态丢失。
- 新增 `ClarificationManager`，由 `ExecutionPlanService` 持有。
- Qt 用户页只持有 `ExecutionPlanService` 实例，不直接管理追问队列。
- `ClarificationManager` 负责创建、查询、回填、超时清理和取消追问。
- 每个 `ExecutionPlan` 同一时间允许存在多个 pending clarification，但对用户逐个提问。

建议接口：

```python
class ClarificationManager:
    def add_missing_fields(self, plan: ExecutionPlan, fields: list[PendingClarification]) -> None: ...
    def current_question(self, plan_id: str) -> PendingClarification | None: ...
    def apply_answer(self, plan: ExecutionPlan, text: str) -> ClarificationResult: ...
    def expire(self, now: float) -> list[str]: ...
    def clear(self, plan_id: str) -> None: ...
```

参数缺失决策表：

| 参数 | 缺失处理 | 原因 |
|---|---|---|
| 目标位置/坐标 | 必须追问 | 没有目标不能执行 |
| 位置名歧义 | 必须追问 | 例如 A/A1/焊接A 同时存在 |
| 移动方式 | 可默认并告知，复杂路径可追问 | 默认 PTP/直线需和现场策略一致 |
| 速度 | 可默认并告知，高风险动作应追问 | 当前已有记忆速度 |
| 加速度/减速度 | 默认跟随速度并告知 | 现有规则为 acc=dec=speed |
| 延时时间 | 必须追问或拒绝 | 延时无默认值容易误执行 |
| IO 对象 | 必须追问 | IO 编号/名称不可猜测 |
| gesture 映射 | 必须追问 | 当前已有此类澄清 |

追问回答处理：

1. 用户回答进入 pending clarification 分支。
2. 解析回答并回填到对应 `ExecutionPlan` / `ExecutionStep`。
3. 如果仍有缺失参数，继续追问。
4. 如果参数齐全，状态进入 `modified` 并触发重预检。

## 草案编辑模块接口

步骤级编辑不应继续堆到 `operator_ui_mixin.py`。建议新增：

```text
robot_modbus_lite/draft_editor.py
```

职责：

- 编辑 `ExecutionPlan`。
- 返回新的 plan，不直接修改原对象。
- 记录最近一次修改，支持单步撤销。
- 不访问 GUI，不下发执行。

建议接口：

```python
class DraftEditor:
    def update_step_params(self, plan: ExecutionPlan, step_id: int, params: dict[str, Any]) -> EditResult: ...
    def update_all_speed(self, plan: ExecutionPlan, speed_pct: float) -> EditResult: ...
    def delete_step(self, plan: ExecutionPlan, step_id: int) -> EditResult: ...
    def append_step(self, plan: ExecutionPlan, step: ExecutionStep) -> EditResult: ...
    def undo(self, plan: ExecutionPlan) -> EditResult: ...
```

撤销语义：

- `undo()` 只撤销最近一次成功编辑。
- 撤销后清空撤销快照；再次调用 `undo()` 返回失败提示“当前没有可撤销的修改”。
- 第一版不实现 redo，避免用户误以为撤销和恢复会自动交替。
- 保存、取消、执行后必须清空撤销快照。

编辑命令解析优先级：

1. 如果存在 pending plan，先尝试本地规则识别编辑命令。
2. 本地规则命中则直接编辑，不调用 DeepSeek。
3. 本地规则未命中但像编辑意图，可让 DeepSeek 只做“编辑意图结构化”，不能直接执行。
4. 编辑完成后状态进入 `modified`。

第一阶段支持的编辑命令：

- “把第 N 步速度改成 X%”
- “第 N 步延时改成 X 秒”
- “删除第 N 步”
- “最后加一步回 home”
- “整体速度改成 X%”
- “撤销上一次修改”

本地正则最小集合：

| 意图 | 示例 | 建议 pattern |
|---|---|---|
| 修改步骤速度 | 第 2 步速度改成 30% | `第\s*(\d+)\s*步.*速度.*?(\d+(?:\.\d+)?)\s*%?` |
| 修改步骤延时 | 步骤 2 的延时改成 5 秒 | `(第|步骤)\s*(\d+)\s*步?.*延时.*?(\d+(?:\.\d+)?)\s*(秒|s|毫秒|ms)?` |
| 删除步骤 | 删除第 3 步 | `删除.*(第|步骤)\s*(\d+)\s*步?` |
| 整体速度 | 整体速度降到 30% | `(整体|全部|所有).*速度.*?(\d+(?:\.\d+)?)\s*%?` |
| 追加步骤 | 最后加一步回 home | `(最后|末尾|后面).*加.*步(.+)` |
| 撤销 | 撤销上一次修改 | `(撤销|恢复上一步|取消刚才的修改)` |

解析边界：

- 正则命中后仍必须校验步骤编号存在。
- 速度范围、延时范围、追加步骤动作必须走本地参数校验。
- 正则未命中但像编辑意图时，再调用 DeepSeek 编辑意图结构化。
- 正则解析逻辑放在 `ExecutionPlanService` 或独立 parser 中，`operator_ui_mixin.py` 只调用服务。

## 修改后重新预检策略

重预检不应无条件高频全量执行。

触发规则：

| 修改类型 | 预检策略 |
|---|---|
| 只改速度/acc/dec | 立即跑 L1；保存/执行前跑全量 |
| 改目标位置/坐标 | 跑 L1 + L2 |
| 新增/删除/重排步骤 | 跑 L1 + L2 + L3 |
| 采纳 L2 中点建议 | 跑 L1 + L2 + L3 |
| 只改描述/名称 | 不跑预检 |

防抖策略：

- GUI 文本连续输入不立即预检。
- 用户明确提交编辑命令后触发预检。
- 如后续做表单式编辑，建议 300-500ms debounce。

执行前规则：

- 无论前面是否做过增量预检，保存并执行前必须全量跑 L1/L2/L3。
- 预检期间如果设备进入报警/急停，方案状态改为 `precheck_failed`。

## 两条确认路径的统一策略

当前有两条路径：

- `_operator_pending_confirm_plan`：单步/多步原子动作确认。
- `_operator_pending_flow_draft`：复杂流程草案确认。

短期策略：

- 底层先保持两条路径，避免大改执行链路。
- 展示层统一为 `ExecutionPlan`。
- 原子动作进入确认时临时包装为单步或多步 `ExecutionPlan`。
- 流程草案从 `expanded_steps` 转为 `ExecutionPlan`。

长期策略：

- 将确认页、草案页、执行方案页统一由 `ExecutionPlan` 驱动。
- `VoiceNlpPlan` 只表示 NLP 解析结果，不再承担执行方案状态。

## 错误路径和降级策略

| 场景 | 策略 |
|---|---|
| DeepSeek 超时/额度不足 | 回退本地规则和知识库；不能生成可靠草案时提示拆分输入 |
| 预检不可恢复失败 | 标记 `precheck_failed`，禁止确认执行，只允许修改/取消 |
| 预检可采纳建议 | 保持 `precheck_failed` 或 `ready_with_warning`，允许采纳建议后重预检 |
| 编辑非法步骤 | 提示“当前方案没有第 N 步”，不改变方案 |
| 删除后误操作 | 支持“撤销上一次修改” |
| 执行前设备报警 | 停止进入执行，状态改为 `precheck_failed` |
| 草案长期未确认 | 超时后提示重新确认或取消 |

## 安全原则

- DeepSeek 只负责理解、问答、草案生成和资料检索。
- DeepSeek 不直接控制机械手。
- 所有执行必须经过本地白名单、参数校验、安全预检和确认。
- 用户未确认前，草案不得自动保存或执行。
- 应急动作仍走既有可审计 Func104 快速通道。

### 2. 两条确认路径迁移策略

当前两条路径不能继续各自扩展，否则会形成两套编辑、两套预检、两套确认。

| 阶段 | 迁移动作 |
|---|---|
| 阶段 0 | 新增 `ExecutionPlan`，支持从 `VoiceNlpPlan` 和 `flow_draft["expanded_steps"]` 包装转换 |
| 阶段 1 | 优先让 `_operator_pending_flow_draft` 接入 `ExecutionPlan` 和 `DraftEditor` |
| 阶段 3 | 将 `_operator_pending_confirm_plan` 也包装为 `ExecutionPlan`，统一预检展示 |
| 阶段 4 后 | 目标收敛为一个 `_operator_pending_execution_plan`，旧字段只作为兼容期桥接 |

短期允许底层执行路径保持现状，但用户可见的草案、编辑、追问、预检展示必须统一走 `ExecutionPlan`。

### 4. DeepSeek 编辑意图协议

DeepSeek 可以辅助理解模糊编辑表达，但不能直接修改执行方案，也不能直接生成可执行控制动作。

本地规则优先处理：

- “第 N 步速度改成 X%”
- “第 N 步延时改成 X 秒”
- “删除第 N 步”
- “最后加一步回 home”
- “整体速度改成 X%”
- “撤销上一次修改”

本地规则未命中且存在 pending plan 时，DeepSeek 只能返回结构化编辑意图：

```json
{
  "type": "edit_intent",
  "operation": "update_step_params | update_all_speed | delete_step | append_step | undo | unknown",
  "step_id": 2,
  "params": {
    "spd_pct": 30
  },
  "append_action": null,
  "reason": "用户要求把第2步速度改成30%"
}
```

处理规则：

1. schema 校验失败则拒绝，不改变草案。
2. `operation=unknown` 时转为追问。
3. `append_step` 必须再经过本地 Func 白名单和参数校验。
4. 所有编辑最终由 `DraftEditor` 执行，并触发状态变更和预检。

### 5. 预检短路和性能策略

修改后重预检必须避免“每次全量同步跑完”的体验问题。

| 场景 | 策略 |
|---|---|
| L1 阻断项失败，如急停、报警、暂停、目标明显越界 | 立即停止，不继续跑 L2/L3 |
| L1 非阻断警告，如速度钳位 | 可继续跑 L2/L3，并展示 warning |
| 只改速度/acc/dec | 立即跑 L1，执行前再全量跑 L1/L2/L3 |
| 改目标位置/坐标 | 跑 L1 + L2 |
| 新增、删除、重排步骤 | 跑 L1 + L2 + L3 |
| 用户连续输入 | 不触发预检 |
| 表单式编辑 | 300-500ms debounce 后预检 |
| 保存并执行 | 无论之前跑过什么，必须全量跑 L1/L2/L3 |

### 6. 错误恢复路径

状态机需要明确失败后如何回到可编辑状态。

| 当前状态 | 用户/系统事件 | 新状态 |
|---|---|---|
| `precheck_failed` | 用户修改参数 | `modified` |
| `precheck_failed` | 用户采纳建议 | `modified` |
| `precheck_failed` | 用户取消 | `cancelled` |
| `need_clarification` | 用户补齐参数 | `modified` 或继续 `need_clarification` |
| `need_clarification` | 超时或用户取消 | `cancelled` |
| `prechecking` | 设备进入报警/急停 | `precheck_failed` |
| `executing` | 执行失败 | `failed` |
| `failed` | 用户查看原因后重新修改 | `modified` |

不做自动重试。所有失败恢复都必须由用户明确修改、采纳建议、重新确认或取消。

### 7. Qt UI 技术选型

本阶段固定使用现有 Qt Widget，不引入 QML、HTML 嵌入或 Web UI。

结构化方案卡片的最低目标：

- 显示步骤编号、动作、Func、目标、速度、关键参数。
- 显示风险和建议。
- 提供确认保存、保存并执行、取消、采纳建议入口。
- 支持从自然语言输入触发编辑，不要求第一版做拖拽排序或复杂表格编辑。

### 9. 最终实施默认决策

- 范围：只做 Qt GUI 用户页。
- 数据模型：先包装迁移，不一次性删除旧路径。
- 编辑策略：本地规则优先，DeepSeek 只做兜底结构化。
- 预检策略：阻断短路、提交后预检、执行前全量预检。
- UI 策略：沿用 Qt Widget，先做可读的结构化方案卡片。
- 安全边界：DeepSeek 不能直接修改控制器，也不能绕过本地校验、预检和确认。
